## Step 2 — the latch (implementation)

`git cherry-pick 1542df0`, then in src/battle.rs:

- NEW FIELD `fight_latch: bool` — canon's `oBattleState_Index_00 == 4`
  handover latch. Set at `Battle::new` when the descriptor's SKIP_INTRO
  declares the pairing against a mid-fight canon state (a state-loaded
  battle's state word IS 4), and in update()'s intro machine when
  `intro_next` walks past the last enemy (the handover site:
  sub_8007A0C's `mov r0,#4 / str r0,[r5,#oBattleState_Index_00]`,
  asm00_1.s:9716-9718, after the last enemy materialises).
- `hp_readout_live()` = `self.fight_latch && !matches!(self.seq.state,
  SEQ_0C | SEQ_10)`. The `SEQ_0C | SEQ_10` arm is canon's terminate arm
  (eStruct2038160_getBattleTerminate01() != 0 leaves to state 0x10 before
  the chain, asm00_1.s:9757-9776). The `intro_fade`/`intro_next` arms of
  F43's first cut are REPLACED by the latch; the `banner` arm is DROPPED
  (the only banner it could see is the closing ENEMY-DELETED one, armed
  only when `over` — vacuous). No paused term: `oGameState_BattlePaused`
  is tested AFTER the chain (asm00_1.s:9795).
- A latch-probe byte at 0x020000C0 (BATTLE_MARKER's own tail, one volatile
  store per frame, written by nothing else): bit0 live, bit1 fade, bit2
  next, bit3 banner, bit4 over, bit5 latch. Read with `--watch`.

No new numeric constants; fitted-constant count unchanged (19).

## Follow-up corrections (docs-only pass, 2026-09-16)

Cite corrections applied after verifier-hyper's read against reference/bn6f:
`bl dispatch_801FEEE` is asm00_1.s:9753 (not :9745, which sits inside the
`#0xc` handover block at 9746-9748); `battle_update_8007A44`'s label is
asm00_1.s:9727 (not :9729, which is the `bl eStruct203F7D8_getUnk01` line);
the `mov r0,#4 / str r0,[r5,#oBattleState_Index_00]` write is
asm00_1.s:9716-9718 (comment at 9716, instructions 9717-9718 — not :9722,
which is `pop {pc}` + `.balign` + `off_8007A40` data); and the bit-3 tests
are asm01.c:71 and :78 (plus asm00_1.s:9755), while asm00_1.c:11121 tests
bit 1 only.

**FORWARD-BLOCKING CAVEAT.** The SKIP_INTRO arm's premise -- that a
state-loaded row's canon `oBattleState_Index_00` is already 4 -- is NOT a
ROM fact. There is exactly one write of 4 in the whole tree,
asm00_1.s:9717-9718 at the tail of sub_8007A0C, and the only route into it
is the `Index_00 == 0` intro machine via the table entry
`.word sub_8007A0C+1` at asm00_1.s:9567, so a battle that never entered
state 0 cannot have executed it. SKIP_INTRO is declared at src/fixture.rs:79
as "not a ROM fact", cursor's canon side loads /tmp/chipselect.state, which
tools/states.py documents as a hand-made ROOT, and no tool has ever read the
byte at 0x02034880 (`eBattleState_Index_00`, resolved from
reference/bn6f/bn6f.map:7093 with offset 0x0 per
include/structs/BattleState.inc). Opening is the arm the asm proves; cursor
is the arm the fixture bit asserts. It is acceptable for now because
cursor's row reads 1/1/170 on main WITHOUT any gate, so this branch is
gate-neutral on that row -- it restored a number, it did not buy one.

**For a later tooling ticket:** the word to make peekable is 0x02034880 on
the canon side (`eBattleState_Index_00`), currently unreachable because
tools/harness.py exposes only `--only`/`--list`/`--no-gallery`/`--ui` —
`--peek`/`--watch` reach a capture only as per-Side `extra=` passthroughs
(tools/harness.py:355, :886), which a harness run does not surface as a
reported value.
