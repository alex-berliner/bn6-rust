## Step 3 — NEW EVIDENCE this session (the actual blocker)

The T153 plan's navi_spawn row requires a canon side that **actually spawns a
navi** (ProtoMan art + 900 HP), not the flip-route Gunner virus the existing
navi-gunner row uses. Walking the ROM this session, I checked whether any
existing encounter-table formation contains enemy_idx = 0x0185 (the
ActorType=1 / AIIndex=0x17 navi id) -- the answer is **no**:

- ROM walk (0x080a0000..0x08100000) for the quad pattern `XX 85 01` where
  byte 0's high nibble = 0x10 (the enemy dispatch type the sub_80AA824 reader
  branches on, asm29.s:10707-10711): **zero hits**.
- The known Mettaur+Gunner formation at 0x080b5347 (T9c's battlestart_gunner
  record) carries only enemy_idx 0x0001 + 0x0085 quads (Mettaur + Gunner,
  both ActorType=0/virus). Every other encounter formation reachable from
  the four event-flagged tables (off_8020170 default / 8020178 EVENT_67F /
  8020180 EVENT_680 / 8020188 EVENT_681) is the same shape: no navi quads.
- CentralArea1 list (0x080b4b78, 14 records, the T87 EVENT_681 walk source)
  has 14 records × 4-byte quads = 56 quad slots, all with byte 2 in
  {0x01, 0x02, 0x04, 0x13, 0x85, 0x1f, 0x37} (the v0/v1/v3 Mettaur / Gunner
  / ai4 ranks / shells -- all ActorType=0 virus). Zero navi quad hits.

So **a true navi spawn is not reachable by the encounter roll alone**. The
ROM has no formation that natively spawns a navi. The flip-route scenario
the navi-gunner row uses (poke-at AIData ActorType=1 + NameID=0x0185 on the
Gunner virus the battlestart_gunner state spawns at frame 69) is the ONLY
canon-near way to render a navi spawn today, and it produces a Gunner virus
art + 60 HP spawn, not the ProtoMan art + 900 HP a true navi spawn would.

Per `reference/bn6f/asm/asm00_1.s:8546-8561` (AUDIT wave 3c "fresh-state"
ticket comment, the worklog verified this ticket too): `oBattleSettings_
EnemySetupArrPtr` is a **plain ROM pointer, not a RAM copy** -- confirmed
byte-for-byte by walking eToolkit → BattleStatePtr → BattleSettings →
EnemySetupArrPtr live and diffing the target bytes against `/tmp/bn6f_
real.gba` (0 diff). The spawn dispatch loop
(`SpawnBattleObjectUsingBattleEntityConfig_8007368`, asm00_1.s:8572-8636)
follows that pointer straight into ROM. So:

- **Runtime --poke of an encounter quad** is dead (mgba busWrite16 cannot
  write ROM; T151 measured). The only path to a non-ROM-canonical encounter
  is a ROM-file data patch (tools/patch_sterile.py's `--empty-net-
  encounter` does this for ONE specific quad, the only safe one of its
  kind).
- **Repointing CurBattleDataPtr (0x02001b9c) to a fake BattleSettings
  struct in RAM** CAN work in principle -- the spawner dereferences
  `[r5,#oBattleState_BattleSettings]` then `[r0,#oBattleSettings_
  EnemySetupArrPtr]`, both RAM dereferences. If the fake struct's
  EnemySetupArrPtr points at a RAM formation array I write, the spawn reads
  from there. **T145 worklog step 4 reported this route closed** ("the
  repoint sticks but the spawn still builds the Gunner, spawn reads ids
  from a RAM copy made earlier in init") -- but the AUDIT wave 3c note
  says EnemySetupArrPtr is ROM, not RAM, which makes T145's negative finding
  consistent with a T145-side setup bug (e.g., the fake struct's
  EnemySetupArrPtr was left zero / pointing at a Gunner formation rather
  than a custom navi formation). Re-attempting this needs a fresh state-
  build session.

## Step 5 — what blocks landing this ticket (the actual blocker)

The navi_spawn row's canon side requires a canon state that spawns a TRUE
navi (ProtoMan art + 900 HP, via `byte_81067FC` art + `byte_8106804 row 0`
HP). Per step 3, no such state exists on main today. Building one needs:

A. A `tools/states.py` recipe that creates a fake BattleSettings struct in
   free EWRAM (e.g. 0x0203E000, the same scratch T145 used), with its
   EnemySetupArrPtr field pointing at a custom formation array (e.g.
   0x0203E100) containing a single 4-byte enemy quad: `11 25 85 01` (slot
   index 1, panel (5,2), enemy_idx = 0x0185, high byte in the high nibble
   = 0x01).
B. A frame-60 poke-at that writes the fake struct + the custom formation
   array to RAM.
C. The T131 OPT lever (`oS2001c04_Unk_28` at 0x02001c2c nonzero,
   `oS2001c04_OptCurBattleDataPtr` at 0x02001c30 with high byte = 0x08)
   to make the encounter roll ADOPT the fake record wholesale instead of
   rolling a real one. The OPT adoption is consumed at the build step, so
   the pokes must hit frame-59 (per T131's measurement, T151b step 2
   cite).
D. A watch-write on `oBattleState_BattleSettings` (BattleState.inc +0x3c,
   read by sub_8007358 at asm00_1.s:8565) at the populate frame to
   confirm the fake struct IS what the spawn reads. The T145 negative
   result ("spawn still builds the Gunner") was almost certainly a T145
   bug in the fake struct layout, not a real fork; re-running with
   careful field layout should succeed.
E. Verify the spawn populates at capture frame ~69 with NameID 0x0185,
   HP 0x0384 (900), panel (5,2), exactly like a true navi spawn would.

That sequence is 1-2 sessions of work and is not landing in this session.
