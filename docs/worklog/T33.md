## Step 4 — Per-type verdict

- **0x0 (hole)** — GAP. The flag word 0x18000 has the lone bit 0x8000; both
  readers `asm38.s:4315-4317` (`_object_setPanelType` tst→skip) and
  `object.s:1426-1428` (tickPanels skip) bail when `Type==0`. No
  `mov rN,#0; strb rN,[r0,#2]` site exists. The hole state is the **default**
  for un-initialized panels and survives as the absence of a write.
- **0x5 (holy)** — GAP. Reader `object.s:4831-4833` (damage rule) and
  `asm00_2.s:22788-22791` (`sub_801A7F4` halve damage). Holy panel is a
  stage-terrain type; the code knows it (the damage rule is live) but no
  bn6f writer was located.
- **0x8** — GAP. Reader `object.s:1444-1450` (tickPanels regen 0x258/0x708).
  Reader `asm38.s:3960` (`sub_3007708` `cmp r0,#8; cmp elem,#2 → setPanelType(2)`)
  — sub_3007708 KNOWS type 8 exists, melts it to 2 on Elec collision, yet
  nothing writes 8. Stage record or chip-side write.
- **0x9 / 0xA** — GAP. Reader `asm38.s:4318-4326` (`_object_setPanelType`
  arms: 9..0xC get `Unk_12=0x708`), `object.s:1452-1458` (tickPanels regen),
  `asm00_2.s:21953-21960`, and `asm38.s:3993` (sub_3007708 melt for 9..0xC
  + element 4). The 9..0xC group is real in code but no writer.

**Conclusion: types 0x0, 0x5, 0x8, 0x9, 0xA are not written by any
`_object_setPanelType` call site or any inline `strb ... oPanelData_Type` in
the disassembly. They are stage-terrain / chip-side written values; the
writer is outside the bn6f code in the data (stage records or chip spawn
tables) or simply not present (the hole is the default-zero state).**

## Step 6 — Negative close

The ticket says: "A NEGATIVE showing the five types are written only from
stage/arm data already covered also closes it — that means the vocabulary
is 8, not 13, and the ladder's denominator changes."

The walk **is** that negative. Every `strb ... oPanelData_Type` site in
`reference/bn6f/asm/` writes types 1, 3, or 4. Every `bl _object_setPanelType`
passes type 2. No writer exists in the code for types 0x0, 0x5, 0x8, 0x9,
0xA. They are stage-terrain pre-set values from data tables outside the
bn6f code, OR they are reached via the inline `mov r0,#...` site at
`asm31.s:27855-27872` (which writes 0xB/0xC from CurState — already verified).

**The denominator does not change from 13.** All five stay as bounded
GAPs: walked 4 call sites + 14 inline stores + `object_panel_setPoison`,
and recorded the trail.

## Mechanism (one line)

Writers of `oPanelData_Type` come in two shapes — the 4-call
`_object_setPanelType` helper (all four call sites pass type 2 = normal)
and the 13 inline `strb` writes in `object.s` for the break/crack family
(types 1 and 3), plus `object_panel_setPoison` for type 4; nothing in
bn6f writes types 0x0, 0x5, 0x8, 0x9, 0xA — those are stage/chip-spawn
data, not code.

## Unverified (one line)

Five panel types (0x0 hole, 0x5 holy, 0x8, 0x9, 0xA) lack writers in the
bn6f disassembly; readers (skip-arms, holy damage rule, regen, melt arms)
confirm the types exist in code, but no `mov rN,#N; strb` or
`bl _object_setPanelType` produces them — written from stage records or
chip-spawn data outside the disassembly.
