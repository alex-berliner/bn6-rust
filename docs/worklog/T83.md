### Erratum 1 — the bit pattern in the ticket is wrong

The ticket body (line 23 of the ticket text) reads:

> bits `0x4000|0x8000` from `oBattleObject_StatusFlags2`

That is `0xc000 = OBJECT_FLAGS_IMMOBILIZED | OBJECT_FLAGS_CONFUSED`. But
the asm gate that arms `METTAUR_WANDER` is the `=0xa000`
BLIND|CONFUSED `tst` at `reference/bn6f/asm/asm31.s:171395-171397` —
0xa000 = `OBJECT_FLAGS_BLIND(0x2000) | OBJECT_FLAGS_CONFUSED(0x8000)`. The
existing comment at `src/objects.rs:352` already names this:

> "OBJECT_FLAGS_BLIND/CONFUSED/IMMOBILIZED (0xa000/0x4000) yet,
>  include/structs/CollisionData.inc:16-18"

`include/structs/CollisionData.inc:16` (BLIND=0x2000), `:17`
(IMMOBILIZED=0x4000), `:18` (CONFUSED=0x8000). So the ticket's `0x4000`
should be `0x2000` to match the RowCheck gate that arms `METTAUR_WANDER`,
otherwise the flipped gate would arm `Wander` on a paralyzed+confused
Mettaur (a subset of canon's cases — fine for confused — but missing the
blind case the cited gate actually covers).

`object_getFlag` (`reference/bn6f/asm/asm00_2.s:21627-21632`) returns
`oCollisionData_ObjectFlags1` (offset 0x3c from the CollisionData struct,
**not** `oBattleObject_StatusFlags2`). There is no
`oBattleObject_StatusFlags2` in this ROM: `BattleObject.inc` does not
have a `StatusFlags2` field — the flag words live in CollisionData
(`ObjectFlags1` at +0x3c, `ObjectFlags2` at +0x40, both 32-bit). The
ticket's "StatusFlags2" naming is a second erratum; the gate reads
`ObjectFlags1` (the first 32-bit word).

The ticket (line 23) calls for "a battle with one Mettaur and a
confused-source chip firing on MegaMan". This needs:

1. A confused-source chip — there is none (existing comment at
   `src/objects.rs:346-348`: "This project has no chip that sets

2. A `set_confused()` hook on the battle side to apply CONFUSED to the
   Mettaur slot. None exists.
3. A `Style::Confused` variant on `Style` enum. None exists
   (`src/ai.rs:143-160`'s `Style` enum has Mettaur/Thrust/Divide/Gunner
   only — T81 §"T72 PARTIAL claim audit" confirmed T72's
   `Style::Confused` claim was a worklog-only artefact in commit
   `462ccda`, no scaffolding in the tree).
4. A per-AIIndex confused-stub at `src/ai.rs:143-160` — the T72 PARTIAL
   claim, REFUTED by grep by T81.

The ticket tells me to add the row bound onto the Mettaur slot via a
battle with one Mettaur and a confused-source chip. Building that
requires items 1–4 above, **and adding them widens scope** (the ticket
says "no other src/ edit" beyond `src/objects.rs:352+430` and the new
anchor; it forbids touching `src/ai.rs`, `src/battle.rs`, `src/fixture.rs`
explicitly in the "NOT" list).

In short: the ticket asks me to make the gate runtime-active AND prove
it via a row, but the row's mechanism (confused chip → set_confused →
style dispatch → per-AIIndex confused stub) lives in modules the ticket
forbids me to touch.

## What would unblock T83

* **T83a**: Just the gate flip — `BLIND_OR_CONFUSED` becomes a runtime
  read of `oCollisionData_ObjectFlags1` at the enemy slot's
  `CollisionDataPtr`. Address: enemy slot 0 base `0x0203ab60` (PAUSED
  rows), `oBattleObject_CollisionDataPtr` at +0x54
  (`reference/bn6f/include/structs/BattleObject.inc:144`), dereferenced

  No anchor.rs needed — just a function in `objects.rs` that reads
  `*(me.actor_ptr + 0x54) as *const u32` and tests bit `0xa000`. No
  harness row; this lands the code without proof and depends on a
  follow-up for the row. Scope widening: still 0 (only
  `src/objects.rs:352+430` touched).
* **T83b** (deferred): The confused-source chip + per-AIIndex confused

  effect to the chip data, which IS `src/battle.rs` and `src/fixture.rs`
  — that ticket's scope is wider than T83 allows.

This split is the right shape but is **not what T83 asks for**; T83
bundles the two and forbids the second half's files. The honest move
on this branch is NEGATIVE.
