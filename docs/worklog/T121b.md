## Environment facts established first

- The struct includes live in the disassembly submodule:
  `reference/bn6f/include/structs/PanelData.inc` (`Flags` u32 at +0x14). The .inc's comment block
  names only 0x2 (blocks movement), 0x20 (enemy panel) and the 0x00800000.. support/attack group —
  NONE of those appear in the 13-word type table. The 0x20 enemy-panel bit is OR'd by
  `_object_updatePanelParameters` from `Alliance << 5` (asm38.s:4220-4223), separately from the table.
- ROM source of the table: `/tmp/bn6f_real.gba` and `reference/bn6f/bn6f.gba` are byte-identical
  (`cmp` clean). Table at file offset 0x1D7E24 (address 0x081D7E24).
- `_object_updatePanelParameters` has NO per-frame caller: callers are asm38.s:3736/3760/4044/4075/4197
  (whole-field init sweep sub_30078C8 loops cols 7..1 × rows 4..1), :4329 (the setter's tail) and
  object.s:1475 (regen). So a raw RAM poke of `Type` does not re-OR flags on its own; flags move
  only through the writer routines.

## Step 1 — the 13 words (ROM bytes only) — LANDED (ebfa97a)

tools/panel_flags_export.py reads the ROM bytes at 0x081D7E24 and writes assets/panels.bin
(52 raw bytes, one LE u32 per type). Words (each with its ROM address):

| type | @addr | word | bits (named after the only word that sets them) |
|---|---|---|---|
| 0x0 | 0x081D7E24 | 0x00018000 | HOLE(0x8000) + unnamed 0x10000 |
| 0x1 | 0x081D7E28 | 0x00014000 | BROKEN(0x4000) + 0x10000 |
| 0x2 | 0x081D7E2C | 0x00010010 | unnamed 0x10 + 0x10000 |
| 0x3 | 0x081D7E30 | 0x00010050 | +CRACKED(0x40) |
| 0x4 | 0x081D7E34 | 0x00010110 | +POISON(0x100) |
| 0x5 | 0x081D7E38 | 0x00012010 | +HOLY(0x2000) |
| 0x6 | 0x081D7E3C | 0x00010410 | +GRASS(0x400) |
| 0x7 | 0x081D7E40 | 0x00010810 | +ICE(0x800) |
| 0x8 | 0x081D7E44 | 0x00011010 | +TYPE8(0x1000) |
| 0x9..0xC | 0x081D7E48..54 | 0x00010210 | +UNK_9C(0x200) |

Bit-name provenance: each of 0x40/0x100/0x2000/0x400/0x800/0x1000/0x4000/0x8000 is set by exactly
one type's word → named after that type (derived, ROM bytes). 0x10 is set by every type except
hole/broken; 0x10000 by ALL 13 — both keep `unnamed:` status. 0x200 marks exactly the 9..0xC group
the setter gives `Unk_12=0x708` (asm38.s:4318-4326). inventory.py's `PANEL_TYPE_FLAG_WORDS`
(already on main) carries the same words; my read is an independent confirmation, no row changed.

**Cross-check that fell out free (corroboration, NOT a live rule)**: `object_crackPanel`'s flags
rewrite `Flags = (Flags & ~0x3f0f) + 3` (asm/object.s:2215-2218) clears exactly the table's
per-type low bits (bits 0-3 and 8-13); normal's word 0x10010 has no bit inside the mask, so
crack = OR 0x40 → 0x10050 = the type-3 word exactly.

## Step 2 — canon flags watch over the doll-poison route — MEASURED (2 captures)

Route: the chip-poisseed canon side (`_chip_canon_0c("46")` — STERILE + afterdissolve_0x0c state,
chip poked into hand+library, one-shot press at frame 3), watched with `--watch 0x02039C00:0x320`
(the whole panel array: rows of 8 panels — 6 visible + 2 Alliance=0xFF padding — 0x20 bytes each;
capture 1 watched only the first 18 words and saw nothing, capture 2 widened to the full array).

- **Frame 52**: the seed object appears over its target panel — that panel's flags gain the
  0x80000000 ally-attack bit (`0x00010032 → 0x80010032` on p(5,2)).
- **Frame 53**: SIX panels — cols 4-6 × rows 1-2, the 3x2 enemy-side area — all flip:
  flags `0x00010032 → 0x00010134`, `Type` byte 02→04, `Animation` 02→04.
- **The writer is `object_panel_setPoison` (object.s:2540-2563), byte-for-byte**: guard
  `Flags & 0x10` (:2544-2546), then `Flags = (Flags & ~0x3f5f) | 0x114` (:2547-2551) — and
  `(0x10032 & ~0x3f5f) | 0x114 = 0x10134` exactly — then `Type=4`, `Animation=4` (its two
  `strb #4` stores, :2552-2554). The 3x2 loop is the seed gimmick's per-CurState writer table
  `byte_80E2588` (asm31.s:89654-89667: entries = 0x10 guard byte + writer pointer, choosing
  object_crackPanelDup1 / object_breakPanel_dup3 / object_panel_setPoison), dispatched by
  `t4_0x1e_80E25D0` (asm31.s:89669-89682).
- So the answer to the ticket's step-2 question ("does it equal your type-4 row"): the POISON bit
  0x100 yes; the full table word no — the live writer is setPoison's own masked template
  **0x114** = the table's 0x110 + an **unnamed 0x4 bit set by setPoison itself**; the mask also
  **clears 0x2 (blocks movement)**. The 0x100 flag and the Type byte are NOT written
  independently — setPoison writes both together (plus Animation) in one routine.
- Aside measured free: `Unk_12` reads 0x0708 on fresh NORMAL panels (frame-0 dump, +0x12), so the
  setter's 9..0xC arm is not that value's only writer — tickPanels' regen writes it too
  (asm/object.s:1430-1434).

## The row design considered and rejected (the bounded NEGATIVE)

Design (worked out before any capture, recorded here so it is reviewable): scenario =
`/tmp/battlestart.state` (the opening row's canon root, no rebuild) + canon `--poke-at` frame 10
poking panel (1,1)'s Type byte (0x02039C02=4) and flags halfwords to 0x00010112 (= the measured
fresh word 0x10012 OR the type-4 table word 0x110 — what `_object_updatePanelParameters` would
leave); rust side via a poke-visible setter in src/field.rs (a `PANEL_POKE_BOX` static consumed by
the already-per-frame `Panels::update`, battle.rs:4275 call site untouched, + a
`PANEL_FLAGS_WATCH` static for `--watch`; addresses read from the ELF with `nm`, never hardcoded);
row isolated with bg VISIBLE (the poked Type re-renders poison tiles via sub_800C5E0's per-panel
rebuild, object.s:1709-1746 — that tile is the pixel carrier); negative = one-sided (canon
UNpoked vs rust poked), the only non-blind reading since a symmetric no-poke pair is identical.

Coordinator decision (2026-09-18): **stop at the bounded NEGATIVE; do not build it.** Two reasons
stand: (a) the row would compare a state driven by a synthetic poke rather than a live rule, and
(b) a poke-box + watch static pair in src/field.rs is a bespoke test-only input channel with no
precedent in src/, and the one-sided negative is a new negative KIND in tools/harness.py — both
larger than the ticket budgeted; the writer that makes the row meaningful is on the battle/object
side the ticket's Files exclude. My original premise report ("Type never leaves 2; the live writer
ORs 0x104 bypassing the setter") was a word-level decode error — the byte dump above corrects it:
the live writer IS T115's cited writer and Type DOES move. That correction does not resurrect the
row: reason (b) is independent of it.

**What was measured about the port before reverting it** (one build, no captures): the full
field.rs port (flags array + table decode from the asset + setter rules + poke box) built clean
and produced ROM 592016 B vs main's 592752 — .text SHRANK 824 B and .rodata grew 88 B (the 52-byte
asset + alignment) under fat LTO: an additive change with a NEGATIVE footprint delta. T116's
lesson (size delta moves the seam) applies with a sign flip worth remembering: code size response
to added source is not monotonic. The port is reverted; the landed tree does not include the asset
in src, so the shipped ROM is byte-identical to main.
