Bit-name derivation: each of 0x40/0x100/0x2000/0x400/0x800/0x1000/0x4000/0x8000 is set by exactly one
type's word → named after that type (derived from the ROM bytes). 0x10 is set by every type except
hole/broken; 0x10000 by ALL 13 — both keep `unnamed:` status. 0x200 marks exactly the 9..0xC group the
setter gives `Unk_12=0x708` (asm38.s:4318-4326).

Cross-check against T115's writer table (the 9 types with writers): each writer type's word carries
exactly its own new bit on top of the 0x10|0x10000 base — 1 broken 0x4000, 2 normal (base only),
3 cracked 0x40, 4 poison 0x100, 6 grass 0x400, 7 ice 0x800, 8 0x1000, 0xB/0xC 0x200. Consistency
check that fell out free: `object_crackPanel`'s flag-mask rewrite `Flags=(Flags&~0x3f0f)+3`
(object.s:2215-2218) clears bits 0-3 and 8-13 — i.e. exactly the per-type low bits — and ORs
cracked's 0x40; normal (0x10010) has no bits inside the 0x3f0f mask, so crack = OR 0x40 → 0x10050
= the type-3 word exactly. The table and the crack family agree byte for byte.

## Row design decided (recorded BEFORE any capture so the choices are reviewable)

- The poke cannot be delivered to our side by any existing input channel: the fixture descriptor
  (FIXTURE.md) has no panel-type field and its +62/+63 bytes are already contested overlays;
  src/fixture.rs and src/battle.rs are out of this ticket's scope; `BATTLE_MARKER`'s own padding is
  write-only from the ROM's perspective by main.rs's documented contract ("nothing in this crate ever
  reads the region back"), so reading a mailbox out of it from field.rs would silently break that
  contract's premise.
- Therefore the ONE-SIDED-poke negative is the only non-blind reading of "negative = the same scenario
  without the poke": negative = rust poked vs canon NOT poked. If our side's poison rendering were
  fake/absent, that negative reads 0 (both normal) — blind. It is the F-property for this row.
- Canon-side poke mechanics verified in the assembly first (no capture spent on a guess):
  the per-panel tile layout is rebuilt from `Type` outside the setter — sub_800C5E0 walks
  ePanelData and calls `buildPanelTileLayout_800C01C` with `[r7+2]` (Type) per panel
  (object.s:1709-1746), so a mid-battle Type poke re-renders the tile; and `_object_updatePanelParameters`
  has NO per-frame caller (callers: asm38.s:3736/3760/4044/4075/4197/4329, object.s:1475 regen only),
  so the FLAGS word must be poked directly alongside the Type byte (0x00010110 = two halfword pokes).
  Poke target: panel array index 0 = panel (1,1) (panel_800BFC4's walk: +0x20 per column, +2 skipped
  per row — row stride 8, col-major from (1,1); object.s:1042-1066), EMPTY so no navi stands on it and
  the M3 poison-damage rule (a future ticket's deliverable) cannot fire.
- Rust side: a poke-visible setter in src/field.rs — a `PANEL_POKE_BOX` static (the ticket's "the
  setter's rules that a measurement can see (type 0 refused)"), consumed by `Panels::update`
  (battle.rs already calls `panels.update(occupied)` every frame at :4275 — no battle.rs edit), plus a
  `PANEL_FLAGS_WATCH` u32 static written every update for the rust-side --watch. Addresses read from
  the built ELF with `nm` at row-build time (not hardcoded — boot length moves with code size).
