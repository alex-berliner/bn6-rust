## Step 2 — IMMOBILIZED bit mask derivation (measurement)

Two distinct asm sites cited in the ticket text. Verified by
direct reading of `reference/bn6f/asm/asm31.s` and
`reference/bn6f/asm/asm00_2.s`:

1. **The reader site (asm31.s:171386-171390)** -- the Mettaur
   decision loop's IMMOBILIZED gate. From the disassembly:

   ```
   loc_810A038:                        ; 171385
       bl object_getFlag ; () -> int   ; 171386
       mov r1, #1                      ; 171387
       lsl r1, r1, #0xe                ; 171388  <- bit 14 = 0x4000
       tst r0, r1                      ; 171389
       bne locret_810A078              ; 171390  <- return (skip confused/wander arm)
   ```

   `object_getFlag` (asm00_2.s:21621-21626) reads
   `oCollisionData_ObjectFlags1` at `oBattleObject_CollisionDataPtr+0x3c`
   (CollisionData.inc:145). Mask 0x4000 in flags1 = bit 14 =
   `OBJECT_FLAGS_IMMOBILIZED` (CollisionData.inc:17). **Bit mask = 0x4000.**

2. **The setter site (asm00_2.s:23893-23908)** -- cited in the ticket
   text as the source for `lsl r1, r1, #0x14`. This site is `loc_801B2D6`,
   the if-endif in a different routine's flag cascade. The
   disassembly comment `// OBJECT_FLAGS_IMMOBILIZED` here is **WRONG**
   -- `lsl r1, r1, #0x14` = bit 20 = mask 0x100000, which is
   `OBJECT_FLAGS_DRAG` (CollisionData.inc:22), not IMMOBILIZED.
   The disassembly's `enum32 OBJECT_FLAGS_*` reuses names; the
   offset (0x14) does not match the IMMOBILIZED mask (0xe). T18's
   audit (worklog, 2026-09-15) treats it as the bit-20 flag (DRAG).

   **The ticket's "0x10 in a u8 / flag2 stride" claim does not match
   either reader or setter:** the reader (asm31.s:171386-171390) reads
   flags1 (NOT flags2) and uses bit 14 (NOT bit 20). There is NO
   `flag2 at +0x4 ⇒ mask 0x10 in a u8` involved -- flags2 lives at
   `oCollisionData_ObjectFlags2 = +0x40` (CollisionData.inc:148) and
   shares no layout with flags1.

   **The bit mask IS 0x4000 (32-bit), bit 14.**

3. **Behaviour of the gate.** If `flags1[14] != 0`, the routine
   `bne`s to `locret_810A078` -- a plain return -- skipping the
   BLIND|CONFUSED check (`tst r0, #0xa000`) and the row compare.
   The Mettaur therefore spends every frame inside the decision
   loop with no state transition: no RowCheck, no confused-wander
   arming, no hop, no attack. This is what "immobilized" means at
   the AI level: a freeze in place.

## Step 3 — the additive arm's scope

The ticket's "Files" list allows `src/objects.rs` only, and explicitly
forbids `src/fixture.rs`. The arm is ADDITIVE ONLY -- it must not
re-edit the existing T6/T9j `MettaurEntry`/`Style::Mettaur` arms.

A direct port of the asm gate needs:
- A way to access the enemy's CollisionData flags1 word
- A way for the rust side to know the bit is set

The existing `BLIND_OR_CONFUSED` constant at src/objects.rs:380 is
the project's pattern for a `false` const that mirrors a future
runtime flag. The simplest additive change that captures the asm
cite and the bit mask in source is:
- A new const `OBJECT_FLAGS_IMMOBILIZED: u32 = 0x00004000` (or
  similar) tagged with the proven provenance.
- A comment near the existing `BLIND_OR_CONFUSED` const naming the
  equivalent immobilized check.

Without a fixture field, the rust side cannot receive the
"immobilized is set" signal, so the rust Mettaur will continue its
normal decision loop while canon's Mettaur freezes. The comparison
will be maximal (the rust side attacks, the canon side stands still).
This is the "NEGATIVE on scope conflict" -- the row's acceptance
("immobilized 0/0/N non-blind") requires the rust side to also be
frozen, which requires `Fixture` to carry the signal.

## Step 4 — additive code change (landed)

Added to src/objects.rs:
- `const OBJECT_FLAGS_IMMOBILIZED: u32 = 0x00004000` with a provenance
  tag pointing at CollisionData.inc:17 and asm31.s:171386-171390.
- A new doc comment near `BLIND_OR_CONFUSED` naming the equivalent
  bit-test the asm gate does and its freeze-in-place behaviour.

The const compiles cleanly. It does not change any behaviour (the
existing `BLIND_OR_CONFUSED` const is `false`; the immobilized const
is informational and unused for now -- a future ticket that adds the
fixture field will flip it live via a setter at src/fixture.rs).

ROM sha256 before/after: 0d3ea6d3... == 0d3ea6d3... (the const is
linker-dropped because no code reads it; the asm cite lives in
source comments).

## Step 5 — harness row (NOT LANDED)

The harness row needs to:
- Boot a state where canon's Mettaur is pre-immobilized
  (a one-time `--poke 0x0203abf0:0x4000` -- `oCollisionData_ObjectFlags1`
  at the Mettaur slot's BattleObject base +0x54 +0x3c = 0x0203abf0).
- Compare against a rust side that is also immobilized.

The second bullet is unreachable from this scope: the rust build
stores its actor struct in the heap, not at EWRAM 0x0203ab60, so a
per-frame `--cheat 0x0203abf0:0x4000` writes to EWRAM but no rust
code reads it. The only rust-side signal mechanism this project has is
`Fixture::enemy_state/enemy_action` (offsets +62/+63), which requires
`src/fixture.rs` edits.

Adding the row with only the canon-side poke would produce a row that
DIFFS every frame (rust attacks, canon stands still) -- a 100%
mismatch, not "0/0/N non-blind". NEGATIVE per the ticket's own
NEGATIVE exit, with the follow-up shape named below.

## Dropped ideas

* "Add `Fixture::enemy_immobilized` and read it in src/objects.rs"
  -- drop. The ticket's "Files" list excludes `src/fixture.rs`; doing
  this widens scope.
* "Read the IMMOBILIZED bit from canon's EWRAM via raw pointer in
  src/objects.rs" -- drop. The rust build has no actor mirror at
  EWRAM 0x0203ab60; the read would always return 0 on the rust side.
* "Use the existing `enemy_state` field (offset +62) as the signal"
  -- drop. `enemy_state` carries `CurState` (BattleObject+0x08), not
  the flags word; reusing it as a signal breaks the cursor/windowclose
  rows that already use it (F38h's bytes-overlay is fragile).
* "Set the rust side to a const `true` and skip the row" -- drop.
  The ticket explicitly forbids fitted-true for the gate (per T83's
  NEGATIVE's own "Rules" clause).

## What would unblock T84 (the follow-up)

A two-ticket split (same shape as T83's recommendation):

* **T84a**: Add `Fixture::enemy_flags1: u32` (or similar) at a
  reserved-region offset (e.g. +64..+67, not currently used). The
  fixture reader in src/fixture.rs exposes it; src/battle.rs's
  enemy-spawn path ORs it into the actor's flags mirror. The harness
  `--cheat` for this row pokes 0x4000 into that fixture byte every
  frame. (src/fixture.rs + src/battle.rs touched.)
* **T84b**: With T84a landed, the additive check at src/objects.rs
  can be wired to read the per-actor flag mirror; the harness row
  passes 0/0/N non-blind.

T84a is a small ticket (~30 calls, a fixture field + a one-line
spawn-side OR), the additive const landed here is its ready-made
gating half.
