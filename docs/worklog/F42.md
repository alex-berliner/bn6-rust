### CORRECTION -- the containment claim below is REFUTED (verifier-hyper, run 20260915-103014; read this before citing the table)

Two of this section's own numbers were re-derived independently and hold: integrated
158935/5606/40 with negative 261034, and BG1-only-at-the-row's-offset 1370701 (the
heading's `s=116` is a mislabel -- every figure here reproduces at **108**). What does NOT
hold is the inference drawn from them, for two reasons:

1. **The containment was guaranteed, not found.** The BG1-only mask used for
   `integrated ∩ BG1-only = 158935` is **100% saturated -- all 38400 px differing -- on 34
   of the 40 frames**, and those 34 frames carry **139125 of the row's 158935 px (87.5%)**.
   On a saturated frame `integrated ∩ BG1 = integrated` is true by construction for *any*
   set whatever, so it discriminates nothing; ditto `integrated & ~BG1 & BG3 == 0`, which
   is empty because `~BG1` is empty there, not because BG3 was exonerated. The test carries
   information only on k=0..5 -- **19810 px, 12.5% of the row**.
2. **`--only-bg N` is not a same-layer comparison on this row past k=4**, which the repo
   already documents at tools/harness.py:1362-1370: from capture 121 `self.shown` is
   `Some`, `battle.rs` skips `filler_bg` and every layer drops one hardware BG (BG0
   backdrop, BG1 panels, BG2 HP box, BG3 RESULT window), so "`--only-bg N` is a
   same-content comparison on this row only for k=0..4". Capture 121 is k=5 on this row's
   pairing, and the verifier's per-frame BG1 density jumps 29.0% (k=3,4) -> 92.5% (k=5) ->
   100.0% (k=6..39) right across that boundary. For 35 of 40 frames `--only-bg 1` compared
   *different hardware planes*, so its 1370701 is partly an artefact of that.

So do NOT carry "BG1 owns all 158935 px / BG2 contributes 0" forward: the layer attribution
survives only over k=0..5, and **BG2's share has never been measured at all** -- and cannot
be from the command line, because `--only-bg` is a per-`Side` `extra=` passthrough
(tools/harness.py:292-293), not a CLI flag (argparse at :3211-3214 accepts only
`--only/--list/--no-gallery/--ui`); a BG2 split for this fixture needs a new row.
What still stands from this ticket: the premise number is wrong (158935, not 1589), the
entry cannot be deleted, and -- the part that distinguishes F42 from F41 -- this row is
genuinely NOT a never-resolves case (FIELD_ZERO inherits `flags=0x31` at

## Step 4 — the mechanism, with the cite (no port attempted; see budget)

The canon writer of these pixels is the backdrop art system, already cited in
src/backdrop.rs's module doc: the art is the GFXAnim engine — `LoadGFXAnim`/
`ProcessGFXAnims` (reference/bn6f/asm/asm00_0.s:3510-3697), per-slot `Timer` in
`eGFXAnimStates` (0x020094c0), tile copy `sub_8001C94`, loaded at battle init from
`sub_8080DA0` (reference/bn6f/asm/asm00_1.s:8434-8435, asm21.s:33/37); the scroll is
`BGScrollCB_BG1Diagonal3to2Scroll` off `eBGScrollCBCounters`. Our port is
src/backdrop.rs (STEP_ORDER/STEP_HOLD schedule model + T9e's `backdrop_seed_table`).

The port is already in the tree and the row still reads 158935, so what diverges is
INSIDE the ported mechanism: the animated tile ART content (glyphs) shown during the
window, not the scroll (shift test) and not the map/palette (module doc: those never
move). The visible part is only BG1's margin around the arena (the arena covers BG1
elsewhere) — which is why the row reads ~4-5.6k/frame while the BG1-only split reads
~21-34k/frame at the same offsets.

## Why this is a NEGATIVE (the landing condition is unreachable)

1. The defect is 158935 px, not 1589 — the premise number does not exist.
2. Every pixel is BG1 art content. T9e's seed lever (the ticket's named cheap port)
   was already applied to this row (BG1-only 660992 → 645888 on 2026-09-14, ~15k of
   660k) and rewrites only the three 0xE0000000 seed columns; it cannot close a
   full-window art-content divergence. The shift test rules out any alignment/scroll
   fix, and no offset in s=0..149 aligns it away.
3. Reaching 0 needs the GFXAnim step/content divergence itself found and fixed (which
   step of the schedule shows wrong glyphs, and when) — a new investigation in
   src/backdrop.rs's schedule model, not a seed tweak. FIELD_ZERO's seeds
   (art_entry=10, art_timer=7, tools/harness.py:1564) are outside this ticket's file
   list anyway.
4. The never-resolves gate that F41 named for chip-use does NOT apply here:
   FIELD_ZERO inherits flags=0x31 (RESOLVE_OVER, tools/harness.py:1489), both sides
   resolve on schedule, and the window itself compares clean (k=0..1 = 0).
5. Capture budget: 10/10 mgba_capture runs spent (baseline 4, integrated-kept 2,
   BG3-only 2, BG1-only 2). Any fix + re-measure needs 2-4 more and was not spent on
   an unfixable number. All post-baseline analysis ran free on the kept capture dirs.
