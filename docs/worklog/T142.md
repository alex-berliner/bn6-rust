  is rust 8+113 = **121** .. 160 vs canon 135..174. Event-locked, matches.
- BG0CNT (0x04000008, u16 LE, end-of-frame snapshot):
  - frame 0..7: `0x0000` (screenblock 0, prio 0)

  The flip is EXACTLY at frame 121 = the row's boundary capture.
- DISPLAY_CONTROL (0x04000000): `0x0080` frames 0..7, `0x1f40` frames 8..192 —
  **does not change at the flip**. Only BG0CNT (and, unwatched, the other CNTs)
  change.

### Verdict: **S1**

The map at the post-flip address was final long before the flip; the pre-flip
map (screenblock 17) is all zeros and renders black. Rows 0..14 of frame 121
show screenblock-17-black, rows 15..159 show the screenblock-19 backdrop:
the **BG0CNT store landed mid-scan, between scanlines 14 and 15**. A map-copy
spill (S2) cannot produce this: there were no new map bytes to copy on that
frame at all, and the map bytes at both addresses were stable for 100+ frames.

Mechanism shape (source, recon-confirmed): `commit()` waits for vblank
(interrupt.rs:417-427 early-returns when this frame's vblank already passed),
then stores DISPLAY_CONTROL, per-BG CNT/HOFS/VOFS, then map copies. On the
renumber frame the main loop's work before `commit()` overshoots vblank by ~15
scanlines, so the CNT store lands mid-visible. mGBA composites scanline-wise,
so the top of the frame renders with the stale CNT (blank screenblock 17).

## Verdict (bounded NEGATIVE, with the mechanism named)

- Step 1 DECIDED: **S1**. The renumber frame's BG0CNT store lands mid-scan,
  between scanlines 14 and 15. Evidence (bytes, /tmp/t142_map.bin +
