## Step 4/5 — the port is BLOCKED; this ticket closes NEGATIVE

Canon vs rust mm timeline over the compared window (rust trace = capture 3, its
table.json holds DECIMALS: rust's (4,11) is 0x0b, not 0x11):

- canon: idle (4,8,anim 0,Timer 0) -> chip use (4,0x14,anim 8) k=250..268 ->
  flinch (4,0x03,anim 1,Timer 22..0) k=269..291 -> idle with Timer=0xFFFF
  k=292..539 (the sentinel is NEVER rewritten — no watch store after canon 303).
- rust: idle (4,8,0,0) to k=351 -> (4,0x0b,anim 8) k=352..384 -> idle to k=532 ->
  (4,0x0b,anim 8) k=533..539. HP stays 60 and mercy stays 120 through k=539 —
  rust's player is NEVER hit; rust's 0x0b episode is its cannon chip fired by the
  fixture's AUTO-FIRE (fire_frame=180 seeds auto_ticks, counted down from the
  fight's opening ~k=172 -> 352), not by any scripted press (rust script = "A@170",
  which only closes the custom window).

Model gaps that block the arm, per gap:

1. **Fire-event timing.** Canon's chip fires at k=250 (scripted A@260 ->
   useChipFromHand_800FB54). Rust's chip fires at k=352 (fixture auto-fire).
   Porting the 0x14 encoding onto rust's chip action (currently Action::Attacking
   -> exported 0x0b) cannot move mm_state_action's first divergence past k=250:
   canon reads 0x14 at k=250 while rust still reads 0x08, because the FIRE EVENT
   itself is 102 frames apart, and the fire time is pinned by the fixture's
   fire_frame=180 — the ticket's rules forbid row/fixture changes. (Also for
   nothing: at k=352..384 canon reads 0x08, so a 0x0b->0x14 swap there keeps every
   one of those frames divergent.)
2. **The hit.** Canon's k=269 flinch (action 0x03, anim 1, Timer 0x17 -> 0 ->
   0xFFFF) needs the Mettaur's wave to hit the player. In rust's capture the
   player is never hit (enemy group diverges from k=17, 458/540 — a different
   ticket's objective), so the ALREADY-PORTED flinch model
   (Action::Flinching + take_damage + the Timer export with the fitted
   post_flinch shadow, src/actor.rs:728-739) never fires. mm_timer's 270-count
   divergence cannot drop by any player-side change.
3. **The 0xFFFF tail contradicts the fitted shadow.** Canon holds Timer=0xFFFF
   from k=292 to k=539 (248 frames, no rewrite). src/actor.rs's post_flinch
   shadow exports 0xffff then 9..0 then 0 (fitted off the PAUSED+Start@10
   capture, "measured 137..147"). The two captures disagree; the battle_full
   trace says the sentinel persists until the next Timer-writing event. Whoever
   ports the hit next should re-derive the shadow from battle_full, not the
   older capture.

Given 1+2, no player-side port within this ticket's allowed files can move
mm_state_action's first divergence past k=250, drop mm_timer below 270, or move
the 1370 total — so per the acceptance's negative clause I made **no src change**:
the writers are all named above with frames/PCs/LRs, and the blocking gaps are
the fixture-pinned fire event and the never-hit player.
