### The NEGATIVE (why the extension does not land)

No id is unsafe: all 237 records export cleanly and the ticket's own row class (43 chip rows
+ chip-use, 170-frame cursor class included) is byte-identical to baseline with the bigger
asset. What fails is the footprint coupling: the +161832-byte static (`src/main.rs`
`include_bytes!`) shifts ROM layout, and two rows are layout-pinned —
- `cursor`'s tear (T111's knob, sanctioned to move), and
- `windowclose`, whose alignment band (`canon_ref=81`, search 248..259) was MEASURED on the
  old layout ("offset 253 ... the event, not the score, picks 253", tools/harness.py:2824's
  note): its rust side boots from power-on, so the +162 KB moved the slide-out events out of
  the band and the search can no longer find the true minimum. Re-centering the band would
  fix the row — and that is exactly the "chasing the tear" ticket step 5 forbids.
Per step 5 the asset change is left unmerged: the branch tip carries the 48-record asset;
the exporter regenerates the 237-record set on demand (command at the top). The follow-up
that wants the bigger asset landed needs a footprint story first (e.g. a layout-stable
placement for the asset blob, or re-measuring windowclose's band in the same landing as a
ticketed change, not a silent one).
