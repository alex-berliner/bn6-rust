## Step 4 — localization of t54's 6 moved pixels

Captures kept by calling `harness.run()` directly (run_check deletes dirs). Composite diff over
all 170 compared pairs: **only k=97** (canon 112 <-> rust 342) differs, 6 px:
(119,6), (120,5), (120,6), (121,5), (121,6), (183,5). diffmask on re-indexed paired dirs
(canon 15+k <-> rust 245+k, k=95..99): 0/38400 everywhere except k=97 6/38400.

- diffmask run exactly as the ticket wrote it (`--frames 165..169` on the raw dirs) compares
  SAME-INDEX frames, and this row pairs canon 15+k <-> rust 245+k, so that command as written
  compares unpaired game frames; its output is meaningless for this row and is not quoted as a
  result. The paired re-run above is the real mask.
- OAM watch both sides (`--watch 0x07000000:1024`, canon 112 vs rust 342): **no OBJ entry's
  bounding box covers any of the 6 pixels on either side.** (Sanity check: canon entry 7 reads
  (156,147) 32x16 = F37's o07 HP box, so the frame indexing is right.)
- `--disable-obj` on BOTH sides, full 170-frame diff: **identical 6 px at k=97, total 6** — the
  pixels are BG, not OBJ.
- BG1 layer-local (`--only-bg 1 --disable-obj` both sides): 18 px, ALL at k=97:
  (55,5), (119..124, 5..9 cluster), (183,5). See docs/coverage/cursor.md for the pattern.

Mechanism: this is F37h's documented BG1 sub-frame tile-copy seam, measured at t54's own code
size. HEAD's BG1-only k=97 seam is the landed 2 px (x55 + x183, the map's x+128 repeat); t54's
900-B-smaller ROM shifts the queued GFX transfer's drain position so the seam ALSO catches the
tile column at x119..124 on rows y5..9, and 6 of the 18 layer-local px survive occlusion into
the composite (x55 is behind the BG3 chip window; the rest of the 18 are OBJ-covered or
window-covered). Nothing at k=165..169 moves — T54's "5 px at k=170" was the frame COUNT, not a
moved frame.

## Verdict

**(b), with a correction.** All three trees pick the same offset 237 and the pad moves nothing
(cursor is NOT a pairing/size artifact in the searched-offset sense), and only t54 moves — so
precondition (b) holds — but the moved pixels are **NOT an OBJ entry**: they are BG1's
sub-frame tile-copy drain seam (F35/F37h's mechanism), whose visible extent is code-size
dependent (1 px composite on 584296 B, 6 px on 583396 B, offset identical). Combined with T51
(the cursor deck holds no vulcan id, so use_chip/chip_strike cannot fire), `cursor`'s veto is
**not a logic quantity**: no byte of T54's chip data is read by anything cursor compares. It
also did NOT move for the pure +256 B pad, so the dependence is on total code size/timing
placement, not on any particular byte.

## What is unverified

- HEAD's BG1-only k=97 seam is cited from the landed align note and F37h's coverage doc
  (2 px: x55+x183), not re-measured on this ticket's HEAD captures — the composite 1/1 and the
  OAM parse (no OBJ covers x119..124 on either side) make the t54-only x119..124 group sound,
  but a HEAD BG1-only capture on THIS session's inputs would make it airtight.
- `verify_rows` on wt/t54 (cursor + 4 Vulcan rows) was NOT run: the coordinator's free tier says
  none needed to land, capture budget was spent on the localization, and the harness numbers
  above are this ticket's own measurement.
- The drain-scanline mechanism is inferred from the seam's shape and its code-size dependence;
  no per-scanline trace was taken.
