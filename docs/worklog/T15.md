## Statuses (M3) — verdict: no bit-indexed table exists (kept DERIVED-FROM-HEADERS, new trail)

Walked: `object_setCollisionStatusEffect1/2` (asm/asm00_2.s:21768/21776) just store the status
byte into `oCollisionData_StatusEffectBase/Final`. Consumer `sub_801A554`
(asm/asm00_2.s:22211–22230, plus 22251/22275 siblings) indexes the nearest per-status DATA table:
`off_80209EC` (**data/dat01.s:155**), **6 pointer words, pointer stride 4**, index =
`(StatusEffectFinal >> 4) - 1`; each pointer targets **records of stride 8** — [0] flag2 mask
word, [4] hword value, [6] CollisionData byte offset — 6–7 records per family
(byte_8020A04, off_8020A34, byte_8020A64, off_8020A94, byte_8020ACC, byte_8020AFC).
That table enumerates **6 status-effect families × timing variants**, not the 69 flag bits.
The 69 bits (OBJECT_FLAGS_*, OBJECT_FLAGS_2_*, DAMAGE_*) are set/cleared directly by code
(object_setFlag/object_setFlag2, strh to Damage) with no per-bit indirection. Mismatch vs 69
quantified: 6 families ≠ 69 bits; the bit rows stay header-derived.

## NaviCust (M7) — verdict: FOUND, navicust_jt_NCPs

Give/Take chain read end to end:
`GiveNaviCustPrograms`/`TakeNaviCustPrograms` (asm/asm03_1_1.s:8794/8814) →
`GiveItem` 803cd98 (`KeyItemsPtr[program_id]` — a plain byte array indexed directly by program
id, **no stride, no per-program table here**) → for id 0x71 only,
`reloadCurNaviStatBoosts_813c3ac` (asm/asm37_0.s:1719) → `applyNaviStatsMaybe_813C458`
(asm/asm37_0.s:1796) → **`applyNavicustPrograms_813C684` (asm/asm37_0.s:2012)**, which iterates
the 8 equipped-program slots (byte_2006DD8) and dispatches through
**`navicust_jt_NCPs` (asm/asm37_0.s:2111): 47 .word entries (lines 2112–2158), stride 4**, reached
through the stat-boost reload chain: dispatch keys off `sub_813B9FC(id-1)`, which is **not a lookup**
but `r10[oToolkit_Unk2004190_Ptr] + 8*id` — an **8-byte-stride record array** — and the jump index is
that record's halfword `>> 2` (low 2 bits masked off).

Count and label (corrected by verifier-hyper): **47 entries = 45 `navicust_NCP_*` +
`navicust_GigFldr1` + entry 0 = `sub_813C808`, a `push {lr}; pop {pc}` no-op stub.** The bodies
(asm/asm37_0.s:2161–2600) contain 32 `bl SetCurPETNaviStatsByte` + 11 `bl GetCurPETNaviStatsByte`
(e.g. `navicust_NCP_SuperArmor` → `SetCurPETNaviStatsByte(0, 0x23, 1)`), so the table is a
**47-entry NCP battle-effect handler table**, NOT a program-id enumeration: because `sub_813B9FC`
is a record-array add and the low 2 halfword bits are masked off, several programs can share an
entry, and entry order is a program-list order, not an id space. It is adjacent to — but not — the
enumeration behind the line's 19 NaviStats slots; the SCOPE line may claim it for the handler table
only. The slots quantified stay: 19 = the named **NaviStats slots** those handlers write (a
different axis). Encoded as FOUND with the slots kept DERIVED-FROM-HEADERS.

## Backdrops (M8) — verdict: mapping GAP, byte values DERIVED-FROM-RECORDS (kept)

Distinct `BattleSettings.Background` bytes across 461 records: **0x07 × 192, 0x08 × 1**,
0xff sentinel × 268 → 2 set values + sentinel = 3.
Walked: writer `battleSettings_setBackground` (asm/asm03_0.s:14592–14595, stores at
BattleSettings_200AF60+0x4); `battleSettings_802D2B2` (asm/asm03_0.s:14599–14618) sources the
byte from `byte_203CA50` stage-pair rows `[2*(stage-1)+1]`; `CopyBackgroundTiles`

with signature (j, i, tileBlock32x32, tile_ids *const u16, j_size, i_size) — tile ids arrive in r3
from the caller) takes tile ids from its caller, not from the byte. **No byte→art/palette
table and no arithmetic offset located** within budget — GAP for the mapping, trail written
into the section note. Verifier-hyper's extra search closes the trail (recorded in the section
note): a repo-wide grep for readers of `BattleSettings+0x4` finds **NONE in asm/** beyond the
store at asm03_0.s:14594; `battleSettings_setBackground` has exactly two callers
(asm03_0.s:14617, asm33.s:16529); and `CopyBackgroundTiles`' call sites pick per-scene tile

`sub #0x82`/`#0x70`/`#0x5e` dispatching to byte_812489C/81248C0/81248E4/812492C). So the
byte→art mapping is a **per-scene compare chain over four tile arrays, not a table** — that is
the trail's endpoint, still a GAP for a table.
