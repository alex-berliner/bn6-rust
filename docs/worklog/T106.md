## What canon does (measured)

Recon on the real ROM, afterdissolve_0x0c state, sterile build:

* The dispatch table is `ChargeShotHandlersByTransformation_80117D4`
  (asm/asm00_2.s:5809-5963, 0x94 `.word` cells, indexed by `oAIData_BPwrAtk`,
  AIData.inc loc=0x7). The ticket's "8 entries 0x06..0x0D" are cells of this
  table: 0x06 = `sub_8011BA2` (Cannon), 0x07 = `greatfireAPwrAtk_init_8011BD0`,
  0x08 = `sub_8011BE8`, 0x09 = `sub_8011C00`, 0x0a = `sub_8011C18`,
  0x0b = `sub_8011C38`, 0x0c = `spoutcrossBPwrAtk_init_8011C5E`,
  0x0d = `nullsub_44`. The ticket's `sub_8011818` / `sub_80118A4` citations do
  not exist as symbols: per bn6f.map both addresses land INSIDE the table
  (0x8011818 = cell 0x11, 0x80118A4 = cell 0x34). The "per-shot arm" the
  ticket describes is the indexing code in `sub_80117BA` (asm00_2.s:5795) plus
  the call site in the player's t1 leg (asm31.s:119118, right before
  `object_setAttack1`).
* `off_81333B0` is not in bn6f either (bn6f.map: inside `sub_8133200`); the
  stride-0x10 hold-pose palette table is `// unnamed: hold-pose palette table`.
  Not cited further — the port's palette facts came from pixels, not that table.
* Hold timer: `oAIData_PwrAtkCurChargeTime` (AIData.inc loc=0x1b; player
  AIData at 0x02034080 in this state → 0x0203409b), counted up per frame by
  `sub_8012EBC` (asm00_2.s:9110-9141), capped at the buster's charge time
  (DeterminePowerAttackChargeTime, asm00_2.s:9156). WATCHED: with the button
  held by a per-frame AIData cheat from the state's frame 0, the counter reads
  1 at frame 0 and caps at **100** from frame 99. `oAIData_PwrAtkState`
  (0x0203409d) stays 0 the whole time in this scene (the Unk_44-flag gate at
  asm00_2.s:9092), so canon's charge-glow object (anim = PwrAtkState,
  chargeShotChargeObject_update_80E0E20, asm31.s:86443) is INVISIBLE here.
* Release: a released-word poke (0x020340a6) at frame 130 → **on that same
  frame** CurAction 0x0203a9b9 is written 0x10 (charged attack, 130..159,
  back to 0x08 at 160). The plain buster tap writes 0x11 (132..159).
* Shot kind: a one-shot poke of `oAIData_BPwrAtk` (0x02034087 = 0x06) on frame
  129, the frame before the release, makes the dispatch walk cell 0x06.
  Cell 0x01 (the state's own value at load, peeked) vs cell 0x06: over 170
  frames the two canon captures differ in **0 pixels** (damage differs,
  42 vs 20, but the arena has no enemy). NOTE: that comparison was run with
  `--only-bg 0` which hides sprites — treat it as unproven for visuals; the
  row itself measures cell 0x06 directly.

## The row

`128:pressed` `129:BPwrAtk=6` `130:released` pokes; rust = CHIPUSE_ZERO
fixture (the afterdissolve route's own pairing) + `flags 0x31` +
script `held(B, 108, 105)`; align canon_ref 130, search range(198,212), 32
frames; negative = TAP (not blind).

* The ticket's "HOLD-A" is really the buster button B (JOYPAD_B, asm00_2.s:9332;
  the existing buster row taps B). A scripted hold cannot reach AIData in the
  0x0C sequencer (F31b's wall) — hence the cheat/poke delivery.
* The ticket's "hold_A >= 24 frames arms the dispatch" did NOT match
  measurement: canon caps the counter at 100 and only a full charge produces
  the charged attack. Our arm uses the standing CHARGE_FRAMES (101).

  buster_damage)` -- the NORMAL cell (0x01, damage = buster*10, the standing
  CHARGED_DAMAGE path) and the ported Cannon cell (0x06), verbatim from
  `sub_8011BA2` (asm00_2.s:6173-6192): damage = buster + 0x14*min(buster,5)

  The Strike branch was wired through the dispatch with the default cell
