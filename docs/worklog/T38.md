## Step 2: parity table -- record vs src literal (re-confirmed)

Read both the v2 asset's three Cannon-family records and the real ROM
bytes at `ChipDataArr_8021DA8` (file offset 0x00021DA8 in the 8MB
cart image -- GBA ROM maps 0x08000000..0x09FFFFFF 1:1):

```
$ python3 -c "import struct; f=open('/tmp/bn6f_real.gba','rb').read();
  for i in (1,2,3):
    r=f[0x00021DA8+i*0x2c:][:0x2c]
    print(i, 'elem', hex(r[0x6]), 'fam', hex(r[0xb]),
    'subfam', hex(r[0xc]), 'power',
    struct.unpack_from('<H',r,0x1a)[0])"

```

Cross-checked against `reference/bn6f/data/ChipDataArr.s:33-126`:

| chip id | name     | record (chip_data_struct)                    | src literal                       | matches |
|---------|----------|----------------------------------------------|-----------------------------------|---------|
| 1       | Cannon   | elem=0x0A  fam=0x14  sub=0x00  power=0x0028  | `chip.power` (data-driven) + default elem | YES |
| 2       | HiCannon | elem=0x0A  fam=0x14  sub=0x01  power=0x0064  | `chip.power` (data-driven) + default elem | YES |
| 3       | M-Cannon | elem=0x0A  fam=0x14  sub=0x02  power=0x00B4  | `chip.power` (data-driven) + default elem | YES |

**Zero unexplained mismatches.** The record's `AttackPower` matches the
src's record-driven `chip.power` for all three; the record's `Element`
matches the src's "no special element handling" (`CHIP_ELEM_NONE` for
all three -- the cannon shot is untyped in both our build and the real
ROM).

The only ID-keyed lookup that survives in the Cannon arm is the
**barrel palette** at src/battle.rs:4206:
`barrel.set_palette_add((chip.id - CHIP_CANNON) as usize)` which
equals `byte_80EBD2C[chip.subfamily]` for every record (asm31.s:109657,
rows 0/1/2 are the per-subfamily palette for the cannon barrel). The
record's `attack_subfamily` is 0/1/2 for Cannon/HiCannon/M-Cannon, so
the palette reads the same row either way. The family-0x14 dispatch
replaces the chip-id index in one stroke.
