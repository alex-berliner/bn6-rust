## Where T34's hypothesis holds and where it fails

- **Recov: subfamily IS the right key.** Recov10..Recov300 carry sub=0..7 and the table reads sub 0..7 -> HP 10..300. A `chips::recover_heal(chip.subfamily) -> u16` indexed at subfamily would return the same 10/30/50/80/120/150/200/300 the current `RECOV_HP[(chip.id - CHIP_RECOV10) as usize]` returns. Gate passes.
- **Vulcan: subfamily IS the right key.** Vulcan1/2/3/SuprVulc carry sub=0..3 and the word reads sub 0..3 -> 3/4/5/10 shots. A `chips::vulcan_shots(chip.subfamily) -> u8` would return the same 3/4/5/10 the current `match id { ... }` returns. Gate passes.
- **Barrier: subfamily is NOT the right key.** Barrier/Barr100/Barr200 all carry **sub=4** (chip_data_struct offset +0xc) — the family-0x15 subfamily-4 entry off_802CCB4[4] (asm03_0.s:13716) is the shared handler. The asm code distinguishes the three chips by `attack_param_1` (chip_data_struct offset +0x10, exported as `params[0]` in the v2 tail), not by subfamily. The current comment at src/battle.rs:655-659 says exactly this: *"Barrier, Barr100 and Barr200 are one chip with one handler: family 0x15 subfamily 4 (off_802CCB4[4] = sub_80E3B50), whose first attack parameter indexes byte_8020B2C (data/dat01.s:189) for the bubble's HP. Barrier's parameter is 1 -> row 1 = 10, Barr100's is 5 -> 0x64, Barr200's is 7 -> 0xc8."* A `chips::barrier_hp(chip.subfamily) -> u16` indexed at sub=4 would return 0x0050 = 80 HP for **all three** chips — Barrier would lose its 10 HP and Barr100 its 100 HP, breaking the chip-barrier row.

This is exactly the data-drift case the ticket anticipates: *"A NEGATIVE that names the byte which is not what T30 cites (i.e. the data drift case) also closes this ticket — T34's premise is that the subfamily index reads the right table, and if any chip's `attack_subfamily` byte drifts from the cited value, the lookup needs a different key."* The byte did not drift (subfamily is 4 for all three); the **premise** is wrong: the canonical read for BarrierHpByType_8020B2C is `chip.params[0]` (attack_param_1), not `chip.subfamily`. The lookup needs a different key.

## What is unverified

The barrier "type" byte stored at `oCollisionData_Barrier` (and passed as r0 to `barrierTakeDamage_801A7CC`, asm00_2.s:22585) was not traced from `set_barrier` / `sub_80E3B50` / `sub_801A7F4` through to its initial writer, so the conclusion that `params[0]` is the canonical read is currently anchored on the comment at src/battle.rs:655-659 (which cites the same asm/dat sites T30 cites) plus the chip_export output, not on a direct asm trace.
