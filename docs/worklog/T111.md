## Recon: where the drain is

The custom-screen tile drain is NOT in battle.rs -- it is in `src/custom.rs`
(the ticket's "cust.rs"): `Custom::draw_card` (src/custom.rs:999), the chip
replace branch. When the cursor lands on a slot whose chip differs from the
pictured one, the branch copies the whole card into BG3 VRAM in one burst:
picture fill_from (src/custom.rs:1026, PICTURE_TILES), name row
(draw_card_name), code/element/power row (draw_card_row). This is the only
large mid-frame tile-copy on the custom screen, it runs exactly on cursor-move
frames, and the row is compared `--only-bg 3` (BG3) -- the plane the burst
writes.

The cursor row's walk (`_CURSOR_WALK_RUST`, held Left at rust frames
250+30k, 6 frames, k in 0..5) makes five moves from the initial OK cursor:
OK->4 (k=7), 4->3 (k=37), 3->2 (k=67), 2->1 (k=97), 1->0 (k=127)
(CURSOR_DELAY=2: the move lands two frames after the press; row k=0 is rust
frame 245 = marker origin 8 + alignment offset 237, canon frame k+15).
T105 pass 6 measured the branch damage at k=37 (28 px, the 4->3 move) and
k=97 (1 px, the 2->1 move) -- both are move frames, both run the replace
burst. The pad therefore goes in the chip replace branch, immediately before
`let picture = offer.chip.picture();` (src/custom.rs:1022), delaying the
whole burst; it runs on ALL five move frames, which is what makes it able to
move k=97's phase too.

Frame loop context (src/main.rs:412): `battle.update()` runs right after the
previous frame's `commit()` returned from its vblank wait, so update's tile
writes land while visible scanlines render -- a copy caught mid-drain shows a
seam whose scanline position is a pure timing function. The pad is a
busy-wait of one named const; it reads and writes nothing.

## Pad design (step 2 protocol)

- `SEAM_PHASE_PAD_ITERS` (unnamed until the winning size is measured, then
  `provenance: fitted`): a `for 0..N { asm!("nop") }` busy-wait at
  src/custom.rs before the picture fill. Unit: loop iterations (each ~5-8
  cycles from ROM with waitstates; ~1.3-2 px of scanline per iteration at 4
  cycles/px) -- sized by measurement, not derived.
- Sweep: 1 harness cursor row per size (2 captures: rust + canon; the
  negative is recomputed from the same captures). Per-frame k table from the
  same run() result (variant_label="isolated", the same invocation run_check
  makes). Ladder 1,2,4,8,... adaptive: the k=37 px count is the guidance
  (grows = wrong direction; shrinks toward 0 = right); stop at the first size
  with k=37: 0 and k=97: 1 (total <=1, worst <=1).
- Veto after the winning size: full 10-row set -- opening, mettaur, cannon,
  buster, chip-use, wave, windowclose (guard), popup, emotion_syn
  (0/0/40/644 required), cursor (<=1 class) -- plus ROM sha256+size.

## Sweep log (size -> k table; 1 harness cursor run each, 2 captures)

Variant tried FIRST that did NOT work, so the next worker does not repeat it:
a pad inside `draw_card`'s replace branch (src/custom.rs, before the picture
fill, size 1) moved NOTHING -- exactly 29/28/170, k=37 still 28. Reason:
agb's RegularBackground writes a SHADOW buffer; the real VRAM copy is
commit()'s screenblock `copy_tiles` AFTER commit's own vblank wait, so game
code before the wait cannot move the drain. The knob must sit inside the
vblank window: a VBlank interrupt closure (interrupt_handler.s calls
`__RUST_INTERRUPT_HANDLER` before returning to the BIOS's VBlankIntrWait;
commit's copies start after that), registered from main.rs. That pad moved
the number on the first size, monotone to a V-bottom:

Alignment (marker origin 8 / chosen offset 237 / canon_ref 15) did not move
at any size. k=97's 1 px tear is phase-locked through the whole ladder --
size 17 lands exactly the target shape (k=37: 0, k=97: 1 = main's own tear),
total 1 / worst 1 / frames 170: the <=1 class. Constant tagged

Mechanism (one line): 17 nop-iterations (~90-140 cycles from ROM) delay the
vblank copy START so the screenblock drain's visible cut lands on canon's
phase on the card-replace frames -- k=37's 28 px of stale-vs-new columns go
to 0 and nothing else moves.
