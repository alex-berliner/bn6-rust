## Budget accounting (read this first)

The ticket prescribes "four times each" for 4 rows (= 16 row-runs if each row is its own harness
command) AND "at most 12 capture runs total (enforced at 12)". Those two numbers cannot both be
row-runs. Resolution used here, stated openly: **a "capture run" = one capture-producing COMMAND**
(one `harness --only ...` invocation, however many rows it batches, or one direct
`mgba_capture`-equivalent capture pair). Step 1 therefore runs `--only field,opening,gunner,mettaur`
4 times (2 per session, 2 sessions) = 4 commands, giving each row exactly its prescribed 4 runs.
Both counts are reported so a verifier can re-derive either unit:

- harness row-runs: step 1 = 16 (field 4, opening 4, gunner 4, mettaur 4)
- capture-producing commands: step 1 = 4, step 2 = 2 (field-bg2 kept-dir runs), step 5 = 3
  (`verify_rows` invocations) → **9 of the 12 budget** (warmup/timing run below makes 10).
- side-captures (mgba_capture invocations, F46's counting unit): step 1 ≈ 56, step 2 = 4,
  step 5 ≈ 16 — reported because F46 counted this unit.

Step 2 note: the harness DELETES both capture dirs when a row finishes (run_check, AUDIT pair 13),
so "step 2's frames come from step 1's dirs" is impossible as literally stated — `field-bg2` is not
one of step 1's rows and its dirs never survive a harness run. Instead `field-bg2`'s own sides are
re-captured through `harness.run()` imported from the SAME commit (identical Sides, align, frames —
no goalpost moved), with the dirs copied to `/tmp/bn-f48/` (my own dir; the canon inputs under /tmp
are untouched).

## Plan (ticket procedure, verbatim)

1. Envelope: field, opening, gunner + zero-row control mettaur, 4 runs each, two sessions
   (fresh process each command). Report min/max/spread of total/worst/negative per row.
2. field-bg2 per-frame: which k carries the spread (kept dirs in /tmp/bn-f48/bg2_runN).
3. Sign-consistency: every run's delta vs run 1; symmetric or one-sided; if one-sided, name the
   file:line in tools/mgba_capture.c (report only — the capture tool is off-limits this cycle).
4. Policy in tools/verify_rows.py ONLY: same-session drift-band for --expect on rows whose
   `search` is a range; never widen an expected total of 0; exit-code semantics unchanged;
   envelope printed.
5. Regression of the policy: true expectation PASSES, wrong-by-1000 FAILs, drift-band case reports
   as drift-band.

### Step 4/5 — the policy and its regression (commands 9, 10, 11)

Policy committed at **5e52c5b** (tools/verify_rows.py only): `--with-main [REF]` (default main)
measures the same-session main and bands a SEARCHED row's non-zero expect per the ticket;
`DRIFT_ENVELOPE = {"field": 25}` (provenance: peeked — NOT one delta but the max of FOUR
recorded totals, 158928/158935/158953/158930, of which only the 23 px T17/T19 component is
reproduced and the outer 2 px only cover the never-reproduced 158928; consequence: a real
tree-side regression of up to 25 px on field bands through); zero-total expects never widened;
search=None rows excluded via the measured tree's own Align config (runtime import, fail-closed
on import failure); exit semantics unchanged; flag off by default so no existing land.sh call
changes. land.sh does not pass --with-main (its only call site passes --expect) — that is why a
numeric band can coexist with AGENTS.md's "never a tolerance". Trap recorded in
measurement-drift.md §5: with `main_sha == sha` the code does `main_results = results`, so
`verify_rows <branch> … --with-main <same ref>` degenerates into a plain one-sided ±25
tolerance on the branch's own number — diagnostic only, never a landing gate.

The tests claim was false as committed and is now true: 5e52c5b's message said "7 unit tests"
but they existed only in my session. They now ship in the file as `verify_rows.py --selftest`
(offline, no captures, no harness import): zero-total → None; frames off-by-one → None; BLIND
either side → None; envelope 0 / unlisted row → None; branch 1000 off main → None; exp 26 off
main → None vs exp 25 → fires (inclusive boundary); same-session main anchor → prints
`MATCH (drift-band, main=158930 exp=158953)`; field=999999/0/40/0 → None ⇒ MISMATCH, exit 1.
All 10 probes print their result and pass; a band that cannot fail is not a policy.
Auxiliary fix, required for the at-risk class to be gateable at all: an expectation now matches
ANY of the row's harness ui lines — before, `opening=18740/647/40/98649` (the integrated line the
reports quote) ALWAYS MISMATCHed against the isolated 0/0/40/86591 (visible in F43's worklog);
gates that pass today still pass.

Regression demos on the committed policy (ref = 5e52c5b; main had moved to 8369084 mid-flight —
a sibling landed — my repeated runs stayed pinned to ed9c9c1 throughout):

1. wrong-by-1000: `--expect field=999999/0/40/0` → `MISMATCH total,negative`, **FAIL, exit 1** ✓
2. true expectation: `--expect field=0/0/40/-` → `MATCH (isolated line)`, **PASS, exit 0** ✓
