## Why this is a NEGATIVE worklog

T39's framing — "watch-write the BG3 plateau region at k=77..129 ... the
watch-write lever targets the BG3 enable + chip-window BG3 layer words
during k=77..129" — names four addresses whose canonical
(init/fight-state) writes do NOT occur during the k=77..129 plateau band:

| address (ticket name)           | writes in 130 frames | PC | LR |
|---|---|---|---|
| 0x02000010 BG3_enable_word      | 0                    | —  | —  |
| 0x02000014 BG3_layer_attr      | 0                    | —  | —  |
| 0x02034900 chip_window_state   | 1 (frame 69 only)    | 0x08007790 (thumb) | 0x08007595 |
| 0x02034910 chip_window_layer   | 1 (frame 69 only)    | 0x08007790 (thumb) | 0x080076F9 |

The two writes that DO fire are init-time: at canon capture frame 69
(canon's `battlestart_gunner.state` finished loading and the fight state's
first per-frame pass populated the pointers to MegaMan's BattleObject
[0x0203A9B0] and enemy slot 0's BattleObject [0x0203AA88]). They are
written BEFORE rust's capture window opens (rust frame 0 == the harness's
BATT-marker first appearance; k=77..129 maps to rust frames ~27..79, well
into the fight state). Neither write fires again in 130 frames. The
0x02000010/0x02000014 addresses are never written at all in this row.

The `0x02034900` / `0x02034910` names in the ticket are misleading: the
values stored are `RelatedObject` pointers (src/battle.rs:160 doc cites
`oBattleObject_RelatedObject1Ptr` at sub_800FAAC), not chip-window state
or BG3 layer words. Canon sets them once during battle init and never
touches them again in the gunner's settle window — the BG3 plateau
visual difference (per the harness analysis at tools/harness.py:2493-
2495, "k>=77 — canon's gauge-full pause opens the chip window on BG3")
must be caused by writes to other addresses (likely BG3 hardware
registers BG3HOFS/BG3VOFS/BG3CNT at 0x0400001C/1E/0E, or VRAM tile
data for the chip-window layer, or the panel-update path the ticket
explicitly excludes).

## Step 3 — watch-write on the four ticket-named addresses

The ticket's command invokes a hypothetical `probe.py watch-write`
subcommand that does not exist; the underlying capability is
`tools/mgba_capture`'s `--watch-write` flag (AGENT_GUIDE.md mgba_capture
flags section). I invoked it directly:

```
$ /tmp/mgba_capture /tmp/bn6f_real.gba /tmp/t39_capture 130 \
    --loadstate /tmp/battlestart_gunner.state \
    --watch-write 0x02000010:4 --watch-write 0x02000014:4 \
    --watch-write 0x02034900:4 --watch-write 0x02034910:4 \
    2>/tmp/t39_wp.log 1>/dev/null
$ grep -E '^(WP|watch-write)' /tmp/t39_wp.log
watch-write: 4 range(s), 16 byte watchpoint(s) armed
WP frame=69 addr=0x02034900 write old=0x00000000 new=0x0203A9B0 at=0x08007790 (thumb) r15=0x08007794 lr=0x08007595
WP frame=69 addr=0x02034910 write old=0x00000000 new=0x0203AA88 at=0x08007790 (thumb) r15=0x08007794 lr=0x080076F9
```

Only two writes logged, both at frame 69 (init). 0x02000010/0x02000014
have zero writes in 130 frames. **NO writes occur during k=77..129**
to any of the four ticket-named addresses.

WP line interpretation (per tools/mgba_capture.c:201-209 `wp_entered`):
- frame=69 is the FIRST frame after `battlestart_gunner.state` settles
  into the fight state (the state-loading white runs capture frames 0..70
  per T37's worklog measurement; frame 69 is the last pre-fight-state
  frame where the BattleObject pointers get hooked up).
- Both writes share the writing PC `0x08007790` (Thumb) but different
  LR: `0x08007595` for the 0x02034900 write and `0x080076F9` for the
  0x02034910 write — two distinct init-time callers of the same
  BattleObject-pointer-store site. The LRs are within the 0x08007xxx
  ROM block; that range is past the disassembly reach of this worktree
  (the project ships the `reference/bn6f/asm/` disassembly in the main
  checkout only; `/tmp/bnwt/t39-gunner-bgaplateau` is missing it — the
  asm *.s files are not in this worktree).
- newValue 0x0203A9B0 = `MegaMan*` (BattleObject base for slot 0, the
  player object — src/battle.rs:1763 oracle doc cites it). newValue
  0x0203AA88 = enemy slot 0's BattleObject base (the Mettaur). These
  are the `RelatedObject*Ptr` fields canon hooks to on battle init,
  NOT chip-window state — see src/battle.rs:160 doc citing
  `oBattleObject_RelatedObject1Ptr` (sub_800FAAC, asm00_2.s:1903-1916).
  The ticket's name `chip_window_state` for 0x02034900 is misleading.

## What would close this for a follow-up worker

1. Run mgba_capture with `--watch-write` on the BG3 hardware registers
   BG3CNT (0x0400000E, 2 bytes), BG3HOFS (0x0400001C, 2 bytes), BG3VOFS
   (0x0400001E, 2 bytes), and DISPCNT (0x04000000, 4 bytes), the same
   130-frame capture, --loadstate battlestart_gunner.state. That costs
   one capture. The WP log should show the BG3-on / chip-window layer
   enable at frame ~80 (canon) and confirm the BG3 plateau trigger is
   a hardware register, not a WRAM pointer.

2. If the WP at BG3HOFS / BG3VOFS / BG3CNT shows the rust side is
   missing those writes (and the rust ROM is built; this worktree did
   not run `cargo build --release` because the NEGATIVE outcome
   precludes the change), the port would land in `src/battle.rs`'s
   gauge-pause-to-chip-window path (the `gauge_pause == 0` branch at
   src/battle.rs:2803-2805, which arms the chip-window open in
   `self.custom`) or in the corresponding `Battle::update_chip_window`
   leg the battle.rs:HUD/window block runs.

3. Alternatively, if the WP shows the rust side DOES write those
   registers but the diff is still 2,105,613, the plateau is caused
   by a tile-data / VRAM difference (likely the chip-window tile
   asset in `custom.rs`) — outside the files this ticket allows.
