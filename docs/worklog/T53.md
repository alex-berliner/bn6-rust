## Step 3 — gap to T50's arm

T50's first arm (the 0x0A hop executor port) maps the enemy's
`Action::Hidden | Action::Appearing { .. }` and the trailing `_`
default to CurAction 0x0A in `Actor::oracle_fields`. After T50,
rust's `enemy_state_action` agrees with canon at k=0..16
(both at 0x0A) but diverges at k=17 where canon's mettaur has just
handed CurAction back to 0x08 (`MettaurDecide_8109FD6` dispatch)
and rust stays at T50's 0x0A idle mapping. The fields touched by
the dispatch are: `oBattleObject_CurAction` (+0x09 byte) and
`oAIState_Unk_00` (+0x80 within the AI vars, the decide sub-state
index). The Rust export path already models CurAction via
`Actor::oracle_fields`; the new arm needs to read canon's CurAction
0x08 byte directly rather than T50's static `0x0a` mapping.

#### 5b — diagnosis (this ticket's negative result)

Re-recorded the rust trace with the ported ROM at `/tmp/tr_t53b_r`.
Rust's `e1_state_action` stays at `[4, 10]` for k=0..30+, with the
panel staying at (5, 2) the entire time. Two possible causes
investigated (the tool budget closed before either could be
uniquely pinned):

1. The rust mettaur never reaches `Action::Idle` from a non-Idle
   transition. The trace shows `e1` at CurAction 0x0A throughout
   (T50's mapping for `Action::Hopping` and `Action::Recovering
   { hop_recovery }`), so the mettaur is in some non-Idle Action
   the entire window -- likely `Action::Idle` mapped to 0x0A but
   no `Action::Hopping` motion observed (panel=(5,2) for all 540
   frames). If the mettaur is in `Action::Idle`, `ai_cur_action`
   should be 0x08 (post-spawn-pause `METTAUR_ACT_DECIDE`) and the
   export would return 0x08. The trace shows 0x0A instead, so
   either the new arm is not selected or `ai_cur_action` reads as
   0x0A (which `MettaurEntry::cur_action` never holds -- it cycles
   8 → 9 → 8, never 0x0A).

2. The `Action::Idle` mapping might be reading from the wrong
   Action variant -- e.g. an enum variant I haven't accounted for
   matches a higher-precedence arm. The T50 comment at
   src/actor.rs:680-700 already documented that the rust intro runs
   `Action::Hidden | Action::Appearing { .. }` for several frames
   past canon's settle, so the export during that window reads
   0x0A via the post-T50 default. If the mettaur is still in
   `Action::Appearing` at the export's first compared frame and
   never transitions to `Action::Idle`, the `Action::Idle
   if !is_player => ai_cur_action` arm never fires.

The simplest fix would be to assert (e.g. via a debug print or a
panicked assertion during a release test build) what
`Action::Idle` matches and what `ai_cur_action` reads at k=17, but
the tool budget closed before that could be run. A NEGATIVE that
names the actual arm that fires (`Action::Appearing { .. } => 0x0a`
or `Action::Hopping => 0x0a`) and the actual value of
`MettaurEntry::cur_action` at k=17 closes this ticket.
