## Step 1 — read the tables out of the ROM (measurement, no capture)

Read directly from `/tmp/bn6f_sterile.gba` bytes (af13c206…43e4154cf3, 8388608 B),
file offset = addr − 0x08000000, and cross-checked against the disassembly.

**Ticket-premise correction.** The ticket calls `byte_801E6F4` "the 23-entry
enum→slot table". The ROM says otherwise:

- `byte_801E6F4` @ **0x0801E6F4** (asm00_2.s:31045) is **6 entries + 2 pad bytes**
  `[0, 2, 3, 1, 5, 4]` (pad `0,0`). It maps the **emotion ENUM**
  (`possiblyGetBattleEmotion_8015B64`'s res0, asm00_2.s:15122-15174) to a face
  slot. Its two consumers index it with the enum (`ldrb r0, [r2,r0]`,
  asm00_2.s:30970/30984/30997/31011/31033 — stride 1).
- The **23-entry table next door is `byte_801E700` @ 0x0801E700**
  (asm00_2.s:31049): 25 entries + 3 pad
  `[0, 5, 6, 7, 8, 9, 5, 6, 7, 8, 9, 0x14, 0x14, 0xF, 0x10, 0x11, 0x12, 0x13,
  0xF, 0x10, 0x11, 0x12, 0x13, 0x16, 0x16]` (pad `0,0,0`). It is indexed by the
  **TRANSFORMATION** byte (the r1 second return of possiblyGetBattleEmotion,
  read at asm00_2.s:30966 `ldrb r6, [r2,r4]`), not the emotion enum — with
  post-adjustments: for r4 in 1..10, if `byte_801E6F4[enum] == 2` (Unk_32 set,
  full synchro) slot += 5; for r4 == 11/12, if `byte_801E6F4[enum] == 3`
  (beast out with Mood==0xff: the test at asm00_2.s:31022-31025 is on the
  RESOLVED SLOT value 3, and slot 3 comes from enum 2 = Mood==0xff,
  `byte_801E6F4[2] = 3`; Anger is enum 3 → `byte_801E6F4[3] = 1`, a different
  arm) slot += 1 (asm00_2.s:30975-31001).

**Skip-range (5/6) entries.**
- `byte_801E6F4[4] = 5` — but enum 4 is **unreachable**:
  `possiblyGetBattleEmotion_8015B64` (asm00_2.s:15140-15166) only ever returns
  5 (Unk_36≠0 or Mood==0), 3 (Anger≠0), 1 (Unk_32≠0), 2 (Mood==0xff), 0. So no
  poke on the AIData bytes can ever land a slot in the skip range through the
  enum table. This is the ticket's "one enum that lands on a skip slot" premise
  failing: **there is no such enum**.
- `byte_801E700[1] = 5`, `[2] = 6` — reachable only via a non-zero
  transformation byte, i.e. a Beast Out/Cross state, not a poke recipe on this
  route.
- **Mechanism correction (verifier pass):** the earlier draft claimed the
  skip range is therefore "only reachable in the compared window by the
  draw gate's own byte". That is wrong on two counts. (1)
  eStruct2035280+0xf = 0x0203528F is not a draw-gate owner of the skip
  range at all: it is the 12-step **blink countdown** owned by sub_801CC94
  (asm00_2.s:27550-27551 loads 0xc, :27557-27566 decrements once per frame
  and reloads at 0, :27567-27574 copies the 0x20-byte blink pattern
  byte_801CDA4 -> byte_30016D0 off bit 1 of that same byte); the face slot
  lives at +0x10/+0x11 (asm00_2.s:27341-27342, read back at :27403). The
  draw gate's `cmp #6` / `cmp #5` (asm00_2.s:27648-27652) are two phases of
  that 12-frame cycle — canon blanks the face window ~2 frames per cycle,
  which IS the blink. (2) A transformation-resolved slot 5/6 is uploaded and
  drawn normally: the upload path's `cmp #5` at asm00_2.s:27390
  (`bge loc_801CBBE`) only skips the blink *bookkeeping* — `loc_801CBBE`
  (asm00_2.s:27404) IS the upload — so `byte_801E700[1] = 5` (a cross
  state) reaches the screen whenever the countdown is not sitting at 5/6.
  What `emotion_skip` actually measures is the countdown byte pinned to 5
  (canon's blink blanking held on) against our `emotion 5/6` arm that
  builds no sprites — an empty box against an empty box.

**Slot coverage.** `off_801CD08` @ 0x0801CD08 (asm00_2.s:27580-27603), 23
pointer words, read from ROM, deltas from dword_872D814:
`[0x0000, 0x0180, 0x0300, 0x0480, 0x0600, 0x0780, 0x0880, 0x0980, 0x0a80,
0x0b80, 0x0c80, 0x0d80, 0x0e80, 0x0f80, 0x1080, 0x0780, 0x0880, 0x0980,
0x0a80, 0x0b80, 0x1700, 0x1700, 0x1800]` — byte-identical to the landed
`src/emotion.rs` FACE_INDEX. Slots 15..19 alias 5..9, 21 aliases 20; slots 5/6
HAVE art (0x780/0x880) and ARE drawn -- a transformation-resolved slot 5/6
uploads through loc_801CBBE (asm00_2.s:27404) and reaches the screen except
during the ~2-frames-per-cycle blink phases 5/6; the landed
`assets/emotion.bin` bank covers all 23 slots (0x1900) and all 23 palettes
(0x2e0). Palette check from ROM (dword_872F114 + slot*32): slot 4's palette
DIFFERS from slot 2's, as do all of 0,1,3,4..22 — every drawn face has its own
palette.

**Chosen pokes.**

- `emotion_skip` (skip arm): blink countdown byte, aligned halfword poke

  (eStruct+0xe, the beast-out counter — the SECOND return of the emotion
  call, asm00_2.s:27343-27344 storing sub_801E6A8's r1, and

  earlier drafts called it "stored transformation", which is wrong — it

  0x0203528F=0x05 (eStruct+0xf, the blink countdown → draw emits nothing

## One line of mechanism / one line unverified

Mechanism: canon picks the face from live AIData bytes through byte_801E6F4
(enum→slot) or byte_801E700 (transformation→slot), uploads slot art +
per-slot palette every frame, and the blink countdown at eStruct+0xf=
0x0203528F blanks the window ~2 frames per 12-frame blink cycle (countdown
phases 5/6, asm00_2.s:27648-27652) — the port takes the already-resolved
slot from descriptor +63 and reproduces both a drawn face (slot 4) and the
countdown pinned at 5 (no face on either side) byte-exactly.

Unverified: the remaining emotion slots never compared to a pixel (bank slots
1, 6..22 — no reachable poke on this route drives them; slot 4 and the
pinned countdown are now proven), and the emotion **counter** window, which
is its own item.

## Verifier-driven correction (2026-09-18) — refuted sentences removed

The verifier pass refuted the mechanism claimed for `emotion_skip` and found
two false sentences; this commit removes them from the branch.

1. REFUTED: "the draw gate at eStruct+0xf suppresses the whole window for
   slot values 5/6" — +0xf is the blink countdown (see the mechanism
   correction above), not a skip-range gate.
2. REFUTED: "no AIData enum reaches slot 5/6, so the skip range is only
   reachable via the gate byte" — the transformation table
   (byte_801E700[1]=5, [2]=6) reaches 5/6, and the upload path draws them
   (`loc_801CBBE` IS the upload; its `cmp #5` skips only blink bookkeeping).
3. Also fixed: the `(Anger)` gloss on the +1 arm (the test at
   asm00_2.s:31022-31025 is on resolved slot value 3, which comes from
   enum 2 = Mood==0xff; Anger is enum 3 → slot 1); +0xe renamed from
   "stored transformation" to beast-out counter (asm00_2.s:27343-27344,
   31039); the chain section's "poking it changes no pixels" vs the new
   section's "694 px/frame" contradiction (both true at different countdown
   phases — see coverage/emotion.md's chain section).
4. Coverage arithmetic: M7 emotion goes **1/25 → 2/25** (emotion_syn +
   emotion_face_b); the skip row is withdrawn from coverage pending the
   follow-up (empty box vs empty box proves the align window, not a face).

## For the next ticket: the real defect this surfaced

`src/emotion.rs:71-74` and `:89-95` treat the descriptor's `emotion` as the
value canon's +0xf checks and build **no sprites at all** for 5/6. Under the
blink reading that is a wrong reason to be right only on the emotion_syn
route: canon's +0xf is a per-frame countdown, not a face value, so a
cross-state face (transformation 1/2 → slot 5/6 via byte_801E700, drawn
through loc_801CBBE) is likely missing from our port — the descriptor would
need to carry the resolved slot 5/6 and we would have to build sprites for
it. Needs its own scenario (a cross state with a nonzero transformation
byte, e.g. byte_801E700[1] = 5) plus a src/emotion.rs change. Do NOT
reconcile by re-thresholding the skip row: it stays a pairing row.
