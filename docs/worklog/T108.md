### TRAP for the next worker (cost half a session): v2 asset + v1 reader = battle deleted

Rebuilding with the 7156-byte asset while src/emotion.rs still had the v1 reader
gave a ROM 217KB SMALLER (366952 B, sha e25f7f74...) in which the battle NEVER
STARTS (harness: "the battle-started marker never appeared"). Mechanism: the v1
reader slices `tiles[256..]` as the 16x16 sprite; with the v2 asset that slice is
6144 bytes, agb's `try_from_bytes_in` asserts `bytes.len() == allocation_size`
(dynamic.rs:264, "buffer length should match sprite size"), and with fat LTO +
a fully-known static LLVM const-folds the assert to false and DEAD-ELIMINATES
`Battle::update`/`Battle::draw` and every asset static (confirmed in the symbol
tables: v1 has 159 extra symbols incl. all `_RNnNv..DELETE0` statics; v2 keeps
only a 12KB main inner). The ROM still boots the intro, so only the harness
marker check catches it. **The asset and the reader must land in the same
commit.** Any future asset-size change can silently delete the battle the same
way — the marker check is the guard.
