Worktree: /tmp/bnwt/t118b, branch wt/t118b (from main a8bd3d3).

### Cut structure (step 1)

At pad 17 today's main reads k=7/37/67/127 = 0 px and k=97 = 1 px
(row (y=5, x=183)) — the row is in class, so there is no canon-vs-rust band
to measure at the fitted pad: the two sides' cuts coincide. The cut shows
itself only on broken (footprint, pad) pairs. Measured on two:

- plus-pad17 (k=37): rows y=0..3, x=217..238 — 17 px in the top-right
- minus-pad13 (k=37): rows y=0..3, x=217..221 — same shape, 19 px
- plus-pad21 (k=37): rows y=0..4, x=217..238 — same shape, 25 px

So the seam lives in scanlines 0..4 at x~217-238 (top-right corner), the same
shape at every broken point, and the band DEEPENS (more scanlines) as the pad
moves away from the in-class phase. Copy duration: T118's census arithmetic
(whole screenblock = 2048 B ~= 4.1k cycles ~= 3.3 scanlines) stands; the
pad->px calibration here adds: 1 pad iteration ~= 6.5 cycles ~= 1.6 px of cut
phase, so one scanline (1232 cycles) ~= 190 iterations. I could not measure
the copy's duration directly without instrumenting vendor/ (forbidden by this
ticket) — the 3.3-scanline figure is cycle arithmetic, not a scanline scan.

## Step 3 — the anchor (code change)

SEAM_PHASE_PAD_ITERS deleted; replaced by SEAM_ANCHOR_LY = 160 (REG_VCOUNT
0x04000006): the VBlank closure spins until the scanline counter reads the
VBlank line before returning, pinning commit's copy start to a scanline
instead of a fitted cycle count. At the VBlank IRQ LY already reads 160, so
the anchor's steady-state cost is one 16-bit load + compare (the measured
pad-0 phase, which is the in-class phase on all three footprints).
