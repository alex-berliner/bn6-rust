Worktree: /tmp/bnwt/t118b, branch wt/t118b (from main a8bd3d3).
Premise (from T118's worklog, treated as given): the <=1/1/170 cursor class is a
phase-alignment coincidence between our vblank+pad whole-screenblock copy and

### Cut structure (step 1)

At pad 17 today's main reads k=7/37/67/127 = 0 px and k=97 = 1 px
(row (y=5, x=183)) — the row is in class, so there is no canon-vs-rust band
to measure at the fitted pad: the two sides' cuts coincide. The cut shows
itself only on broken (footprint, pad) pairs. Measured on two:

- plus-pad17 (k=37): rows y=0..3, x=217..238 — 17 px in the top-right
- minus-pad13 (k=37): rows y=0..3, x=217..221 — same shape, 19 px
- plus-pad21 (k=37): rows y=0..4, x=217..238 — same shape, 25 px

So the seam lives in scanlines 0..4 at x~217-238 (top-right corner), the same
shape at every broken point, and the band DEEPENS (more scanlines) as the pad
moves away from the in-class phase. Copy duration: T118's census arithmetic
(whole screenblock = 2048 B ~= 4.1k cycles ~= 3.3 scanlines) stands; the
pad->px calibration here adds: 1 pad iteration ~= 6.5 cycles ~= 1.6 px of cut
phase, so one scanline (1232 cycles) ~= 190 iterations. I could not measure
the copy's duration directly without instrumenting vendor/ (forbidden by this
ticket) — the 3.3-scanline figure is cycle arithmetic, not a scanline scan.

## Step 3 — the anchor (code change)

SEAM_PHASE_PAD_ITERS deleted; replaced by SEAM_ANCHOR_LY = 160 (REG_VCOUNT
0x04000006): the VBlank closure spins until the scanline counter reads the
VBlank line before returning, pinning commit's copy start to a scanline
instead of a fitted cycle count. At the VBlank IRQ LY already reads 160, so
the anchor's steady-state cost is one 16-bit load + compare (the measured
pad-0 phase, which is the in-class phase on all three footprints).

## Steps 3-5 — the anchor measured, and the bounded NEGATIVE (2026-09-19)

The anchor code (SEAM_ANCHOR_LY=160 spin on REG_VCOUNT in the VBlank closure,
commit 8da06fb) was built and measured on three footprints:

| variant | ROM B | cursor k37/k97 |
|---------|-------|----------------|
| anchor, main footprint | 592564 (sha a68bc899) | **31/19 — OUT of class** |
| anchor, −1132 B asset | 591436 (sha 8673403d) | 0/1 — in class |
| anchor +1132 B | not built separately (driver bug: the filler insertion key on the deleted pad const made it a duplicate of the main build) | — |

- LY=161 (one full scanline of delay), main footprint: k37=37, k97=21 — out.
- LY=160 + nop trim 1/2/3/4 (sub-scanline trim, the ticket's allowed residue):
  k37 = 31/31/31/22, k97 = 19/29/29/1 — no in-class trim in 1..4.

A phase-vs-LY table at scanline granularity cannot fix the class: one full
scanline of delay does not re-phase the cut, because the phase that matters is
sub-scanline, and the anchor's own 28 bytes of code (vs the 0-iteration pad
loop's layout) move main's cursor 0/1 -> 31/19. Copy duration in scanlines:
3.3 (T118's cycle arithmetic: 2048 B ~= 4.1k cycles / 1232); 1 scanline ~=
190 pad iterations (6.5 cycles/iter, from the pad->px calibration ~1.6 px per
iteration at 4 cycles/px).

What still sets the phase: the sub-scanline code layout of the IRQ-entry ->
copy-start path (closure body size/alignment, IRQ return, commit preamble).
Evidence: pad-0 layout in-class across +2.5 KB and −1.2 KB asset deltas, but
a 28-byte code delta (the spin replacing the empty loop) breaks it; the
response is chaotic, not monotone in bytes (plus pad0/p13 in-class, minus
p0 in-class, both layouts' neighbours out).

**Verdict: bounded NEGATIVE.** No footprint-stable knob exists at the closure:
not the fitted cycle pad (per-footprint), not an LY anchor, not LY+trim.
src/main.rs is restored to main's proven pad (fitted 17) on the branch tip —
the anchor commit (8da06fb) is kept in history for the record but REVERTED at
the tip; landing it would break cursor on main (0/1 -> 31/19).

Consequences for wt/T112 and wt/T117: this ticket does NOT unblock them by
anchor. Their own measured state (T112 cursor 7/6 at pad 12; T117 sweep
13..18 no in-class value) should be re-read at pad 0/natural phase on their
own trees — today's main suggests the unpadded start is the most often
in-class configuration (3/3 footprints here), but it is a layout coincidence
and must be re-measured per landing, not relied on. The real fix remains
placing our writes at canon's phase by construction (T118's conclusion).

Step 5 (apply on wt/T112 / wt/T117): NOT RUN — the anchor is dead on main's
own footprint, so there is no value to apply; running it on the branches
would only re-demonstrate the re-roll. The 9-row guard set was run on the
branch tip (src == main's src): all PASS at main's own numbers (cursor
1/1/170, the k=97 1 px tear).
