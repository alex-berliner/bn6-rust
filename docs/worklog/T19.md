Choices, and why:
- Arc `_ => (0,0)`: replaced by explicit arms for ALL 11 distinct rows
  SwordArcBySubfamily_80EBAD8 defines (values verified against the ROM bytes
  above) + a named panic arm for anything else. I chose explicit arms + panic
  rather than a debug-only panic because a release-mode panic is still loud
  (the ROM's agb panic handler prints the message), and a debug-only panic
  would reintroduce the silent door in every release capture.
- Shape `_ =>` (the default arm Sword's own shape 1 rides): added an explicit
  `SHAPE_PANEL_AHEAD: u8 = 1` arm (behaviour-identical, shape 1 still pushes
  the single panel ahead) + named panic default for the shapes the table
  carries but no asset record can (0x11/6/0xB -- other subfamilies'). A
  widened asset delivering one of those must fail loudly, not quietly slash
  one panel.

**The six absent family-0x13 ids.** `/tmp/t19_arc_check.py` parses
SWORD_ARC_ROW + the match arms OUT OF src/battle.rs itself (not a copy) and
evaluates the six ids. They CANNOT reach chip_strike through the asset today
(assets/chips.bin holds 48 records, ids 286/339/370/374/376/410 are not among
them -- no reachability is faked here); the check runs their ROM subfamilies
through the shipped mapping arithmetic:

```
BEFORE: 286 sub 0x06 -> row 0x1c -> (0,0) via _ => default
        339 sub 0x05 -> row 0x1b -> (0,0) via _ => default
        370 sub 0x09 -> row 0x25 -> (0,0) via _ => default
        374 sub 0x0a -> row 0x5f -> (0,0) via _ => default
        376 sub 0x0b -> row 0x1b -> (0,0) via _ => default
        410 sub 0x01 -> row 0x16 -> (0,0)   (explicit arm already)
AFTER:  286 -> 0x1c -> (0, 2); 339 -> 0x1b -> (0, 0);
        370 -> 0x25 -> (3, 0);    374 -> 0x5f -> (0, 0);
        376 -> 0x1b -> (0, 0);    410 -> 0x16 -> (0, 0)
        (all explicit; no _ => (0,0) remains)
```

Note 374 (row 0x5f) and 339/376 (row 0x1b) resolve to (0,0) HONESTLY -- that
