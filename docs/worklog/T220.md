## The canon mechanism (the cites)

`bannerSeqState04BannerWait_8008064` (asm00_1.s:10520-10590, the SEQ_04 handler):
- entry run (byte [r5,#3] == 0): arms timer [r5,#8] = 0x1e (30 — our existing
  peeked `BATTLE_START_AFTER_WINDOW`), latches [r5,#3] = 4, then calls
  `spawnBannerRecord_801E792` (asm00_1.s:10567) with (r0,r1) = (0,0) on the
  normal path (GetBattleEffects bit 3 clear) or (0xc, [BattleState+7]) on the
  effects path (loc_8008096/loc_80080A6).
- every run: `bl isBannerBusy_801E754; cmp r0,#0; bne` (asm00_1.s:10569-10571) —
  release only when isBannerBusy returns 0, then `mov r0,#8; str r0,[r5]`
  (asm00_1.s:10609-10610, SEQ_04 -> SEQ_08).

`isBannerBusy_801E754` (asm00_2.s:31233-31255): r0 = 0 when
`eStruct2035280.HudElementMask & 0x8000` is CLEAR; nonzero while set. So the
release edge reads the HUD mask's bit 15, and bit 15 is the banner record's
liveness.

`spawnBannerRecord_801E792` (asm00_2.s:31276-31351): early-returns without
spawning when mask bit 15 is already set (:31284-31289); zeroes byte_2036847 and
byte_2036840 (the record's counter and state bytes, :31292-31293); reads the
descriptor `pt_801EF84[id]` — for id 0 that is `dword_801F040`
(dat00.s:134/183), whose first halfword 0x4034 is the banner sprite's
tile/palette attrs copied into word_2036842 (consumed as OAM attrs in
sub_801CF3C, asm00_2.s:27957-27968 — NOT a frame count), and whose byte [2] = 0
becomes byte_2036848, the record kind; then dispatches the kind handler
(off_801E944) and sets mask bit 15 (`setBattleHudElements_801BECC(0x8000)`,
:31329-31331).

The record's LIFECYCLE is `sub_801CE28` (asm00_2.s:27796-27822), dispatched per
update on the record state byte byte_2036840 through off_801CE5C:
- state 0x00 `sub_801CE6C` (:27831-27847): counts byte_2036847; at >= 5 ->
  state 0x04, counter reset.
- state 0x04 `sub_801CE92` (:27850-27876): counts; at >= 0x30 (48) -> state
  0x08, counter reset. (The sub_801CE28 increment suppression at counter==5
  applies only when state==4 AND kind in {2,4}; our kind is 0, so the count
  runs plain.)
- state 0x08 `sub_801CED2` (:27879-27898): counts; at >= 5 -> state 0x0C
  (after sub_802FE6A teardown of the sprite slot).
- state 0x0C `sub_801CEFA` (:27901-27908): `clearBattleHudElements_801BED6
  (0x8000)` — mask bit 15 CLEARS on this update. That is the record-done edge.

Counted lifecycle: 5 + 48 + 5 counting updates, then the 0x0C update clears the
mask — the mask is clear from the record's 59th update. With the record ticking
once per SEQ_04 frame after the handler's busy check (canon: the mask dispatch
runs after the sequencer handler in frame order), the first SEQ_04 frame whose
busy check sees a clear mask is the 60th — canon's SEQ_04 span k=136..195
(battle_full trace, T7b), which the fitted `SEQ04_FRAMES = 60` /
`age >= SEQ04_FRAMES - 1` encoded.

## Calibration against our Sequencer (why the release frame is unchanged)

`Sequencer::transition` resets age to 0 (src/battle.rs:1379-1384). The SEQ_00 ->
SEQ_04 transition fires inside the SEQ_00 match arm, so on the entry frame E no
SEQ_04 arm runs; on frame E+j the release check sees age = j-1, and fitted
release (age >= 59) fires on frame E+60 — the 60th exported SEQ_04 frame (E
exports SEQ_04 age 0; E+60 exports SEQ_08). The record model: spawn at the
transition edge (mask bit set, record state 0x00, counter 0), tick once per
SEQ_04 hold frame AFTER the release check. The record's 59th update (mask
clear) lands in frame E+59's tick, so the first release check seeing it done is
frame E+60 — the same frame fitted release fired. No fitted count: 5, 0x30, 5
are the three cited canon counters; the 0x0C edge is the cited mask clear.

## The Battle-field layout butterfly (measured, then routed around)

The first port stored the record as a `banner_record: Option<BannerRecord>` FIELD on Battle.
windowclose then read 63962/3557/40 deterministically (x3) and cursor 16241/3385/170. Diagnosis
by A/B captures (/tmp/t220/wcf=fitted, wcr=record, byte-deterministic: fitted x2 = 0 diffs):
- the record-vs-fitted sequencer word (TRC2 0x020000AA, no trace flag) showed IDENTICAL
  SEQ_04 entry (capture 272) and release (capture 332) -- the release frame did not move;
- the marker magic (BATTLE_MARKER, 0x02000000) appeared one capture frame LATER on the record
  build (origin 9 vs 8), and battle frame 0's whole upper screen (y0..109, 24811 px) rendered
  differently, re-syncing from bf1 (record 10 == fitted 9 == fitted 10);
- an inert appended const (`const _T220_PROBE: u32 = 0;`) did NOT flip the row (0/0/40);
- the field addition ALONE (struct + field + init, zero logic wired) DID flip it, to the exact
  same 63962/3557/40 -- Battle's layout shift moves the boot/init timing across a VBlank
  boundary, the marker lands a capture frame later, and the script-timed Start@230/A@260
  presses desync from battle time.
Fix: the record lives in `static mut BANNER_RECORD` (BATTLE_MARKER's ownership precedent,
src/main.rs:173), read/written BY VALUE (Rust 2024 denies references to statics; the record is
Copy). Battle's layout is untouched; all three canaries returned to byte-identical.
