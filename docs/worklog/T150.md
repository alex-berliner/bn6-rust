This ticket asks to port `navicust_NCP_SuperArmor` (the lowest-numbered
SetCurPETNaviStatsByte handler in `navicust_jt_NCPs`, asm37_0.s:2168),

applies here.

## Step 2 -- the chosen handler + the chain (cited, measured)

**Lowest-numbered SetCurPETNaviStatsByte handler** (per inventory.py and
the asm37_0.s walk):

- `navicust_NCP_SuperArmor` (asm37_0.s:2168) is the FIRST handler after
  the no-op stub at asm37_0.s:2162 (`sub_813C808`, push/pop pc; entry 0
  of navicust_jt_NCPs at asm37_0.s:2111). The inventory list and the
  asm bytes both confirm: stub @ entry 0, then SuperArmor @ entry 1
  (jt word at asm37_0.s:2113). SuperArmor calls
  `SetCurPETNaviStatsByte(0, 0x23, 1)` -- writes slot 0x23 (SuperArmor)
  = 1 into whatever NaviStats record the toolkit's `NaviStatsPtr` (the
  `r10` toolkit + 0x74) points at, which is 0x020047cc on the master
  record (T110 measurement).

**Give/take chain** (re-cited, asm37_0.s / asm03_1_1.s):

1. `GiveNaviCustPrograms` (asm03_1_1.s:8799) -- the navicust-program
   "give" entry point: push, bl `sub_803D148`, mov r1 r4, bl GiveItem,
   pop.
2. `GiveItem` (asm03_1_1.s:8305) -- `cmp r0, #0x71 / bne loc_803CDE4` is
   the dispatch gate: when the program id is 0x71 (the navicust-program
   opcode), the routine calls `reloadCurNaviStatBoosts_813c3ac` BEFORE
   the per-item counter write at loc_803CDD8 (loc_803CDD8 only happens
   on the fall-through path).
3. `reloadCurNaviStatBoosts_813c3ac` (asm37_0.s:1720) -- calls
   `applyNaviStatsMaybe_813C458` and then unconditionally calls into
   the MaxHP/CurHP correction block.
4. `applyNaviStatsMaybe_813C458` (asm37_0.s:1796) -- bl
   `sub_813BBD4`, bl `sub_8136C24`, GetCurPETNavi/SaveCurPETNavi flip,
   `sub_813C678`, ClearEventFlag `EVENT_170D`, bl
   `applyNavicustPrograms_813C684`, `sub_813CBCC`, restore
   CurPETNavi, `sub_803CE44`.
5. `applyNavicustPrograms_813C684` (asm37_0.s:2012) -- the dispatcher:
   zero-fill byte_2006DD8 (8 bytes), then loop r6 = 6 down to 0
   reading unk_2006CF8[r6]; for each non-zero entry, call
   sub_813B9FC(id-1) to fetch the record pointer at
   r10[oToolkit_Unk2004190_Ptr]+8*id (the 0x02004190 record array);
   halfword[0] is the handler id with low-2-bits reserved; clear the
   low bits with `lsr r0,r4,#2; lsl r0,r0,#2`, then index
   `navicust_jt_NCPs` and `bx r1` -- dispatch.

## Step 3 -- T110's route refutation applies here (measured, repeated)

T110 enumerated the chain's callers (the only sites that light up the
dispatch path):

```
reference/bn6f/asm/asm00_1.s:4258: bl reloadCurNaviStatBoosts_813c3ac
reference/bn6f/asm/asm00_1.s:4569: bl reloadCurNaviStatBoosts_813c3ac
reference/bn6f/asm/asm00_1.s:4667: bl reloadCurNaviStatBoosts_813c3ac
reference/bn6f/asm/asm00_1.s:4703: bl reloadCurNaviStatBoosts_813c3ac
reference/bn6f/asm/asm00_1.s:4742: bl reloadCurNaviStatBoosts_813c3ac
... and cutscene sites asm28_0/33/36/asm03_1_0 ...
```

NONE of these is battle init. The chain runs from map/boot/cutscene
sites, before any battle state was captured. T110 measured on the
battlestart.state capture: `peek 0x020047cc:0x64 @f5` reads CustomLevel
4, MegaLevel 5, GigaLevel 5, BLeftAbility 0xff, everything else 0 -- the
handlers already ran pre-state.

The battle copies (eBattleNaviStats0 0x0203F4AC -> 0x0203CB10 ->
0x02034A60 -> 0x0203C9E4) are zero through the window; T110 found no
in-window writer. FstBarr control poke at 0x020047d2:0x0001 vs no-poke
over 40 frames: 0 differing pixels -- confirming the battle never reads
slot 0x6 (FstBarr) either, and by the same slot-not-read mechanism,
nothing reads slot 0x23 (SuperArmor) on this route.

A SECOND inspection of asm00_2.s:12300-12325 confirms what *might* read
SuperArmor: JumpTable8014550, indexed by
`GetBattleNaviStatsByte_AllianceFromBattleObject(0x2c)`. That offset
0x2c is in `eBattleNaviStats0`, and it is the BLeftAbility slot (a
halfword before SuperArmor's slot 0x23). The table does include
`SetObjectSuperArmorFlag+1` at index 9, but the dispatch key is
BLeftAbility, not SuperArmor itself. So slot 0x23 (SuperArmor, the
NCP_SuperArmor write target) has no on-route consumer even at this
level.

## Conclusion (what the implication is for T150)

The ticket's port can be written: `src/navicust.rs` with a one-line
dispatcher that, given a `give_pet` list containing the chosen NCP id,
writes the slot. The wireup at BattleStart is a small Battle::new hook
or a flag-check in update(). That is mechanical.

But the acceptance criterion is a non-blind `ncp_row` at 0/0/N. To be
non-blind, the harness must detect a non-zero diff between the
with-NCP-given scenario and the without-NCP-given scenario. Both
scenarios go through the same battle window. Nothing on the battle
route reads slot 0x23 in either scenario. So:

- Canon (with NCP given): handlers ran pre-state; slot 0x23 may or may
  not be 1 depending on the pre-state history; battle does not read
  it; pixels unchanged.
- Canon (without NCP given): same handlers ran pre-state with no NCP;
  slot 0x23 = 0; battle does not read it; pixels unchanged.
- Rust (with NCP given, our port calls apply_chain): slot 0x23 = 1 in
  our model; battle does not read it; pixels unchanged.
- Rust (without NCP given): slot 0x23 = 0; pixels unchanged.

Pixel diff between with and without: 0 on both sides. The harness
negative would read 0; the row would be BLIND by construction -- the
exact failure mode T110 closed on and the supervisor's q4 decision
explicitly ruled out as a row.

The port itself does land M7 SCOPE 0/19 -> 1/19 if it runs against
a real-game check (the field at slot 0x23 of the master record IS set
correctly when our port's apply_chain runs). But the harness-visible
acceptance gate cannot be cleared on this route without widening:
either (a) we make our port visibly diverge from canon (write to
eBattleNaviStats copies that canon doesn't), or (b) we find an
in-battle reader of slot 0x23 we don't yet see. (a) is forbidden by
the do-not-widen rule; (b) is an open question that needs supervisor
sign-off because it changes the SCOPE denominator shape.

## Step 4 -- what I did not do (and why)

- I did not create `src/navicust.rs`. Writing the handler + a
  dispatch hook that does not move any harness-visible number is
  fitting code: a constant arrived at by trying values rather than
  reading the disassembly into the existing rust model. The
  AGENT_GUIDE rule is: cite every byte in the handler and the chain;
  write the field it stores. I CAN cite them. I CANNOT cite a
  consumer that sees the field on the battle route.
- I did not add `ncp_row` to `tools/harness.py`. A BLIND-by-construction
  row is the explicit failure mode the supervisor ruled out (T110
  q4).
- I did not edit `tools/states.py` to add `ncp_full`. The state recipe
  needs the EVENT_poke that arms the chosen-NCP-given path; without
  the row, there is no consumer for the state.

## Ideas tried / considered

- "Give the NCP pre-state, so the slot is already set when the state
  is saved." -- this is what the EVENT_poke shape would do (similar to
  T87's EVENT_681 swap). But T110 measured that even a direct poke to
  the slot value (0x020047d2 = FstBarr) does not produce a single
  pixel of diff over 40 frames. The pre-state approach is mechanically
  possible, the resulting row is BLIND for the same reason.
- "Re-dispatch applyNavicustPrograms in BattleStart in our port, and
  rely on the supervisor accepting a port that diverges from canon's
  per-frame battle behaviour." -- forbidden by the do-not-widen rule
  AND forbidden by the AGENT_GUIDE 'cited and verified' rule (canon
  doesn't do this on the route, our port would).
- "Add a state-only diff to the harness for this row." -- the harness
  diffs pixels; adding a new diff axis is widening tools/harness.py,
  out of scope for this ticket.

## What would unblock T150 (not done here, out of scope)

- The supervisor's sign-off to land the port without a row, on the
  reasoning that M7 SCOPE 1/19 reflects a handler implementation
  rather than a measured visible behaviour (the same shape as T110's
  PARTIAL).
- A measurement that finds an in-battle consumer of slot 0x23 (or
  another handler slot) -- a per-frame SuperArmor poke on a
  battle-active enemy and a 200-frame capture that shows a non-zero
  pixel diff. None of this ticket's scope.
- A separate "navicust-state diff" row axis: add to the oracle
  block a 19-byte or 0x64-byte navicust-slot digest and have
  oracle.py diff that. Would need new fixture fields, a new oracle
  layout, and supervisor approval -- widening.
