## Step 2 — the rule, re-derived from the ROM (cites verified on disk)

`playerFlinchAction_80174FE` (asm00_2.s:18300-18378): entry writes Timer=0x17 (0x0801757C,
`strh` asm00_2.s:18349) then the SAME-frame `loc_8017582` decrement (0x08017586, `sub`+`strh`
asm00_2.s:18353-18355) -> 22; every frame after decrements; on underflow (Timer<0) it sets
CurAnim=0 / CurAction=0x08 / phase=0 (asm00_2.s:18358-18364) and **leaves Timer at 0xFFFF** —
the handler is then never dispatched again (CurAction is 0x08), so nothing rewrites the sentinel.

Writer census (`grep -n oBattleObject_Timer reference/bn6f/asm/*.s`, enclosing functions via
awk over `thumb_func_start`):

- **Player-object writers** (the 0x0203a9b0 slot): the flinch handler above;
  `playerDeleteAction_80173F4` (asm00_2.s:18247); `RunSpawnAnimationMaybe_8016380`
  (asm00_2.s:16097, 16250); `sub_80165C2` (16454); `sub_80170C4` (17875, a phase dispatcher:
  battle_isPaused gate, then CurPhase-indexed table [sub_80170E4, enemyNaviDeathBlink_8017122]);
  `sub_80171A6` (17977, same shape, 3-entry table); `sub_80178B6` (18812, 18888);
  `sub_801483C` (13436, 13697, 13955, 13977 — a CurState-indexed dispatcher at 0x20367F0).
- **Other objects' writers** (their own slots, irrelevant to the navi's +0x20): the t1_0x*/
  chip-object routines (asm31.s), airspin/bass/cornfiesta/dollThunder/eraseBeam/riskyHoney/
  snakearm/trap objects, battle_BDT_main etc.

Which can end the hold: any of the player-object writers above **can** — a new flinch (entry
writes 0x17), a delete, a re-spawn, or an entry through the phase dispatchers (e.g.
enemyNaviDeathBlink) or sub_801483C's table. In battle_full's compared window NONE does: T63's
67-store watch-write table has no store to 0x0203a9d0 after canon frame 303 (k=292), and the
player idles (CurAction 0x08) to k=539. **The hold is open-ended within the trace** — 248
frames measured, k=292..539.

Canon cross-check that non-flinch actions do NOT rewrite Timer: the k=250 chip-use entry
(useChipFromHand_800FB54) stores CurAction only; no Timer store in the whole chip episode
(T63 table), i.e. the sentinel would persist through a later chip use too. Our export must
therefore hold the sentinel across Idle/Attacking/Recovering, and only the flinch entry (our
`Action::Flinching` arm, `ticks`) or a delete/spawn-class writer should replace it. Our model
has no player-side Timer writer other than the flinch, so the sentinel is cleared by nothing.

## Step 3 — the change (src/actor.rs only)

- `post_flinch: u8` (11-frame fitted countdown) -> `timer_holds_sentinel: bool`.
- `POST_FLINCH_FRAMES` deleted; `TIMER_SENTINEL: u16 = 0xffff` with a canon provenance tag
  (asm00_2.s:18355 underflow + measured hold k=292..539, T63 store table).
- Flinch-exit arm sets the flag; export returns `ticks` while Flinching, the sentinel while the
  flag is set and the action is not Dying/Gone (canon's delete writes its own countdown,
  asm00_2.s:18247 — out of our modeled scope, kept exporting 0), else 0.
- Doc block for the Timer export and the battle.rs oracle-field comments updated.

Predicted effect: NONE of the 7 guard rows should move — NOT because the flag is never set
(it IS set: the mettaur row's harness note has MegaMan hit mid-attack-1 on BOTH sides, ours
at battle frame 177, so its player flinches), but because the harness rows compare PIXEL
diffs only: verify_rows' row-result line carries total/worst/frames/negative, and oracle RAM
fields such as mm_timer are not in any row's compared region — no row could move regardless.
battle_full's mm_timer cannot drop below 270 because rust's player is never hit there
(T63 gap 2). This is a model-quality change, observable only once the hit lands.
