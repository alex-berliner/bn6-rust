# T231 — windowclose is red on main: reclaim the boot frame the T216 landing lost

Base: main a06d14e, worktree /tmp/bnwt/t231, branch wt/t231,
`export CARGO_TARGET_DIR=/tmp/ct_t231`.

## Why (from the ticket + T230)

`windowclose` reads 63962/3557/40/266037 on main; it read 0/0/40/207166 when T220
landed (0033d2d). The drift entered main with T216's landing (f440247, pad 25->21).
T230 proved the drift predates T230 and is byte-identical on main and the merged
tree; T230 also measured pad 25 on the merged tree -> still 63962/3557/40, so the
pad value alone was already suspect. T220's butterfly mechanism: a Battle-field /
code-layout shift moves the marker's first appearance one capture frame later
(origin 8 -> 9), and windowclose's script-timed Start@230/A@260 presses desync
from battle time. T231's job: reclaim the boot frame so windowclose returns to
0/0/40/207166 WITHOUT moving cursor off 1/1/170/186279.

## What the marker phase means (one line)

The harness aligns every row on BATTLE_MARKER's first "BATT" appearance, but
windowclose's presses are script-timed at fixed capture frames, so whichever pad
value puts that first appearance on the same capture frame as T220's tree
re-syncs the presses with battle time; 21 puts it one frame off.
