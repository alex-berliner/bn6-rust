## What canon actually does (the cites)

`isBannerBusy_801E754` (reference/bn6f/asm/asm00_2.s:31105-31131, 44 bytes):
- r0 = 0 when `eStruct2035280.HudElementMask & 0x8000` is clear (mask bit 15 off — banner
  RECORD done; SEQ_04 advances).
- r0 = 1 when mask bit 15 set AND NOT (byte_2036848 in {2,4} AND byte_2036840 == 4) (busy).
- r0 = 2 when mask bit 15 set AND byte_2036848 in {2,4} AND byte_2036840 == 4 (record idle
  but mask still set — handler treats this as busy too: cmp r0, #0 / bne).

Called from `bannerSeqState04BannerWait_8008064` (asm00_1.s:10569, the BANNER_WAIT handler,
entry of which calls `spawnBannerRecord_801E792` at :10567).

Our port: `is_banner_idle(&self) -> bool { !self.hud_live || (self.banner.is_none() &&
self.banner_was_up) }`. The `!hud_live` arm is the mask-clear arm; the `banner.is_none() &&
banner_was_up` arm is the "record lifecycle done" arm modelled by the visual banner's
roll-up (after SCALE.len() = 58 frames).

## Cursor regression: T152c's 32 px and T162's fix

T152c ported `is_banner_idle` correctly (trace 40/40 still matched, sequencer first-div
none) but cursor regressed 1/1/170 → 32/31/170. Cause: `banner_at = BATTLE_START_AFTER_WINDOW
= 30` (the 30-frame pre-banner delay set when the chip window closes) shifts the visual
banner's spawn from "SEQ_04 age 0" to "SEQ_04 age 27", and its roll-up from age 58 to age
85 — the model now waits for the visual roll-up rather than the record-idle at age 60.

Fix per T162: at SEQ_04 entry, set `banner_at = 0` (no pre-banner delay) AND spawn the
banner directly. Visual banner up at SEQ_04 age 0, rolls up at age 58. `is_banner_idle`
becomes true at age 58 — 2 frames off from canon's 60 (the explicit tolerance).

## Plan

1. Add `banner_was_up: bool` to Battle struct, init `false`.
2. Add `is_banner_idle(&self) -> bool` method on Battle.
3. Set `banner_was_up = true` at every banner spawn site:
   - end-of-battle banner (ENEMY_DELETED / MEGAMAN_DELETED)
   - per-frame BATTLE_START banner spawn from banner_at countdown (legacy path)
   - new SEQ_04-entry direct spawn
4. In the SEQ_00 → SEQ_04 transition, spawn the banner directly + set banner_was_up.
   Keep `opened = true` set at the window-close site (still used by the ENEMY_DELETED
   guard at line 3662).
5. Replace `SEQ_04 if self.seq.age >= SEQ04_FRAMES - 1` with `SEQ_04 if self.is_banner_idle()`.
6. Remove `SEQ04_FRAMES` constant.

## Trade-off (the cursor vs windowclose mismatch)

T152c's fitted `banner_at = 30` delayed the visual banner's spawn to SEQ_04 age 27. The cursor
test's 170-frame window covered the banner's roll-up at age 85 — a 32-px diff. T162's fix
spawns the banner at SEQ_04 age 0 (banner_at = 0 at SEQ_04 entry), so the banner rolls up at
age 58 and cursor is mostly restored.

But the windowclose test's 40-frame window (rust frames 253..292, canon 81..120) ENDS BEFORE
canon's own SEQ_04 entry (canon k=136, per T152a). With the fitted constant, banner spawn was
at rust frame 290 — only 3 frames of overlap with the windowclose window. With the T162 fix,
banner spawn is at rust frame 264 — 29 frames of overlap, with a fully-grown banner visible
on most of them. Canon shows no banner during the windowclose window (SEQ_04 hasn't been
entered yet in canon at canon frame 120), so the rust banner is now a real regression.

Both fixes are correct under canon's mechanism: `spawnBannerRecord_801E792` runs at SEQ_04
entry (asm00_1.s:10567), the banner record's lifecycle begins then. The fitted constant was
hiding this from the windowclose test by accident; the T162 fix surfaces it.

A clean resolution needs a separate banner-record lifecycle counter (60 frames, decoupled
from the visual banner's 58 frames) — see the T152c worklog's "options (b) and (c)" note.
That is out of scope for T162 (the ticket names only "set banner_at = 0 when SEQ_04 enters").
