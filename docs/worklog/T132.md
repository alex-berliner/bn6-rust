## Step 1 -- the chain, read from the instruction stream (no build)

The ticket's cited chain had one gap; the real setter is found and cited below.

1. **Stat byte.** `u8 SuperArmor // loc=0x23` (include/structs/NaviStats.inc:30). In EWRAM the
   battle-side NaviStats for alliance 0 is `eBattleNaviStats0` = **0x0203ce00**
   (ewram.s:3109; `GetBattleNaviStatsAddr` asm00_2.s:10159 = `oNaviStats_Size*alliance +
   eBattleNaviStats0`), so the byte is **0x0203ce23** (peeked, T123's base confirmed by
   `GetBattleNaviStatsAddr`'s own pointer word -- the base is no longer only peeked).
2. **NaviCust handler.** `navicust_NCP_SuperArmor` (asm37_0.s:2168-2177):
   `SetCurPETNaviStatsByte(0, 0x23, 1)`; jumptable word `navicust_jt_NCPs`+4 at asm37_0.s:2113;
   also called from `navicust_NCP_BodyPack` (asm37_0.s:2537).
3. **PET -> battle copy.** `init_8013B64` asm00_2.s:10956-10958:
   `ldrb r0,[r6,#1]; mov r1,#oNaviStats_SuperArmor; strb r0,[r7,r1]` (the ticket's "stat read"
   cite -- it is the battle-init copy, not the flinch gate).
4. **Stat -> object flag (THE site the ticket could not name).** `sub_801393A`
   (asm00_2.s:10629, called from asm00_2.s:10843 and asm03_0.s:15311): at **asm00_2.s:10681-10691**
   `mov r0,#1; lsl r0,r0,#0x11` (= 0x20000), `mov r2,#0x23; ldrb r1,[r6,r2]; tst r1,r1;
   beq -> object_clearFlag / object_setFlag1`. The offset is in **r2** (`ldrb r1,[r6,r2]`), not
   r1, which is why a grep for `mov r1,#0x23` + `bl GetBattleNaviStatsByte` finds nothing --
   sub_801393A reads the NaviStats base directly (r6 from GetBattleNaviStatsAddr at :10631-10633).
5. **The flag bit is NAMED, not unnamed:** `OBJECT_FLAGS_SUPERARMOR 0x00020000` /
   `OBJECT_FLAGS_SUPERARMOR_BIT 17` (include/structs/CollisionData.inc:20,38), stored in
   `ObjectFlags1 // loc=0x3c` (CollisionData.inc:145) via `object_setFlag1`
   (asm00_2.s:21629-21636: `CollisionDataPtr->ObjectFlags1 |= bit`). The player's CollisionData
   in the mettaur-route battle is 0x020384f0 (watched CollisionDataPtr 0x0203aa04), so the flag
   halfword is **0x0203852e** and bit17 is the value **0x0002** there.
   NOTE: the ticket's other cite, the jumptable word at asm00_2.s:12322 (`JumpTable8014550`,
   reached from `sub_8014536` reading byte **0x2c**), dispatches on the **Transformation** byte
   (NaviStats.inc:36), not SuperArmor -- entry 9 grants super armor to a transformation. It is a
   second writer of the same flag, not the NCP path.
6. **Reader list (hit/flinch path).** The only reader of ObjectFlags1 bit 17 in the hit path:
   `sub_80178D4` **asm00_2.s:18758-18767** ("on push" init, jumptable entry 5 = `sub_80178B6`
   asm31.s:107220, dispatched on `Unk_0d`): `bl object_getFlag` (asm00_2.s:21655, reads
   ObjectFlags1) then `tst r0, 0x20000` -> `CurAnim = 0` (super armor) vs `= 1` (flinch anim),
   bit 0x800 -> 2. Other writers of the bit: asm00_2.s:12415 (Airshoe wrapper sibling),
   12464/12474, 12612/12626/12661/12671 (transformation wrappers), 17731; a CLEAR site:
   `sub_8014080` asm00_2.s:11644-11654 (clears flag + zeroes stat 0x23 when NaviIndex==0).
   A different word entirely: `object_spawnHiteffect` (object.s:5904-5908) gates the hit spark
   + sound 0x6e on `oCollisionData_FlagsFromCollision` (+0x70) & 0x20000 -- the incoming hit's
   flags, NOT the victim's ObjectFlags1, so the NCP flag does not gate the spark (unverified
   beyond the read; see UNVERIFIED below).

**What super armor does not suppress (from the instruction stream + measurement):** damage.
`object_subtractHP` (object.s:4678-4690; hit dispatcher `sub_801B394` calls it at
asm00_2.s:24067 with white flash + sound 0x85 at :24057-24066, all before any flag test) runs
unconditionally. Knockback IS suppressed with the action: measured below -- with the flag set,
CurAction never leaves 08, so `playerFlinchAction_80174FE`'s panel move (asm00_2.s:18311+)
never runs.

## Step 2 -- the lever, measured (this killed the ticket's premise)

Canon = /tmp/bn6f_sterile.gba, loadstate /tmp/pausedwithcannon.state, script "Start@10"
(the mettaur row's own route), MegaMan's object 0x0203a9b0 (HP +0x24 = 0x0203a9d4 watched,
CurAction +9 = 0x0203a9b9, Timer +0x20 = 0x0203a9d0), 180 frames:

- Control (no poke): **HP 60->50 at frame 114, act 08->03 (flinch) at 114, timer 0x16=22 at
  114**, act 3->08 at 137 (timer 0xffff = readout artefact of the watch, the flinch lasts the
  0x17=23 frames FLINCH_FRAMES names; recovery at 137 = 114+23).
- Stat-byte poke `--poke-at 40:0x0203ce22:0x0100` (halfword, see below): byte 0x0203ce23
  verified = 01 from frame 40 through 90 (watch), and **nothing changed: same HP drop at 114,
  same flinch 08->03 at 114**. The stat byte is consumed at battle init only (site 4 above runs
  at init), so a mid-battle stat poke is dead. **The ticket's "one-poke lever" is wrong for any
  route whose battle already started (the PAUSED-state route included).** It would only work
  poked before battle init.
- Flag poke `--poke-at 40:0x0203852e:0x0002`: **HP 60->50 at frame 114, act STAYS 08, timer
  stays 0** through frame 180. THE suppression frame is canon frame 114: damage lands, flinch
  does not. This is the measured rule and the port's target behaviour.

Tooling trap that cost three captures: `--poke 0x0203ce23:0x0001` (odd address, "at load") is
invisible -- loadstate runs after the poke, and `--poke-at` writes a **16-bit value**, so an odd
address lands on the aligned pair; 0x0203ce22:0x0100 is the working form for byte 0x0203ce23.
`--watch-write` armed on 0x0203ce23 saw no write mid-battle, consistent with init-only
consumption.
