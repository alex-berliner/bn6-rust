## Step 4: diagnose which byte caused the regression

`git diff main..4869370 -- src/battle.rs` shows T38's branch CHANGED FIVE THINGS:

1. Added `CANNON_FAMILY: u8 = 0x14` const next to `SWORD_FAMILY` at :1623.
2. Added `CANNON_BARREL_DX/Y` consts (already existed; just relocated).
3. **use_chip Cannon arm** — early-return `if chip.family == CANNON_FAMILY { ... return; }` placed BEFORE `match chip.id`. Body is byte-identical to the old `CHIP_CANNON|HICANNON|MCANNON` arm EXCEPT: barrel palette `(chip.id - CHIP_CANNON)` -> `chip.subfamily`. For ids 1/2/3 subfamily is 0/1/2, same as `id-1` -> **functionally equivalent**.
4. **chip_strike Cannon arm** — early-return `if chip.family == CANNON_FAMILY` placed AFTER the sword early-return, BEFORE `match chip.id`. Body is byte-identical to the old id arm (no chip-id literals anywhere).
5. **REVERTED Barrier port**: T48's `barrier_hp(chip: &Chip)` and `barrier_palette(chip: &Chip)` taking `chip.params[0]` REPLACED by `barrier_hp(id: u16)` and `barrier_palette(id: u16)` doing `match id { CHIP_BARR100 => ..., CHIP_BARR200 => ... }`. Also the body of the bubble dispatch (`_ => { if chip.family == BARRIER_FAMILY && chip.subfamily == BARRIER_SUBFAMILY { ... } }`) was REPLACED by an explicit `CHIP_BARRIER | CHIP_BARR100 | CHIP_BARR200 => { ... }` arm.

**THE LIKELY CAUSE: change 5 (Barrier revert)**, not the Cannon port.
The cursor scenario's deck is `[5, 4, 71, 54, 1]` (Vulcan, AirShot, Sword,
MiniBomb, Cannon). Cannon is the LAST card the cursor highlights. The cursor
walk itself doesn't fire use_chip or chip_strike, so changes 3 and 4 cannot be
triggered during the cursor walk. Change 5 only affects ids 178/179/180 (Barrier
family), which are NOT in the deck — so the direct barrier code path can't fire
either.

So the regression must come from how the rust build READS chip data via
`Chips::get(...)` for any of the deck chips. The card picture/icon blob offsets
in the v2 asset come from the RECORD, not the TAIL — only the TAIL changed in
shape when T19 was added, and the v1 blob pointers are byte-identical (T19's
"append-only" rule). This means the picture/icon blobs at any chip id are byte-
identical pre/post T38 — confirmed: `assets/chips.bin` sha256 is the same on
main and 4869370 (`b7f864ea...`).

**The remaining suspect is the early-return placement itself.** Changes 3 and 4
are byte-equivalent for ids 1/2/3 (Cannon) — but the Rust optimizer may have
re-ordered or coalesced the `match chip.id` arms differently when the early-
return is added above. T38 worklog reports chip-cannon 0/0/40/9505 etc., which
proves the cannon path is correct. But Rust may have lifted code out of the
Cannon arm into a sibling arm now that the structure differs.

**Direct fix candidates (not run):**
(a) Move the early-return INSIDE the `match chip.id` arm for ids 1-3 instead of
    above it — keeps the existing layout and just renames the dispatch key.
(b) Use `matches!(chip.id, 1..=3)` as the early-return guard instead of
    `chip.family == CANNON_FAMILY` — keeps the id-keyed check (same shape as
    T38's old arm) but still gets the family constant into the code.
(c) Revert the barrel-palette change: keep `(chip.id - CHIP_CANNON) as usize`
    as T51 step 5 hints ("no barrel palette change").
