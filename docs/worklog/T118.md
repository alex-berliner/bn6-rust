## Step 2 — chunk census (instrumented scratch build)

Method: temporary edit of `copy_tiles` comparing shadow vs VRAM per 32-byte
chunk, accumulating per-BATTLE_MARKER-frame counts into a `#[no_mangle]`
static (T118_CENSUS, nm'd at 0x020002e8), read with mgba_capture --watch
(6144 B/frame, 450 frames, cursor scenario). The marker frame counter at
0x02000004 does NOT advance in the custom-screen scenario (it is the battle
loop's own frame), so all copies accumulated into one slot — the cumulative
curve still gives per-event deltas; per-frame attribution comes from which
marker frames the jumps land on.

Numbers (32-byte chunks; one 32x32 screenblock map = 2048 B = 64 chunks):

- Construction/initial sync: 337 chunks total over frames 8-15 (bg
  construction + first draw).
- Steady state: 0 chunks changed between content changes.
- Each of the five cursor moves (marker frames 252/282/312/342/372):
  **+22 chunks (~704 B), in ONE dirty-background commit call** (cumulative
  commit calls 38 -> 39 -> 40 -> 41 -> 42).
- Whole 170-frame window: 5 commit calls; today's whole-screenblock copy
  would write 5 x 64 = 320 chunks (10240 B); changed-only writes 110 (3520 B).

Cycle estimate (assumptions: VRAM 16-bit bus 0 ws -> 2 cycles/32-bit seq
write; EWRAM 16-bit bus 2 ws -> 6 cycles/32-bit read; 1232 cycles/scanline;
vblank budget 76704 per ticket):

- Whole-screenblock copy (today): 512 words -> ~1024 VRAM write + ~3072
  EWRAM read ≈ **~4100 cycles ≈ 3.3 scanlines per dirty background** — fits
  inside vblank with huge margin. The coverage doc's "always spills past
  vblank" is WRONG at 32x32 map sizes; the seam was never vblank overflow.
- Changed-only copy: compare all 64 chunks (~3072 EWRAM + ~1024 VRAM read
  cycles) + write 22 chunks (~1400) ≈ **~5500 cycles** — also fits.

**Verdict: a changed-chunk-only copy fits inside vblank on every one of the
170 frames (worst frame ~5.5k of 76.7k cycles).** The class was never about
vblank budget; it is phase alignment with canon's own writes.

## Mechanism (one line)

Canon writes changed tile content MID-FRAME (visible scanlines); the whole
screenblock copy's ~3.3-scanline duration (plus T111's pad) happened to land
our changed chunks at canon's phase, and that alignment is what the ≤1/1/170
class was; a content-driven copy at vblank is ~3 scanlines earlier and every
content-change frame reads its full changed region.

## Step 5 — three-footprint stability: NOT RUN
