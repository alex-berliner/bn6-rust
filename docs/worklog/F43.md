## Step 3 — the guard predicate (asm00_1.s read in full)

The ticket's hypothesis (a guard around the call at asm00_1.s:9790) is
CONFIRMED but the guard is NOT the battle-state word itself. Exact chain, from
asm00_1.s:9727-9800:

- `battle_update_8007A44` (asm00_1.s:9727) is the handler battle_main_8007800
  runs while `oBattleState_Index_00` ([r5,#0]) == 4 — the fight state. The
  intro's own states hand over to it only via `sub_8007A0C`'s
  `mov r0,#4; str r0,[r5,#oBattleState_Index_00]` (asm00_1.s:9716-9718), which runs
  after the intro's clear/panel/decompSprites work. While the intro states run,
  the fight handler — and with it the whole per-frame chain — never executes.
- Inside the fight handler:
  - `bl eStruct203F7D8_getUnk01` (asm00_1.s:9730). If the byte == 4, the
    handler checks `eStruct200BC30_getRef()[0xe]` and either leaves to state
    0x10 or 0x0C — the chain is skipped.
  - otherwise `bl dispatch_801FEEE` (:9753), then `mov r0,#8; and r0,r4;
    bne loc_8007B10` (:9753-9756): if `getUnk01() & 8`, the whole chain is
    skipped (F44 CORRECTION: this is a battle/transition-state test, not
    the "chip-window suppress" this note first called it — decomp
    asm01.c:63-79 writes 2 and 4 into that word and the bit-3 tests are
    asm01.c:71 and :78, and asm00_1.s:9755's `and r0,r4`;
    asm00_1.c:11121 tests bit 1 only, `if (!zf &&
    !(eStruct203F7D8[1] & 2))`; the HUD-element clear itself is
    decomp asm03_0.c:801-805).
  - then `bl eStruct2038160_getBattleTerminate01` (:9757); nonzero sets
    setTwoStructs(9/10) and `*v0 = 16` — chain skipped, fight over.
  - only then the chain: sub_800A01C, GetBattleMode jumptable
    (JumpTable8007B50), RunBattleObjectLogic, camera_802FFF4, panel_800BFC4,
    setChipsForPlayerObjects_800FDC0, **updateBattleHudElements_801BEE0**
    (:9790), sub_802CEC8, handleVariableDamageChip_800AEE8.
- Note the ORDER: `oGameState_BattlePaused` / `battle_isTimeStop` are checked
  AFTER the chain (:9795). Pause does NOT gate the HUD chain — the digits
  keep updating while the fight is paused. So the intro absence is purely the
  state machine (canon is not in state 4 during the intro), and the banner
  wait (our SEQ_04, sub_8008064 asm00_1.s:10386) is equally pre-fight.

Frame range canon holds the gate closed in the opening row: the whole compared
k=0..39 (canon frames 120..159; the fight state arrives only after the banner,
canon's chip window opens at 165 and BATTLE START! goes up ~289 in the
unscripted flow).

## Step 4 — implementation

src/battle.rs, next to `draw()`: new `fn hp_readout_live(&self) -> bool` —

```rust
self.intro_fade == 0
    && self.intro_next >= self.enemies.len()
    && !(self.banner.is_some() && !self.banner_done)
    && !matches!(self.seq.state, SEQ_0C | SEQ_10)
```

and the per-enemy emission loop's filter gains `&& hp_readout_live` (computed
once before the loop). This is the modelled form of canon's guard: the
`intro_fade`/`intro_next`/`opening` terms are the same terms update()'s
`paused` carries for "not yet in the fight state", and `SEQ_0C | SEQ_10` is
our `over` = canon's `getBattleTerminate01() != 0` arm. No window
(`custom`/`presenting`) and no `gauge_pause` term: canon's pause check runs
after the chain, so a paused fight still draws digits — adding those terms
would HIDE digits canon shows.

Deviation from the ticket's file list: the gate is a Battle-state read, not a
per-actor predicate, so it lives on `Battle` in src/battle.rs instead of a new
method next to `is_targetable` in src/actor.rs. src/actor.rs is untouched —
the actor-level conditions (is_present/hp>0/is_targetable) were already
correct and stay in the filter.
