# T28 — Chips as data, second arm: Recov / Barrier / Vulcan — NEGATIVE, nothing converted

## Outcome in one paragraph

The ticket's premise — "the record already carries all of it" — is **falsified by the ROM
bytes**. For all 15 named chips the amount each arm needs (heal amount, bubble HP, shot
count) is **not in the chip record**: `AttackPower` (+0x1a) is 0 for every Recov/Barrier
chip, and `AttackParam1..4` (+0x10..0x13) never equal an amount. The amounts live in three
EXTERNAL tables the src symbols already cite:

- `RecovHealBySubfamily_80EC870` (byte_80EC870): u16s `[10, 30, 50, 80, 120, 150, 200, 300,
  1000]` — verified in ROM at file offset 0x0EC870 (bytes `0a 00 1e 00 32 00 50 00 78 00 96
  00 c8 00 2c 01 ...`). The src `RECOV_HP` literal is byte-faithful to it.
- `BarrierHpByType_8020B2C` (data/dat01.s:194, not :189 — see cite drift below): stride-6
  rows whose first u16 is the HP; row 1 = 0xA, row 5 = 0x64, row 7 = 0xC8 — matching the
  record's `AttackParam1` 1/5/7 for Barrier/Barr100/Barr200. The src `BARRIER_HP=10 /
  BARR100_HP=100 / BARR200_HP=200` literals are faithful to it.
- `VulcanShotsBySubfamily` (dword_80EBFEC): bytes `[3, 4, 5, 10]` (0x0A050403) — verified in
  ROM at file offset 0xEBFEC. The src `VULCAN*_SHOTS`/`SUPRVULC_SHOTS` literals are faithful.

Per the ticket's own rule ("no fix-up table may be introduced to bridge a mismatch — report
the mismatch per chip with both numbers") and step 3's gate ("only for values step 2 proves
equal"), **no code was changed**. This is the NEGATIVE the acceptance text explicitly
accepts: "A NEGATIVE that a mismatched ROM byte contradicts a measured literal is accepted
and becomes the list T29 works from."

Structural notes for T29:
- The Recov id-index `chip.id - CHIP_RECOV10` happens to EQUAL the record's own
  `AttackSubFamily` byte (0..7, verified above) — the canon table byte_80EC870 is
  subfamily-indexed. Switching the index would delete no literal and read no amount from the
  record, so it was not done (ticket: only values proved equal convert).
- Same for Vulcan: dword_80EBFEC is subfamily-indexed (4 entries, sub 0..3).
- Barrier: `AttackParam1` (1/5/7) is the canon index into BarrierHpByType_8020B2C — but that
  table (stride 6: HP u16 + 4 bytes, 0xFF/0xFFFF sentinels) is not in the record and not in
  assets/chips.bin; converting would need either a new export (forbidden) or a copied table
  (a fix-up bridge, forbidden).
- Vulcan timing table (VULCAN*_TIMING :525-528) is `peeked` measurement, indexed by shot
  count, not chip id — untouched, not a chip-id index.
