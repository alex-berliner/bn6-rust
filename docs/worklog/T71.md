## Step 2 — the recipe stream, decoded from the ROM itself

Parser ground truth: `/tmp/bn6f_real.gba`, file offset = addr − 0x08000000. Final numbers:

- `off_802BC60` (PARecipePtrsB) = **20 pointers**; `off_802BCB0` (PARecipePtrsA) = **43
  pointers**. **They are sequential, not parallel**: B occupies 0x802BC60..0x802BCAC, A
  starts immediately at 0x802BCB0 with **no terminator between them**; a single shared
  `.word NULL` at **0x802BD5C** ends A (asm03_0.s:11547). A NULL-walk started at B runs
  63 entries (it runs straight through A's).
- Record layout (confirmed against the asm, not the ticket's byte-guess):
  `[count u8][matcher u8][result u16 LE][ingredient u16 LE]×count`.
  - The **matcher byte is an unscaled byte OFFSET into PAMatchers_80295C0** (asm03_0.s:6700
    `ldr r0, [r1,r0]` — Thumb-1 register-offset LDR does not scale): 0 → `paMatchCodeId_80295C8`,
    4 → `paMatchExact_802961A`. Data carries only {0, 4}: **30 records m=0, 33 records m=4**.
    (T10's old note "matcher=4 is an index" and "layout [count][matcher][result]" were both
    half-right; nothing indexes past the 2-entry table.)
  - Ingredient words are **pure chip ids** (id = word & 0x1ff; every word's code bits are 0),
    compared against the selection array that stores `word & 0x1ff` — so **codes never
    participate in the id match; byte1=1 simply means id+256** (Colonel 272, Colonel[SP] 274,
    Bass 301 appear as ingredients).
- `matchPARecipes_8029520` (asm03_0.s:6643–6735): unpacks up to 5 words (id=low 9 bits,
  code = word>>9) into ids@sp+0..9 / codes@sp+10..19, then slides a window (`r6 += 2`,
  remaining `r5 -= 1`, while `r5 >= 3`): per record, `count <= window-remaining`, then
  `PAMatchers[record[1]]` decides.
  - **m=4 paMatchExact** (asm03_0.s:6788): pair word == selection id word, count times. Ids
    equal, codes free.
  - **m=0 paMatchCodeId** (asm03_0.s:6737): ids equal, then the window's **codes must form an
    ascending consecutive letter run** (reads the window's LAST code as the unconstrained
    anchor, walks down, `expected-1 == actual` each step; '*' (0x1a) is a wildcard, at most 1
    (`cmp r2,#1; bgt fail`); final `expected >= 0` → minimum run A,B,C). Record code bytes are
    ignored by the matcher.
  - **The B table is dead data in this build**: the table-select flag `[sp+0x1c]` is written 0
    at entry (6647–6648) and never set; only PARecipePtrsA (43) is ever walked. B's single
    reference is the branch at 6679. Both tables' records are reported here regardless (the
    ticket's 63 = 20 + 43).
- Acceptance side: on a match, `sub_8029652` (asm03_0.s:6826) sets bit `(result − 0x140)` of
  `0x0203CA48 + param_2*4` — the per-battle/per-player "PA already performed" bitfield; a
  second recognition of the same PA returns 0 (rejected). Flag==0 path wraps with
  `sub_802963C` (asm03_0.s:6813): `SetEventFlag(0x1F60 + result − 0x140)`.
- Counts: **63 recipes**; counts {3: 62, 4: 1} (the 4-chip one: A[12] 0x802BAD8 =
  FireHit3+AquaNdl3+ElcPuls3+RskyHny3 → 0x15A); **190 ingredient slots over 90 distinct
  ChipDataArr ids** (id range 1..341); **30 distinct result ids 0x140..0x15D**.
- Naming (for humans): chip names come from TextScriptChipNames0.s for ids ≤ 0xFF and
  **TextScriptChipNames1.s with base 256** for ids > 0xFF — proven by canon's own
  `sub_8027D10` (asm03_0.s:3266–3292: `if id > 0xff` switch table, `Names1[id & 0xff]`).
  Results 0x140..0x15D = ids 320..349 = GigaCan1, GigaCan2, GigaCan3, WideBrn1..3,
  FlmHook1..3, PwrWave1..3, CornFsta, ParaShl, DestPuls, TimeBom+, StreamHd, SuprSpr,
  H-Burst, LifeSrd, GreatYo, PitHocky, PoisPhar, BodyGrd, DblHero, Darkness, MstrCros,
  SunMoon, TwinLdrs, +0x15D. Sample rows that pin the semantics:
  - B[0] 0x802BB98 `[3][4][0140] 1,1,12` = Cannon + Cannon + TankCan1 → **GigaCan1** (exact).
  - A[0] 0x802BA60 `[3][4][0153] 71,72,73` = Sword + WideSwrd + LongSwrd → **LifeSrd** (exact).
  - A[13] 0x802BAE4 `[3][0][0140] 1,3,321` = Cannon + M-Cannon + GigaCan2 → GigaCan1 with
    **ascending codes** (the m=0 chain-upgrade family, 30 records).

## Step 3 — canon's reader, named

- The site that runs at the custom screen: **`custMenuPressOK_8028D3A`**
  (`asm/asm03_0.s:5437`, `bl sub_8029110` at **5438** is its first instruction) — recognition
  happens on the **OK press**, not per pick (`addChipPick_8028D6C`, asm03_0.s:5497, does not
  call it and does not advance the cursor).
- `sub_8029110` (asm03_0.s:6029) zeroes `ePAScratch_2033000` (0x48 bytes), then calls
  `matchPARecipes_8029520` at **6132** with r0 = `eSelectedChipCodes_20366C0+0x32` =
  **0x020366F2** (the five picked-chip words, written per pick — verified live:
  `--watch 0x020366F2` reads `0001 ffff ffff ffff ffff` on chipselect.state with its one
  Cannon pick) and r1 = 0.
- **The store of the recognized result**: on match, `sub_80292CC` (asm03_0.s:6288) writes the
  result word into the selection scratch and shifts the remaining picks down; then
  `sub_802B6F2` (asm03_0.s:10881) rebuilds the hand buffer at **0x02036660**:
  `word_2036664 = result word`, selection words copied to `word_2036674..` until −1; the menu
  state byte `[r5+0xb] = 0x10` (asm03_0.s:6146–6148). Blank-picked-deck-slots
  (`sub_80293F8`) runs right after (5439).
- Predicate in words: "walk the picked chips as a sliding window (width 3, then any width the
  record asks while ≥ 3 chips remain); for each recipe whose count fits, if every window id
  equals the record's ingredient id AND (matcher 0) the window's code letters ascend by one
  with at most one '*', the recipe fires; the matched window's chips collapse into the result
  chip; each result may fire once per battle."
