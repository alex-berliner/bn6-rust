## Step 1 -- the six mechanism bullets, re-read against reference/bn6f

All six static reads re-done this session. Verdicts with file:line:

1. **sub_80178D4 is not the flinch gate -- AGREE.** asm00_2.s:18751-18772: after entry
   setup it calls `object_getFlag`, tests `1<<0xb` = 0x800 = OBJECT_FLAGS_PARALYZED FIRST
   (asm00_2.s:18766-18768), then `dword_8017A94 // =0x20000` (18769-18772), and the result
   is only a 0/1/2 selector stored to `oBattleObject_CurAnim` (`strb r2,[r5,#oBattleObject_CurAnim]`,
   asm00_2.s:18776) -- CurAnim is +0x10 (include/structs/BattleObject.inc:56), CurAction is
   +0x9 (:40). It never writes CurAction, so it cannot preserve an action id. It sits one
   slot after `playerFlinchAction_80174FE+1 // on flinch // 0x03` in off_80EA52C
   (asm31.s:107218 region; slot 5 "on push" is `sub_80178B6+1`, the next function, whose
   tail sub_80178D4 is). NOT ported as a gate.

2. **The hit-path readers test 0x220000 -- AGREE.** `sub_801AEB0` asm00_2.s:23403-23411 and
   `sub_801AF0E` asm00_2.s:23451-23459 both do `bl object_getFlag / ldr r1,dword_801AF40 //
   =0x220000 / tst r0,r1 / bne skip`, and only when the pair is CLEAR and
   `HitModifierFinal & 1` do they `object_setFlag2(4)` (the flinch-request bit this
   suppresses). dword_801AF40 = 0x220000 = OBJECT_FLAGS_SUPERARMOR 0x00020000
   (include/structs/CollisionData.inc:20, bit 17 at :38) OR OBJECT_FLAGS_ANGER 0x00200000
   (CollisionData.inc:24). My row measures the bit-17 (superarmor) route ONLY; the anger
   half is left unported and cited as such.

3. **The stat->flag copy is boolean -- AGREE, plus one ticket correction.** sub_801393A
   asm00_2.s:10630-10694: r6 = `GetBattleNaviStatsAddr(alliance)` (10631-10635); at
   10683-10691: `mov r0,#1 / lsl r0,r0,#0x11 (=0x20000) / mov r2,#0x23 / ldrb r1,[r6,r2] /
   tst r1,r1 / beq loc_80139BE(object_clearFlag) / bl object_setFlag1`. Gate is
   `stat != 0`, byte 0x23 of NaviStats. T132's "value * 0x20000" is refuted. Same routine
   copies bytes 0x1b/0x1c/0x1d to FLOATSHOE 0x20 / AIRSHOE 0x10 / UNDERSHIRT 0x40000
   (10656-10682). CORRECTION to the ticket: the `bl sub_801393A` at asm00_2.s:10843 is
   inside **sub_80139F6** (thumb_func_start asm00_2.s:10735), not sub_80139C4 (10698-10732).
   sub_80139C4 is a different function (the counter pink-ring spawner, called per-frame from
   the player update asm31.s:107175) whose HP!=0 / ActorType==PLAYER / AIIndex<=0xb /
   mood==2 gates I verified at 10700-10731 -- but it does NOT call sub_801393A. sub_80139F6
   instead gates on AIData event byte +0xa4 in {0x18,0x19,0x54,0xff,0xfe} and a stack word
   < 0x64 (asm00_2.s:10739-10846) and is reached from playerStateDispatch_801AC6C
   (asm00_2.s:23173), itself called per-frame from the player update (asm31.s:107160).
   Third caller: asm03_0.s:15311 inside sub_802D7A0 (battle-init navi-stats copy). So
   "battle init only" is indeed NOT established: sub_801393A re-runs mid-battle when the

## Row design (settled before coding)

- **Fixture field**: the 64-byte descriptor is FULL (bytes 0..63 all allocated; +62/+63
  carry enemy_state/panel_mask and enemy_action/emotion overlays whose enemy-override
  domains collide with a live Mettaur on this route), and the trace block occupies marker
  bytes 128..192. `super_armor: u8` therefore lives at **marker byte 192 = 0x020000c0**
  (first unused byte inside BATTLE_MARKER's 256, past the trace block, before agb's
  0x02000100). Read by src/fixture.rs, copied by src/battle.rs's Profile site, consumed by
  src/actor.rs's take_damage. Canon's byte 0x23 semantics: 0 = no armor.
- **Canon lever**: `--poke-at 40:0x0203852e:0x0202` on the mettaur canon side
  (STERILE+PAUSED+ALIVE+Start@10, --disable-bg), frame 40 per T132's measured-sticking
  frame, value 0x0202 per bullet 5. Control before believing anything: unpoked --watch of
  0x0203852c:4 / 0x0203a9b8:2 (CurState|CurAction<<8) / 0x0203a9d0:4 (Timer|HP) showing the
  flinch at canon 114, then the same capture with the poke showing CurAction stuck at 0x08
  and the flag word holding 0x0202 -- report both.
- **Row**: `super_armor`, mettaur route, `canon_ref=100`, `frames=70` (canon 100..169
  covers flinch 114..136 and recovery 137), rust offset search range(153,174) expecting
  ~165 (= mettaur's 205 - 40), event-paired not score-picked. Rust side = FIELD_ROW +
  `super_armor: 1`. Sides differ ONLY in the lever.
- **Negative**: the harness's own frame shift (automatic, must be non-blind) PLUS the
  behavior negative: same rust side vs canon WITHOUT the flag poke -- canon must flinch at
  114..136 (nonzero on the flinch frames, nonzero via the tested mechanism, not via drawing
  something else). The ticket's INVIS alternative (`0x0203852c:0x0002`) would make its
  nonzero by REMOVING the player sprite -- noted as the weaker control; not used as the
  primary negative for that reason.
- **Known risk carried in**: the mettaur row's own documented 4265/800 residue (departure
  spray, 8 frames, k={0,1,6,11,17,22,63,68} at canon_ref 140) may fall inside this window
  (canon 140..162 => k=40..62). If it does, the row cannot read 0 and lands as a bounded
  negative with per-frame numbers -- per the ticket, that closes it.
