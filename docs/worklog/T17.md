## Steps 3-4 — the append-only asset and the data-driven arm (2026-09-16)

First tried the tail inline (record stride 36 -> 44, 8 behaviour bytes packed
after the palette pointer). That regenerates every blob pointer u32 in the
first 36 bytes (all 48 records diffed) and shifts every blob by +384, which
breaks the ticket's own rule "existing offsets never move". Dropped it.

Landed layout: chips.bin v2 is byte-append-only at the file level —
- the v1 table (48 x 36) and every blob are untouched;
- version field 1 -> 2 (the only non-append byte in the file);
- the behavioural tail (48 x 8: effect_flags, attack_family, attack_subfamily,
  attack_param_1..4, lockout_frames) is appended after the blobs, in record
  order; src/chips.rs locates it as data.len() - count*8.

cmp of every record's first 36 bytes, old vs new asset: **diff count 0**.
Record stride 36 unchanged; the tail's stride is 8. Whole old file is a
byte-prefix of the new one except the version u32 at offset 4.

src/chips.rs: `TAIL` const (provenance: derived), tail offset in
Chips::new computed from data.len() - count*TAIL, guarded only by a bounds
assert; the version u32 at offset 4 is NOT checked, so a v1 asset read by
this code passes the assert and silently reads trailing blob bytes as
behaviour. New pub fields effect_flags/family/subfamily/params/
lockout on `Chip` (effect_flags/params/lockout `#[allow(dead_code)]` —
exported for later tickets, no arm reads them yet).

src/battle.rs: `chip_strike` now dispatches the sword family on the record's
attack_family (SWORD_FAMILY 0x13, canon) BEFORE the `match chip.id`, and the
eleven-id arm is deleted. Subfamily -> behaviour comes from two canon tables
copied from the asm data:
- SWORD_HIT_SHAPE (canon: SwordHitShapeBySubfamily_80EBA18, asm31.s:109334,
  word-indexed so the shape is each entry's first byte) with shape codes
  SHAPE_COLUMN 4 / SHAPE_TWO_AHEAD 2, default = the panel ahead;
- SWORD_ARC_ROW (canon: SwordArcBySubfamily_80EBAD8, asm31.s:109352), rows
  mapped to (animation, palette) via EffectObjectRows_80E0398: 0x16->(0,0)
  0x17->(1,0) 0x18->(2,0) 0x19->(0,5) 0x1a->(1,5) 0x2d->(1,6);
- elemental palette add = subfamily - 0xb for subfamily 0xc..0xf
  (asm31.s:109271-109276), straight from the record byte.
New top-level `SWORD_ARC_UP` use: the block reuses the existing fitted 0x10.

## Unverified — the limit of "as data", and what the next 33 chips must clear

"No per-chip special case survives" must NOT be read as "no per-row special
case survives". The limits, verifiably:

(a) The (animation, palette) mapping is still a six-row
`match SWORD_ARC_ROW[sub]` with a silent `_ => (0,0)` default, and family
0x13 has SEVENTEEN ROM rows — six are not in our asset (ids 286 sub 0x06,
339 0x05, 370 0x09, 374 0x0a, 376 0x0b, 410 0x01; arc rows 0x1b/0x1c/0x25/
0x5f) and would all fall to (0,0): expanding the asset to those chips
produces a wrong-but-quiet arc. A follow-up must either extend the match
from EffectObjectRows_80E0398 or read the effect table.

(b) `SWORD_HIT_SHAPE` branches only on shapes 4 and 2; Sword's own shape 1
reaches its panels through the default arm, so "the table drives the shape"
is literally true only for the shapes it branches on.

(c) FIXED in this pass: the six row bytes and the 0xc/0xf/0xb palette
literals had lost the per-line `// canon:` tags the id arms they replaced
carried (decision-line provenance density went DOWN while the fitted count
stayed flat). They now carry per-line `// canon:` tags (comment text only,
no behaviour change).

Also still open: only the 48 exported chips carry the tail; the other 363
ChipDataArr rows are not in the asset, so family-driven dispatch is proven
on the sword eleven only. AttackParam1..4 / EffectFlags / LockoutFrames are
exported but unread (StepSwrd's Param1=1, Muramasa's EffectFlags=0xda are
unexplained).

**First thing a follow-up ticket must do: add the version check.** Measured
on a real v1 file against the landed code: `tail = data.len() - count*TAIL =
48012`, the guard is `assert!(tail >= 12 + count*RECORD)` = `>= 1740`, so
the assert PASSES and record 0 would read `family = 0x85` (a blob byte)
instead of `0x14` — the sword arm would dispatch wrong SILENTLY instead of
panicking. The version u32 at offset 4 must be checked in `Chips::new`.
