## Step 3: parity table — record vs src literal

| chip id | src literal (current `barrier_hp`)        | record param (chip.params[0]) | byte_8020B2C row | HP       |
|---------|-------------------------------------------|-------------------------------|------------------|----------|
| 178     | `BARRIER_HP=10` (match id)                | 0x01                          | row 1 (offset 6) | 0x000A=10 |
| 179     | `BARR100_HP=100` (match id)               | 0x05                          | row 5            | 0x0064=100 |
| 180     | `BARR200_HP=200` (match id)               | 0x07                          | row 7            | 0x00C8=200 |

The `match id` in `src/battle.rs:675-680` reads three hardcoded constants
(BARRIER_HP / BARR100_HP / BARR200_HP) that are derivable from the record's
`attack_param_1` byte and byte_8020B2C. The `barrier_palette` arm at
`src/battle.rs:664-670` is a similar match-id pair that maps id → palette
index; the three Barrier records carry no per-chip palette discriminator (all
three have library_type 0), so the palette index is still keyed off the
attack_param_1 byte (chip 178/179/180 map to palette index 0/3/6; the
consts BARRIER_PALETTE_GOLD/PINK then drop, replaced by the indexed lookup).

The handler is shared: family 0x15 subfamily 4 routes through sub_80E3B50
(as already noted in `src/battle.rs:652`), so `set_barrier`/`barrier_palette`
both read from the record via params[0].
