(Bytes are the low-address first LE of the u32 field, with the high byte
= 0xFF the wildcard at +3, and the three code letters at +0/+1/+2.)

The struct layout is `include/rom_structs/ChipData.inc`:
- Codes (u32): loc=0x0
- AttackElement (u8): loc=0x4
- Rarity (u8): loc=0x5
- ChipElement (u8): loc=0x6   ← ticket's "Element" byte
- AttackFamily (u8): loc=0xb
- AttackSubFamily (u8): loc=0xc
- AttackPower (u16): loc=0x1a

The ticket's "byte +0x18 (Element)" is miscounted: Element is at +0x6
(ChipElement), not +0x18 (which is AlphabetSortPos, u16). The byte
+0x1a (AttackPower) cite is correct.

## Why this is a NEGATIVE for the proposed ONE record-driven arm

The ticket claims "family unchanged across 3 ids". The actual data says
otherwise:

- chips 24 (TrnArrw1) and 25 (TrnArrw2): **attack_family 0x28**
- chip 26 (TrnArrw3):                       **attack_family 0x2D**

So the family is NOT unchanged across the three. A single
`if chip.family == 0x28` arm would only catch ids 24 and 25, leaving
TrnArrw3 (id 26) routed to the default `actor::BUSTER` arm and firing
as a plain buster — which is the wrong attack.

The 0x2D family on TrnArrw3 is the same family that Muramasa uses
(src/battle.rs:4477 cites `0x2d => (1, 6)` for Muramasa's palette),
which is the long-sword/blade subgroup — adding it to a TrnArrw arm
by a chip-family check would over-trigger Muramasa too. That family
table is byte_80E0398 row 0x2D, used by the sword family strike arc
machinery. So TrnArrw3's record says it dispatches through the same
table as Muramasa's effect object, not as a TrnArrw arrow at all.

The codes (LE bytes) "GMZ?" / "MSY?" / "BET?" are three distinct
3-letter codes, each with a wildcard 0xFF. They are not "AFK / GMZ /
MSY → ascending-code pattern with wildcard" as the ticket asserted —
the first byte of the code triplet is 0x06, 0x0C, 0x01, which is not a
monotonic run. (If the author meant the second byte 0x0C/0x12/0x13
or third byte 0x19/0x18/0x13: neither sequence is monotonic either.)

chip_element is identical (0x01) across all three, so element cannot
discriminate them apart. AttackPower differs per id (40/50/60), so any
record-driven arm MUST read power from the record byte at +0x1a rather
than from a constant — which the existing per-id constant pattern
already does (chip.power works for the cannon/vulcan/sword/bomb/barrier
arms via chip.power, which the record carries at +0x1a via the v2
asset tail; this is what every existing record-driven arm already does).

## Outcome

NEGATIVE. The "ONE record-driven arm" premise in the ticket is wrong
for this family: chip 26's family 0x2D is a different family from
chips 24/25's 0x28, and the three ids are unrecoverable as a single
family arm. The required reading is per-id (chip.power from +0x1a plus
the family byte from +0xb per row), which the existing per-id-match
pattern already handles. The ticket's acceptance clause
("A NEGATIVE naming the per-id element/power pattern ... also closes
it") is the close path used here.

The follow-on for M4, if any, would be:
- (a) split TrnArrw into two arms: one for `family == 0x28` (ids 24, 25),
  another for `family == 0x2D` (id 26) — but 0x2D is Muramasa's family, so
  this arm cannot be TrnArrw-specific; it would either over-trigger
  Muramasa (wrong) or need an additional chip-id check (which the ticket
  forbids: "no per-id `match chip.id`").
- (b) land TrnArrw as a per-id arm (CHIP_TRNARRW1/2/3 constants), which
  contradicts the ticket's "ONE record-driven arm" / "no `match chip.id`"
  constraint.
- (c) leave TrnArrw on the default buster arm — i.e. no behaviour —
  which is the correct present-state and what the harness row count
  stays at.
