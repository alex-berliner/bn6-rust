## Step 3 — the cited HP-display emitter call sites in this tree

The "damage-taken HP-digit OBJ emission" is the per-frame draw of the
enemy/MegaMan HP digit OBJs from the lagging `hp_shown` counter. There
is exactly one such emitter in src/, gated by F44's `hp_readout_live()`:

- **src/battle.rs:4619 — the gate itself**
  ```
  fn hp_readout_live(&self) -> bool {
      self.fight_latch && !matches!(self.seq.state, SEQ_0C | SEQ_10)
  }
  ```
  `fight_latch` is set at the intro handover (F44's only ROM-side write
  of 4 into `oBattleState_Index_00` at asm00_1.s:9717-9718, reachable
  only via `Index_00 == 0`'s intro machine, table entry
  `sub_8007A0C+1` at asm00_1.s:9567) and at `Battle::new` when the
  fixture declares SKIP_INTRO (src/battle.rs:2297-2300).

- **src/battle.rs:5077-5104 — the gated per-frame draw of enemy HP
  digits**, the only call site in this tree that emits enemy/MegaMan
  HP digit OBJs every frame:
  ```
  for (actor, counter) in self
      .enemies
      .iter()
      .zip(self.hp_shown.iter().skip(1))
      .filter(|(a, _)| {
          a.is_present() && a.hp() > 0 && a.is_targetable() && hp_readout_live
      })
  {
      ...
      self.hud.draw_number_in(frame, hp, px + ..., py + ..., counter.set());
  }
  ```

This `draw_number_in` IS the in-battle HP-digit OBJ emitter. F44's
`hp_readout_live()` is its sole gate. There is no second
"damage-taken-only" digit emitter — when the enemy takes a cannon hit,
`enemy.take_damage(power)` mutates `enemy.hp`, the `hp_shown` counter
ticks down one step, and the next frame's per-frame `draw_number_in` redraws
the lagging value. The whole chain is gated by `hp_readout_live()`.

The CANON counterpart: `updateBattleHudElements_801BEE0` (the routine
the F44 ticket cites at asm00_1.s:9790, decompiled at
reference/bn6f/docs/decomp/asm00_2.c:18257, span asm00_2.s:25587-25635)
is the same call — one update per frame, gated by the & 8 / paused /
terminate chain at asm00_1.s:9753-9795 that F44 already modelled.

So F44's gate (`hp_readout_live()`) covers BOTH the intro path
(intro arm) AND the damage-taken path (every frame thereafter, including
the frame the enemy takes damage and the lagging counter starts moving).
There is no separate lever to port.

## Step 4 — why the lever is unreachable on cannon row even if it existed

The `cannon` Check uses `_chip_rust("01")` (tools/harness.py:1087 →
`_chip_rust` at :722):

```python
def _chip_rust(chip_hex: str, flags: int = 0x1F) -> Callable[[str], Side]:
    desc = {
        "enemies": 0, "megaman_hp": 100, "megaman_col": 2, "megaman_row": 2,
        "hand": [int(chip_hex, 16)], "hand_count": 1, "gauge": 0,
        "flags": flags, "fire_frame": 90,
    }
```

`enemies=0` means no enemy is materialised. The damage-taken path on
this row has NOTHING to take damage: `enemy.take_damage(...)` is never
called because `self.enemies` is empty, so the `for enemy in self.enemies`
loop in `draw()` (src/battle.rs:5103) iterates zero times. The HP-digit
emitter call at `draw_number_in` is never reached for any enemy.

MegaMan also doesn't take damage on this row — Cannon is the only chip
in the hand, no enemy fires back, and `flags=0x1F` includes AUTO_FIRE
(battle.rs seeds/reseeds `auto_ticks` exactly as the old demo-auto harness
did, per tools/harness.py:655-680). MegaMan's HP box draw at
src/battle.rs:3749 IS exercised (the `set_hp` call into hud_bg), but
that draws the digit tiles into the HUD BG3 layer, not OAM OBJ digits,
and `hp_readout_live()` does not gate the MegaMan-box digit tiles
(it gates the per-enemy field-position digits at :5077-5104 and the
MegaMan top-left box via the same draw_number_in for index 0). Either
way, the gate is F44's and already exists.

`flags=0x1F` also includes SKIP_INTRO, so `fight_latch = true` at
`Battle::new`, meaning `hp_readout_live()` is true on every compared
frame. The latch is already open; the gate is already open; the digit
emitter is already called every frame; and the row is 0/0/40 PASS —
because F44's gate already makes the digit-emitter-per-frame exact.
