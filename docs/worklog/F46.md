## CORRECTED BY A LATER AUDIT -- 2026-09-15, by F47's verifier (coordinator-applied)

Two of this worklog's central claims were overridden by the verifier that judged it, and that
verifier was itself wrong. Restoring them, because a later ticket was written on the override:

- **The `--watch` OFS readback claim (above, "mgba `--watch` DOES read the write-only OFS registers
  back (returns last value written)") is CORRECT in substance**, and so is the shared-latch
  observation. Proven on the correct range by F47's verifier: the whole `0x04000010..0x0400001E`
  block reads ONE shared per-frame value (`0xd0fc / 0x4211 / 0x4805 / 0xfffe`, H==V, no ramp) while
  `WININ`/`WINOUT` at `0x48`/`0x4A` in the SAME frame read a genuine `0x3f3f`. The read path is an
  address-agnostic `core->busRead8` per byte (`tools/mgba_capture.c:966-972`), so write-only IO
  returns the data-bus latch and never the register file.
- **The register map the coordinator's stamp inserted here is INVERTED and false.** The scroll
  registers are `0x04000010..0x0400001E` (BG0HOFS `0x10`, BG1HOFS `0x14`, BG1VOFS `0x16`); window
  and mosaic are `0x40..0x4C`; `0xC8..0xDE` is DMA2/DMA3, so **`0x040000D0` is `DMA2WordCount`**.
  Settled from the repo, not prose: `reference/bn6f/constants/gba_constants.inc:11` (`BG0Control
  = 0x4000008`), the struct->IO copy at `reference/bn6f/asm/asm00_0.s:2843-2847`
  (`render_800172C` copies struct+4 for `0x38` bytes) with field names
  `reference/bn6f/include/structs/RenderInfo.inc:11-13` and the BG1 writer at `asm00_0.s:3318`; and
  `tools/agbcc/include/gba/io_reg.h:15-22,43-49,119-137` agrees exactly. This worklog's own note
  that `0x04000018` is **BG2**HOFS (not BG1's, as my ticket said) stands; neither of us had it right
  except by accident.
- **The "shift test is UNREPRODUCIBLE" charge against this worklog is withdrawn.** F47's verifier
  reproduced the load-bearing parts on named dirs: base total **300946 exactly**, and the best-shift
  cycle **(2,1),(1,1),(2,1),(1,0) exactly** on a +-4 grid. The earlier non-reproduction was a method
  artifact -- an unmasked full-frame compare on all 4 bytes/pixel differs 38400/38400 because canon
  and the port differ in the pad byte, so *no* translation can reduce it. "Unreproducible" was an
  artifact of method, not a defect in this ticket.
- What still stands against this ticket: the `1024/1024` and "asset step 2, 37/37 slots" art claims
  (best step match 464/1024, canon's tiles span steps {0,1,2}), the `:3287-3303` -> `:3306-3321`
  cite fix, and the un-named capture dirs. The NEGATIVE outcome is unchanged: readback IS
  unavailable -- established for the right reason this time.
