## Step 4 — port blocked by harness.py scope

The src/ port of the gauge-band wiring would be a one-line change at
src/battle.rs:2181:

```rust
let gauge = match fixture {
    Some(f) => if f.gauge != 0 { GAUGE_FULL } else { 0 },  // current: u8 f.gauge
    None => GAUGE_FULL,
};
```

— to read `f.gauge as u16` (or to add a `gauge_band: u16` field that
harness.py would write at offset N+1, with the existing `gauge: u8`
retained for other rows). The problem is upstream of src/: the
harness.py:156 line

```python
buf[18] = descriptor.get("gauge", 0) & 0xFF  # T32: mask the asm-world gauge value (e.g. 0x4000 at asm00_1.s:15305) to u8 for the FIXTURE.md +18 byte; every existing row's gauge is 0 or 1, so the mask is byte-identical for them.
```

writes the descriptor's gauge byte as a single masked u8. The T32
worklog explicitly documents this as a "byte-identical" pre-existing
contract: every existing row's gauge is 0 or 1, so the `& 0xFF` mask
is invisible to them. GUNNER_ROW's `gauge=0x4000` lands at offset 18 as
0x00, exactly like the prior `gauge=0`. **No src/ change can move the
descriptor byte without touching the harness.**

The ticket's no-touch list is: tools/harness.py (T32 owns), tools/
allowlist.py, tools/trace.py, tools/oracle.py, tools/states.py. The
port is therefore blocked by scope. The acceptance verdict is the
ticket's NEGATIVE clause: "A NEGATIVE naming which gunner layer the
plateau sits on (per step 3) closes it."

If a future M5 ticket wants to land this port, the path is one of:
(a) widen `pub gauge: u8` to `pub gauge: u16` in src/fixture.rs AND
    remove the `& 0xFF` mask in tools/harness.py:156 — but that mask
    is T32's documented contract;
(b) add a new u16 field at offset N (e.g., +28 already used by
    `gauge_tick: u16` so +29+30 is free — but harness.py would need
    a new buf[N:N+2] write);
(c) reuse `gauge_tick: u16` (FIXTURE.md +28) — but the existing
    wiring uses gauge_tick to seed HudTiles' flow counter, not Battle's
    gauge word.

None of these are within the T55 scope.
