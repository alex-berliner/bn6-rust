## Step 2 — can the harness witness a torn frame word?

`--watch 0x02000000:8` (marker magic u32 at +0, frame counter u32 at +4),
appended by mgba_capture after every rendered frame.

- mettaur row, rust side, 120 samples: magic goes 0 → BATT at sample 8 and
  stays; counter 0..111 strictly +1; torn samples: NONE.
- cursor row, rust side, 260 samples (the row that actually tears): magic
  never anything but 0 or BATT (torn samples: NONE); counter 0..251 with four
  anomalies near samples 131/140: the counter reads 123 twice then jumps to
  125 (124 never sampled), and 132 twice then 134 (133 never sampled).

Interpretation of the anomalies: the watch sample cadence is not 1:1 with the
ROM's battle-frame loop — occasionally two loop iterations fall inside one
emulated frame. But every sample still reads a COMPLETE word: mgba_capture
reads the watched bytes after `core->runFrame()` returns
(tools/mgba_capture.c:970-974), i.e. between instructions, so it can only
ever observe completed stores. A mid-update (torn) word is structurally
unobservable by this sampler, not just unobserved. On top of that, the magic
the aligner keys on is a constant (`BATT`) after its first write, so even
byte-wide stores could only ever be caught torn on that first write — and
`find_marker_origin` skips any value that is not exactly the magic, so a torn
first write would delay the origin by one frame, never align on a torn value.

## Step 3 — the reader, and whether it needs a stable-two-word protocol

The reader that takes the alignment is `find_marker_origin`,
tools/harness.py:93 (magic unpack at tools/harness.py:105); it reads only the
u32 at 0x02000000 from each 8-byte watch sample — the frame counter at
+0x02000004 is never read by the alignment path. Verdict: no protocol change
is warranted. The sampler cannot see a torn word (reads happen between
instructions, after runFrame returns), and the word it reads is a constant
magic that `find_marker_origin` matches exactly, skipping everything else.
If this read path were ever moved to an instruction-level sampler
(`--watch-write` territory) or the marker ever carried a value that changes
every frame, the right protocol would be the ticket's stable-two-word option:
an even/odd sequence number written BEFORE the value it guards, with the
reader picking the matching pair — not a magic bump. Not implemented here;
no code changed.

## Reproducing the region checksum

```python
import sys, hashlib; sys.path.insert(0, "tools")
import harness as H, chip_compare as cc, numpy as np
chk = [c for c in H.CHECKS if c.name == "cursor"][0]
res = H.run(chk.rust(chk.ui), chk.canon(chk.ui), chk.frames, chk.align, variant_label=chk.ui)
for k, c in enumerate(res.counts):
    if not c: continue
    a = cc.frame_array(res.canon_dir, res.align.canon_ref + k)
    b = cc.frame_array(res.rust_dir, res.rust_origin + res.rust_offset + k)
    mask = (a != b)[..., 0] | (a != b)[..., 1] | (a != b)[..., 2]
    ys, xs = np.nonzero(mask)
    payload = b"".join(bytes([y, x]) + a[y, x].tobytes() + b[y, x].tobytes()
                       for y, x in sorted(zip(ys.tolist(), xs.tolist())))
    print(k, len(ys), (xs.min(), xs.max(), ys.min(), ys.max()),
          hashlib.sha256(payload).hexdigest()[:16])
```
