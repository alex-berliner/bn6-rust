## Step 3 — attribute k=17: PC 0x08011756 inside `sub_801171C`, the post-attack-state exit routine -- DONE

`python3 tools/csrc.py 0x08011756` → routine `sub_801171C` at `0x0801171C` (size 72 B), `reference/bn6f/asm/asm00_2.s:5688-5727`:

```
loc_8011754:
    mov r0, #8
    strb r0, [r5, #oBattleObject_CurAction]   ; <-- 0x08011756, k=17 store
    mov r0, #0
    strh r0, [r7, #oAIAttackVars_Unk_00]
    pop {r6,r7,pc}
```

The full routine (5727-5728: the symbols right before/after it are `object_exitAttackState` at 0x08011714 and `calledOnBAtkProbInit_8011764` at 0x08011764):

```
sub_801171C:
    push {r6,r7,lr}
    ldr r1, [r5,#oBattleObject_AIDataPtr]
    mov r7, #0xa0; add r7, r7, r1    ; r7 = &AIAttackVars (base + 0xa0)
    mov r0, #0; strb r0, [r7,#oAIAttackVars_Unk_1b]    ; zero Unk_1b
    ldrb r6, [r7,#oAIAttackVars_Unk_1c]                  ; r6 = Unk_1c
    cmp r6, #4
    beq loc_8011754                                      ; Unk_1c==4 -> write 8, exit
    cmp r6, #2; bne loc_8011736
    ldrb r0, [r7,#oAIAttackVars_Unk_05]
    strb r0, [r1,#oAIData_ChipLockoutTimer]             ; Unk_1c==2: copy Unk_05 -> ChipLockoutTimer
loc_8011736:
    cmp r6, #3; bne loc_801173E
    ldrb r0, [r7,#oAIAttackVars_Unk_05]
    strb r0, [r1,#oAIData_Unk_15]                        ; Unk_1c==3: copy Unk_05 -> Unk_15
loc_801173E:
    mov r0, #0; strb r0, [r1,#oAIData_Unk_1a]
    ldr r0, dword_8011760 (=0x1000003f)

    bl sub_8012EA8

loc_8011754:
    mov r0, #8
    strb r0, [r5,#oBattleObject_CurAction]    ; <-- THE k=17 STORE

    strh r0, [r7,#oAIAttackVars_Unk_00]
    pop {r6,r7,pc}
```

The store itself is unconditional after a 4-branch dispatch on `oAIAttackVars_Unk_1c` (r6), which itself runs after `Unk_1b = 0`. The PC 0x08011756 is `loc_8011754` (the unconditional tail), so the predicate is "(an earlier branch set Unk_1b=0 and skipped the `Unk_1c==4` early-out OR dispatched through the body)". Crucially the LOSING 0x0A CurAction is what `MettaurHopExec_8109CE6` (the ENEMY hop executor's Unk_00=0 step) arms in its `object_canMove` fallback that refuses a move: T50's task sets `Unk_1a=0` and calls `object_exitAttackState` (0x08011714). Look at the call sequence — `sub_801171C` (0x0801171C) sits EXACTLY 8 bytes after `object_exitAttackState` (0x08011714).

**The k=17 store is therefore: MettaurHopExec_8109CE6 set Unk_1a=0 (it refused to hop — there is no panel free), then took the `object_exitAttackState` path, which dispatched into `sub_801171C`'s exit, clearing the per-state vars (`Unk_1b = 0`, `Unk_00 = 0`) and writing `CurAction = 8`.** The 0x0A → 0x08 edge IS the appear phase of the Mettaur: from frame k=0..16 the hop executor's Unk_00=0 step holds (the object is appearing — not actionable), and the canonical "appear phase ends" predicate is "hop executor's `object_canMove` refuses an Unk_1a=0 hop and falls through to `object_exitAttackState`".

In BN6F source: `MettaurHopExec_8109CE6` is at `reference/bn6f/asm/asm31.s:170689` (per the citation in src/objects.rs:323), it sets Unk_1a=0 on a refused hop, and the LR 0x08011755 inside `object_exitAttackState` (size-1, immediate strb at +2 from start, or +6 from entry) confirms the call sequence: `object_exitAttackState` is at 0x08011714, so the LR 0x08011755 (= 0x08011754 final byte of preceding instr) corresponds to a `bl object_exitAttackState` at 0x08011754..0x08011755 in the caller — which is LOC_8011754 itself = `strb r0,[r5,#CurAction]` ... wait, that's not right.

Re-reading: LR is the value of LR when the bl returns, which for a "bl X+1; thumb2" is the instruction AFTER the bl. Here lr=0x08011755, which equals 0x08011756 - 1, the off-by-one addressing the THUMB BIT, meaning the `bl X` was at 0x08011754 and the call target was object_exitAttackState (or, equivalently, an instruction right before the strb). Actually for `bl object_exitAttackState` the LR saved = PC + 4 + 1 (thumb). PC-relative: if the bl is at 0x08011752 then LR = 0x08011757. If the bl is at 0x08011754 then LR = 0x08011759. Neither matches 0x08011755.

Probably the LR is the LR of the caller's CALL to sub_801171C (not the inner strb's own LR). The structure of sub_801171C is: outer-prologue push, body, then tail `loc_8011754:` which does the strb and returns. The LR captured here is probably from a function that called sub_801171C (outer caller). The exact LR-delving may not matter — what matters is that the WRITE PC 0x08011756 is unambiguously inside `sub_801171C`'s `loc_8011754` tail.
