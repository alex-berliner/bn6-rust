## Mechanism one-liner

Four CHIP_VULCAN* consts deleted (src/battle.rs:270-273); use_chip
(:4161) and chip_strike (:4506) early-return on `chip.family ==
VULCAN_FAMILY (0x17)` in place of the two `CHIP_VULCAN |
CHIP_VULCAN2 | CHIP_VULCAN3 | CHIP_SUPRVULC =>` arms; SHOTS read from
`VULCAN_SHOTS_BY_SUB[chip.subfamily as usize]` (dword_80EBFEC =
0xA050403); the SuprVulc fireball spawn now keys on
`chip.subfamily == VULCAN_SUPRVULC_SUBFAMILY (0x03)`. tools/inventory.py
AS_DATA_FAMILIES extended `{0x13, 0x15, 0x21} -> {0x13, 0x15, 0x17, 0x21}`
(four new chips in the asset: ids 5/6/7/8). docs/SCOPE.md M4 line
updated to 18/411.

## What is unverified

Four chips in the asset carry attack_family=0x17 (verified by sweep over
all 411 struct blocks), so the early-return is exact on this build.
Widening the asset to deliver another family-0x17 chip (no other row
exists in ChipDataArr_8021DA8 today) would re-run the Vulcan pose and
barrel on the new chip too, which would be correct only if it shares
sub_80EBF10 / sub_80EBF6E's behaviour and the SHOTS table is extended
to a fifth subfamily entry (the current array is fixed `[u8; 4]`; a
fifth subfamily would panic on indexing, exactly the failure mode the
ticket's widening-asset rule prefers). src/fixture.rs:547's
`CHIP_VULCAN` mention stays: the deck-entries list there is a
demo-custmatch / demo-cardname scenario fixture, not a per-id index of
an amount, and the literal is in a `//` doc comment (precedent T52).
