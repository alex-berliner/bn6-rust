## 1. Is the capture engine scanline-accurate for mid-frame writes? — NO VBLANK GATE IN THE TOOL (CONFIRMED), mGBA renderer fidelity UNKNOWN

- `tools/CAPTURE_NATIVE.md:30-45`: capture links the mGBA *core*, "steps `core->runFrame`", one raw
  framebuffer file "per rendered frame ... straight from the core's renderer output buffer".
- `tools/mgba_capture.c:941-945`: the frame step is a single `core->runFrame(core);` (the `--trace-pc`
  branch single-steps only the first `trace_steps` instructions **then** "hand off to a normal
  runFrame() to finish the frame out", `mgba_capture.c:919-943`).
- `tools/mgba_capture.c:662-707, 968-975`: `--watch addr:len:file` reads `busRead8` for every watched
  byte **after the frame has actually run** ("append this frame's snapshot ... after the frame has
  actually run"). `--dump`/`--peek` read once at load/end (`mgba_capture.c:1023`).
- There is **no** scanline loop, no LCD/vblank callback, and no "sample the screen at vblank" step
  anywhere in the capture path. The tool records whatever the emulator's renderer produced for the
  whole frame.

CONFIRMED: the capture path cannot be the reason a mid-scan register write goes unseen — it has no
vblank sampling gate at all. The cheapest refutation of S1 ("capture is taken only AT vblank") does
**not** apply.
UNKNOWN: whether mGBA's software renderer composites scanline-by-scanline honouring a mid-frame
`BGxCNT` store. mGBA is not vendored here (`vendor/agb` is agb, not mgba), so this is external
behaviour; a `380131 -> 380263`-style canon drift argument cannot settle it either.
CONSEQUENCE: `--watch` snapshots are end-of-frame state only. They date a store to *a frame*, never to
a scanline; a vblank store and a scanline-22 store both read as "flipped at capture N".

## 2. Order inside one `commit()` — CONFIRMED

`vendor/agb/agb/src/display/mod.rs:318-345` (`GraphicsFrame::commit`), in order:
1. `self.others.vblank.wait_for_vblank();` — **first statement**, line 321;
2. dma swap + old dma `cleanup()`;
3. `self.oam_frame.commit()` (331); **4.** `self.bg_frame.commit()` (332);
5. blend / mosaic / windows; 6. `dma.commit()`; 7. background palettes; 8. `VRAM_MANAGER.gc()`.

`vendor/agb/agb/src/interrupt.rs:417-427` `wait_for_vblank`: if `last_waited_number < NUM_VBLANKS`
it **returns immediately** — a commit whose vblank already passed writes its registers *during* the
frame, not at the boundary. (Same fact `src/main.rs:414-425` documents for the first commit.)

`vendor/agb/agb/src/display/tiled.rs:453-497` (`BackgroundFrame::commit`), in order:
- `DISPLAY_CONTROL` store once: video mode + `enabled_backgrounds = ((1<<num_regular)-1) |
  (((1<<num_affine)-1)<<2)` + forced-blank=0 (461-466);
- then, per shown regular bg `i` **in index order**: `BGxCNT` store `0x0400_0008 + i*2` (471-473);
  `BGxHOFS` = `0x0400_0010 + i*4` (475-477); `BGxVOFS` = `0x0400_0012 + i*4` (478-479); **then**
  `commit_data.screenblock.copy_tiles(&commit_data.tiles)` (482-485) and `tiles.clean(...)` (486).
  Affine blocks are the same shape at 488+ (`BGxCNT` `0x0400_0008 + i*2`).

So per background the order is CNT (and scroll) **first**, map copy **second**, both after the same
vblank wait, contiguously in CPU time. `screenblock.rs:40-47` `copy_tiles` is
`copy_from_nonoverlapping` — a **plain CPU halfword loop, not DMA**. A `Background32x32` screenblock
is `num_tiles()` = 1024 entries = **2048 bytes** (`tiled.rs:362-371`: `SCREENBLOCK_SIZE = 0x800`).
CONFIRMED: (a) CNT register stores, then (b) map copy; (c) tile *char* copies never happen in
`commit()` at all — agb inserts each distinct tile's char data into VRAM at its first `set_tile`
(`tiles.rs:94-97` + `vram_manager.rs`, and `docs/worklog/T133.md:124-127` states it outright:
"agb allocates one VRAM tile per distinct tile index at its first `set_tile`"). So the only bulk
copy in the commit path is the **map**.

Priority/CNT timing — CONFIRMED: value captured at `show()` time, written at `commit()` time.
`regular_background.rs:438-445` ("won't be visible until you call `commit()` ... calling `show()`
takes a snapshot"), `:457-470` `show()` builds `bg_ctrl_value()`, `:490-495` `set_priority` "won't
take effect until the next call to `show()`", `:508-518` `bg_ctrl_value()` reads `self.priority`.
So S1 must act through those snapshotted stores; S2 through the copy that follows them.

Arithmetic caveat, PLAUSIBLE-at-best: `docs/worklog/T118b.md:44` measures "whole screenblock =
2048 B ~= 4.1k cycles ~= **3.3 scanlines**" (1232 cycles/line). One dirty 32x32 map is ~3.3
scanlines, not 22. A 22-row (27k-cycle, ~13 KB) spill needs **4+ dirty maps in one commit**, or
larger (64x64) maps. Whether `field`/`backdrop`/`hud`/`shown`'s maps are 32x32 or 64x64 is
UNKNOWN to me — I did not read `src/field.rs`/`src/backdrop.rs`/`src/hud.rs`. Cheapest check:
`--watch 0x04000008:2` on each of BG0..BG3 in one run and decode the screen-size bits 14-15/4-5.

## 3. What changes hardware BG index order — `show()` call order, CONFIRMED

- `tiled.rs:403-416`: `set_next_regular` assigns `bg_index = self.num_regular; self.num_regular += 1`
  — i.e. the **Nth background shown this frame gets hardware index N-1**. That assignment is then
  written to `BGxCNT` in `commit()` (`tiled.rs:468-486`). So the register values change at commit
  time; the *ordering* is decided at show time. CONFIRMED.
- `src/battle.rs:4892-4935` (the comment claims agb assigns 0,1,2... in `.show()` order; the asm
  reference in the comment is `src/battle.rs:4546-4549` in the harness note, stale) and the call
  site: `if self.shown.is_none() { self.filler_bg.show(frame); }` then `backdrop.show`,
  `self.bg.show`, `hud_bg.show` (4934-4947), then `self.shown.as_ref().map(|w| w.show(frame))`
  (4957). When `self.shown` comes up the filler is skipped, so every shown layer shifts index 0..2.
- A layer that stops being `show`n does **not** get a store: `commit()` iterates
  `.take(self.num_regular)` (`tiled.rs:468-470`), so only indices `0..num_regular-1` are rewritten,
  and the vacated top index keeps its stale register value — but it is masked off by the single
  `DISPLAY_CONTROL.enabled_backgrounds` store (461-466). PLAUSIBLE (source-clear, but the ordering
  consequence for the *split scanline* is not proven by any capture): what a viewer sees at the
  renumber is a mix of one commit's DISPLAY_CONTROL + N CNT stores + N map copies, all issued
  back-to-back after vblank.
- `window.show(frame)` at 4957 is the `shown` RESULT window's own background: its `BGxCNT`
  (priority via `set_priority`, charbase) is snapshotted when it is shown and stored in the same
  commit. UNKNOWN which priority/screenblock it lands on — that is what the two CNT values say.

## 4. The one observable that separates S1 from S2 (my check of the verifier's guess)

GUESS AS GIVEN IS WRONG (window too small). VRAM geometry, CONFIRMED from source
(`tiled.rs:362-371`): `VRAM_START = 0x0600_0000`, `SCREENBLOCK_SIZE = 0x800`,
`SCREENBLOCK_ALLOC_START = VRAM_START + CHARBLOCK_SIZE*2 = 0x0600_8000`, `end =
SCREENBLOCK_ALLOC_START + 0x4000 = 0x0600_C000`. So **maps live at blocks 16..23 =
0x06008000..0x0600BFFF**, 2 KB each; the existing watch `0x06004000:16384` ends at
`0x06007FFF` — tiles only, as stated.

Decode the two BG0CNT values (screen-base block = bits 8-12, `regular_background.rs:508-518` sets
`screen_base_block`): `0x1100 >> 8 = 0x11 & 0x1F = 17` -> map at `0x06008800`; `0x1303 >> 8 = 0x13 &
0x1F = 19` -> map at `0x06009800`. (0x1303 also sets priority P3, 0x1100 is P0 — CONFIRMED by bit
layout, but that the *pre*-flip value belongs to `filler_bg` and the *post*-flip to `shown` is
PLAUSIBLE only.) `0x06008000:4096` = blocks 16..17 = `0x06008000..0x06008FFF` therefore contains the
**pre**-flip map and **excludes block 19 (`0x06009800`)**, the post-flip one — the verifier's window
would watch the map that is being vacated, not the one that must appear.

Corrected, literal command (fixture/flags per `tools/harness.py:2215-2218`: `--only-bg 0` for rust,
`--only-bg 1` for canon, `fixture=FIELD_ZERO`, `script=Start@10`; pass whatever `plain_rom()` is in
this checkout):

```
tools/mgba_capture.sh <rust-plain-rom> /tmp/t142_rust 40 --only-bg 0 \
  --watch 0x04000008:2:/tmp/t142_bg0cnt.bin \
  --watch 0x06008000:8192:/tmp/t142_scr.bin
# same, canon side: <sterile.gba> + PAUSED loadstate + DELETE_ENEMY + --only-bg 1
```

`--watch` costs **no extra capture** (it is read after each `runFrame`, `mgba_capture.c:662-707,
968-975`), has no length cap (16 watches max; only `--watch-write` has the 64-byte budget,
`mgba_capture.c:713-745`), and its `busRead8` reads cannot perturb state. 8192 B x 40 frames = 320 KB.
Window byte map: pre-flip BG0 map = `0x06008800..0x06008FFF` = bytes `0x800..0xFFF` (halfwords
0..1023); post-flip BG0 map = `0x06009800..0x06009FFF` = bytes `0x1800..0x1FFF` — i.e. **the last 2 KB
of the 8192-B window is the map that must appear on the flip frame** (2 KB of `u16` map words,
`Tile` index + palette bits).

Read-out rule (the decider):
- If, on the capture whose `BG0CNT` snapshot is `0x1303` and whose rows 0..21 are black, the 2 KB at
  `0x06009800` **already** equals the new map (and the band is still black), then the map content was
  in place before that frame's visible scanlines: a REGISTER change landing mid-scan is the only
  remaining explanation -> **S1**. (A map *spill* would show a mixed/partial map there, not a finished
  one.)
- If instead `0x06009800` only becomes the new map on that frame's or the next frame's snapshot while
  the band is black, the map copy itself was late -> **S2**.
- Adding `--watch 0x04000008:2` in the same run is what event-locks the flip to a capture number
  instead of trusting `canon_ref=135`/`rust_offset=113`; `--watch 0x04000000:2` (DISPLAY_CONTROL)
  does the same for the enable-mask change.
Caveat, UNKNOWN: no tool in `mgba_capture.c` can stamp a store with a scanline (see §1), so this
separates S1/S2 by *content timing*, not by directly observing a mid-scan store.

## TWO THINGS THE TICKET SHOULD DO THAT I DID NOT ASK FOR

1. **Record the frame's boundary commits as RAM, not just VRAM**: put `--watch 0x04000008:2`
   (BG0CNT), `0x04000000:2` (DISPLAY_CONTROL), and the other three `0x0400000A/0C/0E:2` in the *same*
   capture as the map window, so the flip frame is event-locked in-capture rather than by the harness's
   hand-carried `canon_ref=135`/`rust_offset=113`, and so the pre/post screen-base and enable-mask
   values are read rather than assumed. Two bytes per register per frame, no extra capture.
2. **Re-run the pad control the way T137 did**: build one worktree at `SEAM_PHASE_PAD_ITERS=17` and
   one at 25 (or 0) and compare the band *height* on `field-bg1`, because T139's "pad 17<->25
   byte-identical" and T137's "pad-17 builds differ (23 vs 22 rows)" cannot both be explained by the
   pad alone. If a pad change moves the row-22 boundary, S1 (a register store's scanline) gains support;
   if only footprint changes move it, S2 does. This also keeps `wt/t138`'s in-flight pad sweep from
   being the only sweep on record.

## THE PREMISE I CANNOT VERIFY FROM SOURCE

That S2, **as worded** ("copies the WHOLE screenblock ... spills past vblank into the first visible
scanlines every frame", `src/main.rs:307-321`), can produce a band **22 rows** tall. `T118b.md:44`
measures one whole screenblock copy as ~3.3 scanlines; 22 rows needs ~13 KB of copy inside one commit,
i.e. four 32x32 maps dirty in the same `bg_frame.commit()` (or fewer, larger 64x64 maps). I did not
read `src/field.rs`/`src/backdrop.rs`/`src/hud.rs`, so I cannot say what map sizes the four shown
backgrounds use, nor whether all four ever go dirty in the same frame — so I can neither confirm nor
kill S2's arithmetic. Same class of UNKNOWN: that mGBA composites scanline-by-scanline (not vendored
here), which is the only thing that lets *either* seam produce a horizontal cut at all.
