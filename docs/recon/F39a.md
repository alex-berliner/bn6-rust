## B — PAL_OBJ slot choice

`reference/bn6f/asm/sprite.s:254-303`, `sub_8002818` (called from `asm03_2.s:808` and `:1152`, one call per active slot, `r5 = slot_base+0x20`):
```
sub_8002818:
	push {lr}
	ldr r0, [r5,#0x34]      ; affine/alt source ptr
	tst r0, r0
	bne loc_800282A
	ldr r0, [r5,#0x1c]      ; asset header ptr
	ldr r0, [r0,#4]
	add r0, #4
	ldr r1, [r5,#0x18]      ; frame offset
	add r0, r0, r1
loc_800282A:
	ldrb r1, [r5,#4]        ; Unk_04
	ldrb r2, [r5,#5]        ; Unk_05
	add r1, r1, r2
	lsl r1, r1, #5
	add r0, r0, r1          ; source = asset + frame + (Unk_04+Unk_05)*32
	ldrb r1, [r5,#0x15]     ; ObjectSprite.Unk_15
	lsr r1, r1, #4          ; SLOT = Unk_15 >> 4   <-- the whole slot choice
	ldr r3, off_8002868     ; = byte_3001550  (0x03001550)
	lsl r1, r1, #5
	add r3, r3, r1          ; dest = 0x03001550 + slot*32
	mov r6, #0
loc_8002840:
	ldr r2, [r0,r6]
	str r2, [r3,r6]
	add r6, #4
	cmp r6, #0x20
	blt loc_8002840         ; copy 32 bytes = 16 colours
	ldrh r7, [r5,#6]        ; Unk_06
	tst r7, r7
	beq locret_8002862
	lsl r0, r7, #0x11
	lsr r0, r0, #0x11       ; blend param
	lsr r2, r7, #0xf        ; jump index (sub_3005EF0 off_3005F20)
	lsl r2, r2, #2
	mov r6, #0x20           ; 16 entries
	mov r7, r3              ; dest

	bx r1
locret_8002862:
	pop {pc}
```
Findings (derived, straight off the code):
- The slot is a FIXED, pre-existing field: `Unk_15 >> 4` of the sprite record (`sprite.s:273-275`). No bitmap, no first-fit search, no free-list read, no counter — `sub_8002818` never looks at another slot to choose one.
- `0x03001550` holds 16 × 32 bytes = `0x3001550..0x300174F`: an IWRAM mirror of the 16 OBJ palettes; `slot*0x20` is the destination. (Also referenced at `asm00_0.s:4839-4892`, `asm32.s:22126+`, `asm03_1_1.s:4995+`.)
- `sub_3005EF0` (`asm38.s:508-547`) is a colour-blend of the 16 staged words in place, not an allocator: `r0` = blend param, `r2` = jump index into `off_3005F20`, `r6` = 0x20, `r7` = dest.
- The OAM palette nibble itself is written literally into the entry, not resolved through the slot allocator: `asm38.s:1352-1355`
```
	ldrb r4, [r2,#4]        ; frame/OAM list entry byte 4
	lsl r1, r4, #0x1c
	lsr r1, r1, #0x1c       ; low nibble
	lsl r1, r1, #0xe
	orr r3, r1              ; -> attr1 bits 12-15 = OAM palette bank
```
- Fill order of `0x03001550`: driven by the driver's slot loop order (`asm03_2.s:786-830`, r7 0..14; `:1141-1160`, 0..5) and by each sprite's pinned `Unk_15>>4` — i.e. by slot index, not by allocation order.

UNVERIFIED (writer of `Unk_15`): which routine pins the number. Candidates are `sprite_load`/`sprite_initialize` (`sprite.s:86`, `:101` — those write `Unk_03/category`, not `0x15`) or the battle-object→sprite bind; I did not find the `strb ...,[r5,#0x15]` writer.
UNVERIFIED (0-5 vs 0-15): whether canon's 16 populated IWRAM palettes at the opening are simply every active sprite's pinned slot, or a per-battle palette table preloaded before the spawn window. Nothing read so far preloads `0x03001550` wholesale.

Our counterpart — `src/spr.rs:699-763` `PaletteVramSingle::try_allocate_shared` (call sites `:703`, `:715`, `:731`, `:759`):
- IS a counterpart of canon's *staging write*: it hands the sprite a 16-colour palette that ends up in an OBJ palette bank (`assets.palette(index)` → `Palette16` → shared slot), and the `part_palette` it returns is what our part binds.
- IS NOT a counterpart of `sub_8002818`'s slot choice: it is an order-dependent first-fit allocator over free/shared slots, so the bank number is a function of allocation order, not of the asset. Canon's bank is `Unk_15>>4` (data) and the OAM attr nibble comes from the frame-list byte (`asm38.s:1352`).
- Our `pal_offset` (`src/spr.rs:65/122`, `flags >> 4`, i.e. the same nibble as `asm38.s:1352`) is used to *pick a different asset palette to allocate* (`src/spr.rs:750-763`: `offset_index = frame.pal + shift + e.pal_offset`, then `try_allocate_shared(&self.assets.palette(offset_index))`) — the nibble selects content, while the bank number is whatever the allocator returns.

Cheapest runtime checks
1. `--peek` `0x03001550` (0x200 bytes) at k=0 and k=32 on a canon capture; if slot n holds the asset palette of the sprite whose record says `Unk_15>>4 == n`, the pinned-field shape is confirmed and the 0-15 population is not a preloaded table.
2. `--watch-write` the ObjectSprite byte `slot_base+0x20+0x15` for the enemy's slot during k=0..2 → identifies the writer of the pinned slot.
3. Control capture pinning our `PaletteVramSingle` index to the frame-list nibble (`frame.pal + pal_offset`, no allocator) for the enemy and HUD rows: if our attr2 bits 12-15 become 6/2 and the "pal[0] == canon pal[14]" mismatch disappears, the allocator shape is the whole cause.
4. `--peek` the asset OAM entry byte 4 for the part that reads ours-10/canon-2 and ours-14/canon-6 — if those nibbles are literally 2 and 6, ours is replacing a literal bank with an allocator index; if not, palettes are missing from our assets instead.
